## Project overview

DriverVarázsló is a Windows driver-management utility (Hungarian UI/comments) distributed as a single PyInstaller-built `.exe`. It manages third-party/inbox drivers (list, force-delete, backup/restore, offline WIM/ESD extraction), can repair non-booting Windows installs (BCD/bootloader rebuild from WinPE), pauses Windows Update driver pushes, removes ghost devices, runs a one-click "AutoFix" routine that chains a reboot via a scheduled task, generates an HTML hardware report with S.M.A.R.T. data (one-click printable to the shop's network printer), launches bundled stability-test tools (FurMark/Prime95/Linpack/HWiNFO/HD Sentinel) with screen-sleep temporarily disabled and their startup dialogs auto-answered, shows/disables BitLocker on the system drive, and downloads a standalone firewall net-blocker batch script. See [README.md](README.md) for the full feature list — but note the README has drifted from the code: it describes the AutoFix reboot chain as using the `RunOnce` registry key (it is a **scheduled task**, `DriverVarazsloResume` — there is no `RunOnce` anywhere in the tree), names the release script `rebuild.bat` (the real name is `rebuild_verzioszam_novelessel_es_github_pushal.bat`), claims an `atexit` handler kills orphan processes (see the process-exit rules below — `atexit` would never fire), and says Python 3.14 (the build machine runs 3.12). Trust the code and this file over the README.

## Commands

**Do NOT build the exe yourself — the user builds it when they want to** (explicit user decision). They have the two build scripts in the project folder (`build.bat`, `rebuild_verzioszam_novelessel_es_github_pushal.bat`) and run them by hand. Make and verify your code changes (syntax check + importing the API classes + driving the pure/mixin logic against live data — see below), then tell the user it's ready; leave the actual PyInstaller build/release to them unless they explicitly ask you to build. This is the build-side twin of the "never commit/push on your own initiative" rule.

There is **no test suite, no linter config, and no `requirements.txt`** in this repo — "verifying a change" ultimately means building the exe and running it, but that build is the *user's* step, not yours.

```bash
python driver_tool.py            # run from source (GUI; self-elevates via UAC)
python driver_tool.py --cli      # run from source, force the text-menu CLI
python -m PyInstaller --clean --noconfirm DriverVarazslo.spec   # build -> dist/DriverVarazslo.exe
python -m py_compile app/gui/autofix.py             # cheapest syntax check while editing
python -c "import app.gui.api, app.cli.api"         # both API classes still assemble
cmd /c rebuild_verzioszam_novelessel_es_github_pushal.bat < nul   # FULL RELEASE - only on explicit request
```

**Both `.bat` files end with `pause`.** Call PyInstaller directly (as above) rather than `build.bat`, or the build appears to produce no output at all and hangs waiting for a keypress. Same reason `< nul` is mandatory on the release script — which bumps `BUILD_NUMBER`, builds, commits and **pushes**; see the Git / release rules before ever running it.

### Verifying logic without a machine to break

"No test suite" does **not** mean "nothing is testable". The `app/*_core.py` modules import nothing from `ctypes`/`pywebview` and never call a subprocess themselves — **every function that needs one takes `run` as a parameter** — and the parsing/decision helpers are pure functions. So the risky logic — HWID matching, DISM output parsing, downgrade/duplicate filters, delete-result classification — can be exercised in-process, in a second, with a stub:

```python
from app import drivers_core
drivers_core.parse_dism_driver_list(open('sample_dism_output.txt').read())   # pure

class R: returncode, stdout, stderr = 0, 'Driver package deleted successfully.', ''
calls = []
def fake_run(cmd, **kw): calls.append(cmd); return R()
drivers_core.delete_driver_package(fake_run, 'oem7.inf')   # asserts on `calls`
```

Do this for any change to matching/parsing/filtering rules, using **hardware IDs and command output copied verbatim from the field log** — that is how the R9-200 GPU-matching bug was pinned down and confirmed fixed. Put throwaway scripts in the scratchpad, not the repo.

**The GUI mixins are drivable too — and on a Windows dev box they can run against *live* data, which is stronger than any captured sample.** A mixin only needs `_run` and `emit`; nothing forces you to build the whole `DriverToolApi`:

```python
class F(GuiHwScanMixin):
    def _run(self, cmd, **kw): return subprocess.run(cmd, capture_output=True, text=True, encoding='utf-8')
    def emit(self, *a, **k): pass
f = F()
f._catalog_search_collect(candidates, f._get_installed_driver_info())   # real WMI + real catalog
```

This is how the "vendor driver instead of the generic one" work was validated end-to-end without ever installing anything: real `Win32_PnPEntity`/`Win32_PnPSignedDriver` output, real `catalog.update.microsoft.com` queries, decisions printed instead of executed. It is also what exposed that the audio device advertises **only** SUBSYS-scoped hardware IDs — a fact no captured sample would have suggested. Pair it with a stubbed `_catalog_fetch_rows` (returning hand-written rows) to unit-test the *decision* logic offline: which row wins, when a version gate applies, when nothing is offered.

**Two more patterns that keep getting reinvented — start from these instead.** Both are offline, deterministic, and cover the two areas most likely to break silently.

*Catalog decision logic, with no network.* Stub `_catalog_fetch_rows` to hand-written rows and stub the `DownloadDialog` fetch; then every branch of the release gate (newer / not newer / inbox guard / `generic_ok`) is one call. Rows are `(guid, title, lowercased_row_text, 'YYYY-MM-DD')` — the row text is what `_catalog_row_score` reads, so keep a realistic "windows 11 client, version 24h2 … drivers (other hardware)" string in it:

```python
import io, ssl, urllib.request
from app.gui.hwscan import GuiHwScanMixin
class _Dlg(io.BytesIO):
    def __enter__(self): return self
    def __exit__(self, *a): return False
urllib.request.urlopen = lambda *a, **k: _Dlg(
    b"downloadInformation[0].files[0].url = 'https://catalog.example/x.cab';")

class F(GuiHwScanMixin):
    target_os_path = None
    def _catalog_fetch_rows(self, hwid, ctx): return ROWS
    def emit(self, *a, **k): pass
F()._catalog_find_driver(device_dict, {PNP_UPPER: installed_dict}, ssl.create_default_context())
```

*Scheduled-task / chain-flag propagation.* The resume legs are separate processes, so a dropped flag is invisible until a customer machine misbehaves — assert on the generated `-Argument` string instead of trusting the call sites:

```python
class R: returncode, stdout, stderr = 0, '', ''
class F(GuiAutofixMixin):
    _si = _nw = None
    def __init__(s, **flags): s.__dict__.update(flags); s.cmds = []
    def _run(s, cmd, **kw): s.cmds.append(cmd[-1]); return R()
    def emit(s, *a, **k): pass
f = F(_autofix_skip_printers=True, _autofix_allow_storage=False, _autofix_allow_firmware=True)
f._schedule_autofix_resume('--resume-autofix')
f.cmds[0].split("-Argument '")[1].split("'")[0]   # -> "... --resume-autofix --skip-printer-drivers --allow-firmware"
```

Iterate `itertools.product((True, False), repeat=N)` over the flags — every combination, every time one is added.

Two harness gotchas that waste time otherwise: run these with **`PYTHONIOENCODING=utf-8`**, or the first `print()` of an emit string dies on cp1252 and the emoji crash reads like a code bug (the real `emit` sends JSON to JS and is unaffected); and generated PowerShell can be syntax-checked without executing it — `[System.Management.Automation.PSParser]::Tokenize($script, [ref]$errors)` on the string pulled out of the module.

Still out of reach without a real machine and `dist/DriverVarazslo.exe`: anything that changes the device stack (installs/deletes), the stress automation, and the AutoFix reboot chain.

### Field logs are the primary bug report

Bugs in this project arrive as a `DriverVarázsló_debug.log` from a shop machine, not as a stack trace.

**Where to find them: `debug_logok/` in the repo root.** The user drops the log from each tested machine there (standing arrangement, 2026-07-28) — so when they say "here's the log", look in that folder first rather than asking for a paste. **Read it with Grep, not Read**: these files run ~1 MB / 7000 lines, a full read burns the context that the analysis itself needs, and a log on disk can be re-queried any number of times while a paste cannot. Grep by `[TAG]`, by thread name, or by timestamp window; `sed -n 'A,Bp'` for a specific stretch. The folder is not a build input — nothing in the app reads it.

Reading one:

- Pair a `[CMD]` line with its result by the **`[threadName]`** — parallel workers interleave, and a command's output can otherwise look like it belongs to a different call.
- `[CALL] Class.method(...)` / `-> return (elapsed)` brackets every API method; a `[CALL]` with no matching `->` is where execution stopped.
- Grep `STRESSTOOLS-DEBUG` for stress-test reports, `[EMIT:` for what the user actually saw on screen, `[UI-AKCIO]`/`[CLI-INPUT]` for what they clicked or typed.
- **A log that ends mid-line followed by a run of blank space is not a truncated paste** — it means the machine went down hard (BSOD/power loss) with the file's tail still in the page cache. Work that happened after the last readable line is invisible; reconstruct it from state instead (e.g. the third-party package count in the *next* session's startup dump). This is how the broken-chain bug was found.
- The log's Hungarian text may render as `Ã¡`-style mojibake in the paste, and a few tools (`reg.exe`, `pnputil`) emit genuinely mis-encoded bytes; both are display-only, never a bug in itself.

## Code layout (refactored 2026-07 from a single 8000-line driver_tool.py)

- **`driver_tool.py`** — thin entry point ONLY: the `BUILD_NUMBER` literal + the `__main__` block (single-instance mutex, UAC self-elevation via `_relaunch_elevated()`, logging setup, GUI-vs-CLI dispatch, WebView2 install offer + watchdog). **The `BUILD_NUMBER = <int>` line must stay in this file, at column 0, forever**: every already-deployed exe's auto-updater downloads *this file* from GitHub and regexes `^BUILD_NUMBER\s*=\s*(\d+)` out of it (and `bump_build.py` edits it here) — moving it to another file would permanently freeze all fielded installs on their current build. At startup the entry point copies it into `app.common.BUILD_NUMBER` (a module attribute defaulting to 0); **all other code reads `common.BUILD_NUMBER`**, never imports it from `driver_tool` (that would re-execute the module and duplicate state).
- **`app/`** — everything else, one file per feature (roughly one per sidebar menu item):
  - `app/common.py` — shared plumbing: WebView2 runtime check, `is_admin`, `resource_path` (frozen `sys._MEIPASS` vs `_PROJECT_ROOT`), `_ps_quote`, `_app_data_dir`, `_app_exe_path()` (see below), the command-result helpers used by both `_run`s (`CommandResult`, `CMD_TIMEOUT_RETURNCODE`, `STATUS_DLL_INIT_FAILED`/`spawn_failed` — see Logging), the `_webview_ready`/`_webview_error` events (single instances shared by GUI code and the entry-point watchdog — do not recreate them elsewhere), the `BUILD_NUMBER` holder, and the call-logging layer (`install_call_logging`, see Logging below).
  - `app/win32.py` — ctypes structs/constants (SendInput, console screen buffer, `ShellExecuteExW`, `GlobalMemoryStatusEx`, recycle bin, `get_work_area` via `SPI_GETWORKAREA` — the FurMark frame compensation uses it to tell a window frame from a clipped window; the **DisplayConfig (CCD)** structs + info-type constants used by the Kijelző view's HDR handling — their `size` fields are checked against the Windows definitions, so no field may be added or removed).
  - `app/wu_core.py` — the WU scan/install **shared core** (see its own bullet below).
  - `app/stress_defs.py` — stress-test constants: `STRESS_TOOLS`, `STRESS_TOOLS_BULK`, `STRESS_TOOL_ARGS`/`STRESS_FURMARK_LABEL` (see below), `STRESS_KILL_IMAGES`, `STRESS_CLICK_SEQUENCES`, `LINPACK_PROMPT_SCRIPT`, `LINPACK_RAM_OPTIONS`, `STRESS_POWER_SETTINGS`/`STRESS_POWER_REG_KEY`. **`STRESS_TOOL_ARGS` applies to the BULK launch only** (`start_stress_tests`) — the per-tool cards deliberately launch with no arguments at all, so the tech configures the program by hand (standing decision). Today it holds one entry: FurMark starts at **3840×2160 / 8× MSAA / `/xtreme_burning`, `/run_mode=2` (burn-in), with NO `/max_time`** so it runs until the tech stops it (explicit user decision, 2026-07-31 — "ott mehet végtelenig amíg le nem állítom"). **The 4K here is deliberately NOT the benchmark's 1024×768, and the two must not be "unified"**: windowed FurMark renders at most the screen size (see the measurement in the `benchmark_defs.py` bullet), which is fatal for a *measurement* — it would rank monitors — but exactly right for a *burn*, where it simply means "render the biggest image this machine can". Only the MSAA value is imported from `benchmark_defs.py`; the size lives here. It deliberately omits `/log_score`: a stress run is not a measurement and must not append to the score file the Benchmark view parses. Two knock-on rules: `_launch_stress_exe` takes `args=` and passes them on **both** the `Popen` and the elevated `ShellExecuteExW` path (`lpParameters` — otherwise an elevated FurMark would silently start with its own defaults), and `STRESS_CLICK_SEQUENCES['furmark']` lost its `'GPU stress test'` step (with `/nogui` there is no settings window to click) while keeping the `GO` CAUTION-dialog step as **optional, 20s** — the benchmark's own `/nogui` runs are the evidence that the dialog does not appear, but if some version shows it, the stress test must not stall. **`/run_mode=2` + "no `/max_time` means unlimited" is the one part not yet verified on real hardware** — the Geeks3D docs give `/max_time` a 60000 ms default but describe burn-in as running "until the user presses the ESC key"; if a field run ever stops itself after ~a minute, the fix is an explicit unlimited switch (the program's own `startup_options.xml` expresses it as `time_based_benchmark="0"` + `max_time="0"`).
  - `app/benchmark_defs.py` — benchmark constants: `BENCH_TOOLS` (Cinebench R20 + Unigine Heaven + FurMark exe-lookup patterns, searched in the shared `stresstools.zip`), the automated-run constants (`CINEBENCH_CLI_ARGS` — the CLI multi-core flags whose stdout carries the "CB <score>" line; `FURMARK_CLI_ARGS`/`FURMARK_BENCH_TIME_MS` — `/nogui /benchmark /max_time=10000 /log_score`; `CINEBENCH_TIMEOUT_S`, `FURMARK_EXIT_GRACE_S`), the pre-benchmark app-closing constants (`CLOSE_APPS_PROTECTED`, `CLOSE_APPS_WAIT_S`) and `BENCHMARK_API_URL_DEFAULT` (the cloud leaderboard endpoint default). **The FurMark measurement runs at 1024×768 + 8× MSAA + `/xtreme_burning`, windowed, 10s — the load comes from the sampling and the burn-in mode, NOT from the resolution** (explicit user decision, 2026-07-31; `FURMARK_BENCH_WIDTH`/`_HEIGHT`/`FURMARK_MSAA`). Why the resolution is deliberately small: **windowed FurMark cannot render bigger than the screen**, so any nominal above the smallest shop monitor would make the leaderboard rank *monitors* — see the measurement two paragraphs down. Why the load is still enough: 8× MSAA takes the per-frame sample count from 786k to 6.3M, and Xtreme burn-in roughly halves the frame rate on top of that (measured on the dev box's HD 530: 28 → 14 frames in the same 10 s window), so the total is ~10× the old `1024×768`/`0× MSAA` — a modern card lands in the tens of FPS, where the driver/CPU frame-submission path cannot be the limit. The Xtreme mode also matches the shop's manual practice (the FurMark install on the dev box carries `xtreme_burn_in="1"`), and it is a power virus by design: on a weak PSU or a dying card the machine can drop out mid-measurement and produce no result — an accepted trade. (The GUI's neighbouring post-FX switch has **no** CLI flag in FurMark 1.x — only `startup_options.xml` — so it is deliberately not forced into the run; writing that file would also leak into the benchmark's own runs from the same folder.) **The previous generation of this rule — "the settings deliberately mirror the shop's old hand-written FurMark script" (2026-07-29: `1024×768`, `/msaa=0`, `/enable_dyn_bkg=1 /bkg_img_id=2`, on the grounds that the technicians know those FPS ranges by heart) — is fully reversed and must not be reinstated**: the user's instruction was to forget that script entirely. The animated-background flags went with it, and measurement settled the question they were based on: the installed FurMark's `startup_options.xml` has `dynamic_bkg_image="1"`, i.e. the background is animated by default and `/enable_dyn_bkg=1` never did anything — while `/bkg_img_id=2` *did* silently swap the default image 0 for image 2 (this file used to claim 2 *was* the default; it is not). So what is left in the command line is operational only, plus the two load switches: `/nogui /benchmark /max_time /width /height /msaa /xtreme_burning /log_score /disable_catalyst_warning /nomenubar`. Two consequences: leaderboard rows uploaded **before** this change are not comparable (no settings column in the sheet — delete them by hand), and an old/low-VRAM card's driver may silently drop the sample count — hence `parse_furmark_scores` now also parses **`[MSAA=…]`** and a mismatch against the requested value logs a WARNING, exactly like the resolution check. Windowed, **never fullscreen**: a panel that cannot do the requested mode would produce **no result at all**, while a clipped window still produces one.

    **WINDOWED FURMARK NEVER RENDERS BIGGER THAN THE SCREEN — measured, do not re-litigate** (2026-07-31). This cost most of a session, twice, because **FurMark's own UI says otherwise**: its header (`Burn-in test, 3840x2160 (8X MSAA)`) and the `width`/`height` fields of `furmark-gpu-monitoring.xml` echo the *requested setting*, not the rendered image. The only honest source is the `/log_score` score file's `[Resolution=…]`. The decisive run, with the packaged FurMark **1.39.3.0**, on a 1080p monitor, identical settings (`/nogui /benchmark /max_time=10000 /msaa=8`, no Xtreme):

    | requested | `[Resolution=…]` | frames / 10 s |
    |---|---|---|
    | 3840×2160 | `1924x1061` | 13 |
    | 1280×720 | `1264x681` | **28** |
    | 3840×2160 (repeat) | `1924x1061` | 14 |

    Had it really rendered 4K, the 720p request would have produced the *same* frame count; it produced double, and the pixel ratio (2.04 Mpx vs 0.86 Mpx = 2.37×) accounts for it. So the render is the window's **client area**, capped by the display. That is why the nominal size must fit every shop screen: above it, a 4K-monitor machine would render 4× the pixels of a 1080p one under the very same command line — a far worse distortion than anything else in this file. Same lesson as the colour-profile case, and as the 1.19-vs-1.39 flag differences below: what a tool *displays* is not a measurement.

    The other constants here are `FURMARK_BENCH_RUNS` (**three** measured runs since 2026-07-31, best wins: run 1 is the cold run — FurMark loading itself and compiling shaders — plus two real measurements) and `BENCH_PRE_KILL_IMAGES` — both explained in the `app/gui/benchmark.py` bullets. `FURMARK_SETTINGS_LABEL`/`CINEBENCH_SETTINGS_LABEL` exist so the UI text and the real command line cannot drift apart: the view renders whatever `get_benchmark_settings()` returns (including the literal command line as a tooltip), and nothing about the settings is hardcoded in `ui.html`.
  - `app/tempclean_core.py`, `app/blockscript_core.py` — dual-API (GUI+CLI) shared logic for temp-cleanup and the block.bat download. (`app/nicpack_core.py` existed here until 2026-07-28 — the NIC rescue pack was removed on explicit user decision, see its bullet below.)
  - `app/colorprofile_core.py` — colour-management reset to the Windows default. **As of 2026-07-31 the AutoFix no longer calls it at all** (explicit user decision): it is invoked only from the GUI *Kijelző & Színkezelés* view, on an explicit click. The chain used to run it in leg B / CLI FÁZIS 3/b; that was removed because the same step is a dramatic improvement on one panel and ruins another — field-proven in both directions on the same build (a wide-gamut QD-OLED gained its native gamut when the association vanished; a TN Dell was left with blown-out white). A picture change nobody asked for and nobody can trace is not a driver fix. Both call sites carry a comment saying not to put it back. Three steps: delete the per-monitor ICC **profile associations** (`HKCU`+`HKLM` `…\ICM\ProfileAssociations\Display`), delete the **profile files those associations named**, and set `CalibrationManagementEnabled` to **1**. The reboot that follows reloads the gamma ramp, so the tech sees the result immediately. Deliberately leaves the **Printer** association branch alone (a customer's calibrated printer is unrecoverable damage, and the fix is about the display). Four rules here are field-proven and must not be undone:
    - **Never empty the whole `spool\drivers\color` folder** — only the files the display associations actually named. Measured live, that folder holds `sRGB Color Space Profile.icm` (**Windows' own default profile** — delete it and the machine has no colour reference at all), `RSWOP.icm`, the `.camp`/`.cdmp`/`.gmmp` WCS model files, and **printer** profiles (Canon `CNBJPRN3.ICM`/`CNFRD1.ICC`, `Epson IJ Printer 07.icc`). Wiping it is not "factory state", it is a broken machine plus the printer damage the printer-protection rule exists to prevent. `PROTECTED_COLOR_FILES` + `PROTECTED_COLOR_EXTS` are the belt-and-braces guard: a monitor association that points at Windows' own sRGB (a real case in the offline test) must not take it down. Every deleted file is logged by name at WARNING; every protected one is logged as `KEEP:` with the reason.
    - **`CalibrationManagementEnabled` must end at `1`, never `0`** (2026-07-28, explicit user decision). The reset used to set it to `0`. That value is the "Use Windows display calibration" switch, and with it off **no ICC profile's gamma curve (VCGT) is ever loaded on that machine again** — so the reset did not just remove a bad calibration, it removed the user's ability to apply a good one, permanently and invisibly (*"így akkor sose tudok betölteni semmilyen icc profilt"*). Note what `1` does and does not do: it makes the machine **able** to load a profile; it cannot restore a deleted one.
    - **A CAUTIONARY NOTE ON THE FIELD CASE THAT TRIGGERED ALL OF THIS — do not repeat my mistake.** The report was a blown-out white / no near-white grey separation on a TN panel after a chain (`MONITOR\RGT1352`, generic `monitor.inf`, **zero** Catalog rows when queried 3×, so no factory monitor profile exists on that machine either). I attributed it to the colour reset because the log said `ASSOC:HKCU:|4`. **That attribution was wrong and was retracted**: the `4` counted registry *keys*, and the very next measurement (dev box: 8 keys, **0** values) showed such keys are normally empty — so the reset may well have deleted nothing at all on that machine. The log does **not** contain evidence of what caused the blown white, because the old code never logged the profile values. Everything in this bullet list is still right as *design* (don't disable the loader, log what you delete, count values not keys), but the causal claim was not; the same run also replaced the display driver (AMD packages deleted → NVIDIA `30.0.14.7381` installed), which is at least as plausible a cause. The lesson for the next session is the one this whole file is built on: **a count is not evidence — log the thing itself.** The next such report is answerable only because `PROF:` lines now name the profiles. **Partial re-retraction (2026-07-31, from git):** the retraction above went too far. It correctly killed the *association-count* inference, but Build 235's script set `CalibrationManagementEnabled = 0` **unconditionally** — `git show 306eb49:app/colorprofile_core.py` — so on that TN Dell the gamma loader *was* switched off; that half is certain, not inferred. It is also the half that matches the reported symptom (no VCGT ⇒ no correction ⇒ blown white on a cheap panel), and unlike a deleted association it **never heals on its own**: any machine fixed with Build 235–237 still carries the 0 until something writes 1. Build 238 both stopped writing 0 and started writing 1, so a re-run of a current build repairs it — and the Kijelző view now reports and repairs it explicitly. Lesson unchanged, and now sharper: separate what the code *provably did* from what a log *suggested* it did, and retract only the latter.
    - **Every association is logged by name BEFORE deletion** (at WARNING — it is a destructive step). Without it the field question *"where did my calibration go?"* is unanswerable: the old code deleted the branch and logged only a count. Values are read as both `REG_SZ` and `REG_MULTI_SZ` (the layout is Windows-version dependent) and every `.icm`/`.icc` token in them becomes a deletion candidate.
    - **Count the registry VALUES, not the subkeys.** The branch is mostly empty container keys (`…\Display\{class-GUID}\0000`, `\0002`, …) and the actual profile is a *value* inside them.     - **The FurMark score file has NO "FPS" and NO "points" text on modern versions — parse `[FRAMES=…]`/`[TIME_MS=…]` and compute** (field-proven 2026-07-29, FurMark 1.39.3.0). The first release of the automated run only understood the old `3162 points (FPS: 52)` shapes, so a perfectly good run — process started, ran 14s, wrote its file — was reported as *"a FurMark nem írt ki FPS-eredményt"*, and the user's read of it was **"the FurMark didn't even start"**. The real line is `AMD Radeon RX 6500 XT - [FRAMES=618] - [TIME_MS=10000] - [Resolution=1898x1024] - [MSAA=0X] - [Mode=Windowed] - … - FurMark 1.39.3.0 - [Date=…]`, i.e. FPS = frames ÷ (ms/1000) = 61.8. All older shapes are still parsed as fallbacks, and the last entry always wins (the file is an append log). Two extras the same line made possible: the rendered `[Resolution=…]` is compared against the requested size and a mismatch logs a WARNING (see `benchmark_defs.py`), and **FurMark returns the frame count as its exit code** (`returncode=618` next to `[FRAMES=618]`), which is logged as a cross-check that the parsed result belongs to *this* run. Lesson for the next tool integration: never assume an output format — capture one real sample first, and keep the parser's failure log printing the file's tail (that WARNING is the only reason this was a 5-minute diagnosis).
    - **The FurMark measurement runs THREE times and the higher FPS wins — a single run is worthless on exactly the machine the shop measures** (field-proven 2026-07-30 with two runs, raised to three on 2026-07-31 alongside the 8× MSAA + Xtreme switch, both explicit user decisions; `FURMARK_BENCH_RUNS`). Run 1 is the **cold run** (FurMark loading itself, compiling shaders, allocating the larger MSAA buffers) and runs 2–3 are the real measurement, so a background kick during one of them can no longer decide the result. Everything below was measured with two runs and still applies unchanged. The report was "the results are all over the place": 133.1 FPS then 181.2 FPS on the same box (RTX 3060), same command line, same rendered resolution. FurMark itself is not the problem — three back-to-back verification runs on the warmed-up machine gave **185.5 / 184.2 / 183.5 FPS, a 1.1% spread**. What made the 133.1 was its *position in the session*: it came 100 s after a fresh **621 MB `stresstools.zip` download + extract**, i.e. the FurMark binary ran for the first time ever from that tree — cold page cache, Defender scanning the just-written exes, empty NVIDIA shader cache. Arithmetically it is as if the first **~2.6 s** of the 10 s window rendered nothing (1331 frames = 181 fps × 7.35 s). The corroborating datapoint is in the same log: that round's **Cinebench was also 3.3% low** (4036.1 vs 4172.86), so there really was background load. **This is the shop's normal case, not an edge case** — a new machine downloads the pack and benchmarks immediately, so the first measurement was systematically ~25–30% low and *that* is the number that went to the leaderboard. Two full-length runs (best wins) fix it: the first doubles as warm-up, and a random Windows Update/Defender kick during either run can no longer decide the result. Both runs' FPS **and their spread** go into the log (`[BENCHMARK] FurMark döntés: …`) — a large spread is itself information for the shop. Cost ~+13 s. Do not "optimize" this back to one run, and do not replace it with a shorter throwaway warm-up: the second mechanism (transient background load *during* the measured run) needs two real runs. **A machine's FIRST-EVER measurement gets one extra run** (`FURMARK_BENCH_MAX_EXTRA_RUNS`): until the window frame is known, run 1 still asks for the nominal size — it is what *teaches* the frame — so it renders smaller and cannot compete. The run count is therefore driven by the number of results **at the nominal resolution**, not by runs attempted; the extra run is skipped once compensation has been abandoned and is hard-capped so a machine that never produces a usable result cannot loop. **The "enough comparable results" threshold is `FURMARK_MIN_COMPARABLE_RUNS` = 2, deliberately NOT `FURMARK_BENCH_RUNS`** (2026-07-31, caught by the offline test when the run count went to three): requiring three *nominal* results would make every first-ever measurement do a fourth run, while run 1 is the cold run by design and is not supposed to compete.
    - **`/width` and `/height` set the WINDOW size, not the render size — compensate for the frame or the leaderboard compares different pixel counts** (field-proven 2026-07-30, re-confirmed 2026-07-31). FurMark renders into the *client* area, and the frame is **machine-dependent**: measured **22×56 px** on a 125%-scaled box and **16×39 px** on a 100% one. So the same command line renders `1002x712` on one machine and `1008x729` on another (~3% pixels ⇒ free FPS for the higher-DPI machine; on the 125% box the compensated run measured 174.6 FPS vs 184 uncompensated, i.e. the older rows were ~5% optimistic). Verified fix: requesting `1046×824` renders exactly `1024×768`. The first run's `requested − rendered` difference is therefore learned, logged, and persisted per machine in `<app_data>\furmark_frame_delta.json`, and every later run asks for `nominal + delta`. **This was briefly deleted on 2026-07-31 (during the short-lived 4K experiment) and then restored on explicit user request — "mindig minden gépen a renderelt kép legyen 1024x768".** Consequences and guards, all load-bearing:
      - **Only results rendered at the nominal size compete for "best"** — otherwise the frame-shrunk run (fewer pixels, higher FPS) would win every time, which is the bug inverted. If *no* run hit nominal, the best of what exists is used and the "not the requested resolution" WARNING fires: a skewed number still beats no number.
      - **Never learn the delta from a clipped run.** On a small screen the nominal window itself can get cut, which looks like a huge "frame"; learning that would make the next run ask for more, clip harder, and run away. Two guards: the magnitude limit `FURMARK_FRAME_DELTA_MAX_X/_Y` = **64/120** px (sized from the real 22×56 and 16×39 measurements, so it covers ~250% scaling while rejecting a 168 px clip — the offline test caught this exact runaway with the original, looser 96/240 limits, **do not loosen them back**), and the work-area check in `plan_furmark_size` (`app/win32.py: get_work_area`). The work-area guard is meaningful precisely *because* the nominal is 1024×768 and fits every existing display — so "does not fit" can only mean clipping.
      - **If a compensated run still misses nominal, compensation is abandoned for the rest of the measurement** (logged at WARNING) rather than retried with a bigger window.
      - The decision logic is offline-testable end to end: stub `_run_furmark_once` and `_furmark_delta_load/_save`, monkeypatch `app.gui.benchmark.get_work_area`, and drive `_run_furmark_capture` — see the scratchpad-test pattern. The pure halves (`parse_resolution`, `furmark_frame_delta`, `plan_furmark_size`, `build_furmark_cmd`) live in `app/benchmark_core.py`. Worth re-running whenever the settings or the run count change: that harness is what caught the four-runs-on-a-new-machine regression when `FURMARK_BENCH_RUNS` went to three.
    - **Already-running stress/benchmark programs are killed before measuring** (field-proven 2026-07-30, explicit user decision; `BENCH_PRE_KILL_IMAGES`, `build_find_bench_tools_ps`/`parse_find_bench_tools_output`). In the field the tech launched FurMark by hand from the per-tool card, then started the benchmark a minute later: the Cinebench exited after 11 s with `returncode=0` in the middle of `Rendering…` and **no `CB` score line**, and the run was reported as "the Cinebench produced no score". The graceful `_close_running_apps_sync` does not cover this — it only touches processes with a visible titled main window, and that FurMark was not in its `TRY:` list at all. So the pre-kill is a separate, name-based sweep, and unlike the user-app closing it uses `taskkill` deliberately: these are not the customer's work, there is nothing to lose, and their presence invalidates the measurement. It runs **regardless of the "close running programs" answer**. Every process is logged by name and pid at WARNING *before* it is killed, and the sweep also names the monitors (HWiNFO/GPU-Z/CPU-Z) — their sensor polling perturbs the score too. The listing script sets `$ErrorActionPreference = 'SilentlyContinue'` **and ends with `exit 0`**: non-elevated `Get-Process` raises non-terminating errors on processes it cannot read, so the script returns 1 while its output is perfectly fine (measured), and a caller that trusts the exit code throws away a correct list — the parser keys off the `DONE` line instead.
    - **The leaderboard's dedup key is `machine_row_id(MachineGuid, name)` — the machine AND the typed name, never the bare GUID** (field-proven 2026-07-30, and it cost a real measurement). The cloud side (a Google Apps Script, outside this repo) upserts on the `machine_id` field, and we used to send `get_machine_id()` alone — so two runs on one machine **under two different names silently overwrote each other**, and the first score was gone: the sheet keeps one row per key, and the user's intent (a before/after pair, or two configs) was unrepresentable. The composite key gives both halves: *same* name → updates its own row (a botched run stays fixable), *different* name → a new row. It also closes a second hole the shop is exposed to: **on a cloned Windows image several physical machines carry the same `MachineGuid`**, so the bare GUID would have had different machines overwriting each other's results too. Key shape: `<guid>|<readable-slug>-<6 hex of the normalized name>` — the slug because a human reads that sheet, the hex because accent-folding + truncation can map two *different* names onto one slug (`Gép 1` vs `gep-1`), which would be the same silent overwrite again; the name is normalized (casefold + collapsed whitespace) first, so a rerun typed with different capitalization or a trailing space still updates rather than duplicating. The bare GUID still travels as a separate `hw_id` field — the sheet has no such column today, so the script drops it exactly like the `furmark` field (proof it's harmless: the live GET returns `fm=` empty with the value in `heaven`). Two consequences worth knowing: rows uploaded **before** this change are keyed on a bare GUID and can never be updated again — `_bench_existing_row` logs a WARNING naming any such leftover row so it can be deleted in the sheet by hand; and the upload now logs (and the toast now states) whether it **created** a row or **overwrote** an existing one — a silent overwrite is exactly what made this bug unnoticeable. Never "simplify" the key back to the GUID, and don't move the dedup to the Apps Script: the whole point of the composite key is that it needs **zero** backend change. Offline-tested (both the pure key function over accent/case/emoji/collision cases and the whole `upload_benchmark_result` path with `core_fetch_leaderboard`/`core_upload_result` stubbed — see the scratchpad-test pattern).
    - **A failed leaderboard *re-read* after a successful upload must not be reported as an upload failure.** `upload_benchmark_result`'s worker refreshed the leaderboard inside the same `try` as the POST, so an exception from that refresh emitted `❌ Feltöltési hiba` + `benchmark_upload_result {ok: False}` **after** the success toast — the tech would re-upload an already-uploaded result. The refresh now has its own `try` and only logs a WARNING (`core_fetch_leaderboard` swallows its own errors into an `error` key, so this only fires on something genuinely unexpected — which is exactly when a false failure report does the most damage).
    - **The pre-benchmark "close everything" step is graceful-only, and its filter needs the window TITLE, not just the handle.** The run dialog offers to close running programs first (background Chrome/Steam/updaters steal CPU+GPU and make scores low and jittery); on yes, `_close_running_apps_sync` runs `build_close_apps_ps`. Rules that must not be softened: (a) it calls **`CloseMainWindow()` (WM_CLOSE), never `Stop-Process`/taskkill** — identical to clicking the window's X, so an app with unsaved work prompts and *stays open*; those are reported, never forced (a benchmark must not cost the customer their unsaved document); (b) the target filter is `MainWindowHandle -ne 0 **-and MainWindowTitle**` — measured on a live dry run, handle-only also selected **`svchost.exe`** (it has a title-less window), and a WM_CLOSE to a service host can stop services; a real user app always has a title. `CLOSE_APPS_PROTECTED` (shell, our own exe + WebView2, system hosts incl. svchost, and the tech's diagnostic windows: taskmgr/regedit/eventvwr…) is the second line of defence; (c) every attempted close is logged **by name with its window title** at WARNING before it happens, and the survivors are logged too — this is a destructive-ish action on someone else's machine. Verify changes here with the listing-only dry run (strip the `CloseMainWindow` call and the sleep) rather than by closing real windows.
  - `app/cli/` — the CLI backend, same pattern: `api.py` assembles **`CliApi`** from `base.py`, `drivers.py`, `dupdrivers.py` (DriverStore duplicate cleanup, interactive), `backup.py`, `bcd.py`, `wu.py`, `ghost.py`, `tempclean.py`, `blockscript.py`, `autofix.py`, `bitlocker.py` (status + disable), `report.py` (HTML report, S.M.A.R.T. only if stresstools already extracted), `updater.py` (check + self-update); `menu.py` holds `run_cli_mode()` (the text menus).
  - Mixin method names are globally unique within each API class; everything shares one `self`. When adding a method, put it in the feature's file — if no file fits, make a new mixin file and add it to the `class DriverToolApi(...)` / `class CliApi(...)` base list in the matching `api.py`.

### Code organization rules (IMPORTANT — this structure must not erode back into a monolith)

- **A new feature = a new file**, following the existing pattern: new mixin in `app/gui/<feature>.py` (and `app/cli/<feature>.py` if it has a CLI equivalent), registered in the base-class list of the matching `api.py`. Never bolt a new feature's methods onto an existing unrelated mixin, and never grow `base.py` into a dumping ground — `base.py` is only for genuinely cross-feature plumbing (`emit`, `_run`, `_safe_thread`, dialogs, target-OS state).
- **Logic shared by GUI and CLI goes in a module-level `app/<feature>_core.py`**, called by both thin mixins — never duplicated into both classes; duplication is what caused the Build-192-era "one path works, the other silently broken" bugs. Since the 2026-07 dedup pass this is fully enforced: every feature with both a GUI and CLI face has its `_core` module (see the Code layout list), the mixins only do presentation (emit vs. print) and threading/cancel wiring. Long core sequences take a `log(msg)` callback (GUI passes a `task_progress`-emitting lambda, CLI passes `print`) and an optional `check_cancel()` callback (CLI passes None).
- **Constants/ctypes**: feature-local constants live at the top of the feature's own file (see `storeprint.py`); constants shared across files go to `app/stress_defs.py`-style def modules or `app/common.py`; ctypes structs go to `app/win32.py`.
- **The product is Hungarian**: every user-visible string (UI text, toasts, `emit('task_progress')` log lines, CLI menus, HTML report labels) and every code comment is written in Hungarian. Only logger messages mix — their `[TAG]` prefixes and identifiers stay ASCII/English while the sentence is Hungarian, because the debug log is read by the shop, not by Microsoft. Don't introduce English UI strings; a mixed-language screen is a field-support problem, not a style preference.
- Keep files roughly feature-sized. The biggest are `app/gui/hwscan.py`, `app/gui/autofix.py`, `app/wu_core.py` and `app/gui/stress_automation.py` (all four ~900–1200 lines and still growing); if one grows past that because it really contains two concerns, split it the way `stress.py`/`stress_automation.py` was split. Don't chase an exact line budget — the question is whether the file is still *one* feature.
- **When you add/rename/split a file, update the "Code layout" list above in the same change** — this map is what lets a fresh session navigate without grepping the whole tree.
- **`ui.html`** — the entire frontend: plain HTML/CSS/JS (no framework, no build step), dark "glassmorphism" theme **with a unified hero-card design system (2026-07 facelift)**: every view opens with a `.view-hero` header card — big title + description + `.hero-chip` feature chips on the left, the main action button(s) in `.vh-actions` on the right, and a faint emoji watermark taken from the `data-emoji` attribute. Color variants: default purple, `.vh-red` (dangerous/blocking: BitLocker, block.bat), `.vh-blue` (Windows/system: WU, HW scan), `.vh-teal` (backup/report). Two bespoke heroes predate the generic class and stay as-is: `.stress-hero` (orange, Stress Teszt) and `.autofix-hero` (purple, the AutoFix quick-launch card in the Drivers view; big button style `.btn-autofix-hero`). The Stress view additionally has the `.tool-grid`/`.tool-card` service-program card grid. **New views/features must follow this hero pattern** (title/desc/chips + action right), and existing element `id`-s must never change during styling (JS references them). Sidebar label for the stress view: "Stress Teszt & Szervíz Programok". Drivers-view order (explicit user decision): welcome hero (🧙‍♂️, generic `.view-hero` with the `.welcome-features` grid at `flex-basis:100%`) on top → third-party driver table panel → AutoFix quick-launch `.autofix-hero` at the bottom. Talks to Python only through `window.pywebview.api.<method>()` (helper: `api()`) and receives async push events via `window.handlePyEvent(payload)`, which Python calls from `DriverToolApi.emit(event, data)` (`app/gui/base.py`) via `window.evaluate_js(...)`. JS console errors/uncaught exceptions are forwarded back to the Python logger through `api().js_log(...)`. The refactor did not change the JS↔Python contract: every `api().<name>()` call still resolves to a `DriverToolApi` method (verified programmatically after the split).
- **`__file__` is a trap after the split**: any "path of the running program" logic must use `app.common._app_exe_path()` (frozen → `sys.executable`, source → repo-root `driver_tool.py`), NOT `os.path.abspath(__file__)` — inside `app/` that now points at the submodule and would break e.g. the AutoFix scheduled-task exe path when running from source. All five original occurrences were converted; don't reintroduce the raw pattern.

## Logging (deliberately maximal — the debug log is the primary field-diagnosis tool)

### Rule 0: every new code path must log — no exceptions

**Explicit user decision (2026-07-26), and it outranks brevity, tidiness and taste.** This project has no test suite, no telemetry and no debugger on the machines that matter. The *only* channel through which a shop run teaches us anything is `DriverVarázsló_debug.log`. A test run whose log does not say what the program decided is a test run that produced **nothing** — the machine has already been handed back to the customer, the state is gone, and the question ("why did it skip that driver?", "did it even look at that device?") becomes permanently unanswerable. Every rule in this file that cites field evidence exists because a log line happened to be there; every bug that took two releases to find was one that wasn't.

So, when you write or change code here, the log is part of the deliverable, not an afterthought:

- **Every decision states its outcome *and* its input.** Not `[CATALOG] Kihagyva` but which package, for which device, against which installed version. A verdict without its evidence cannot be re-checked from a paste.
- **Every filter names what it dropped**, with a per-reason count in one summary line at INFO and the dropped items at DEBUG (worked examples: `deep_catalog_candidates`, `_filter_wu_scan_devices`, the printer/boot protections). A list that silently shrinks is the single hardest thing to diagnose from a log.
- **Every destructive action names its target before doing it** — deletes, force-deletes, registry writes, scheduled-task changes, power/policy changes. `pnputil` calls go through `_run` and log themselves; `shutil.rmtree`/`os.remove`/`Popen` do **not**, so they need an explicit line (see `force_delete_driver_files`).
- **Every "we chose not to do X" is as loggable as doing it.** Protected, skipped, deferred, already-installed, no-op — these are the states a field report actually asks about.
- **Failure paths log at WARNING/ERROR with context**, including the returncode and a truncated output snippet. `except: pass` is banned (see the no-silent-except rule below); a swallowed failure that changes behavior logs at WARNING.
- **Module-level functions are not covered by `install_call_logging`** (it only wraps API-class methods), so anything in an `app/*_core.py` module must log explicitly — this is the most common gap.
- **The one counter-rule: hot loops must NOT log per iteration.** The file is 5 MB × 2 rotating; a per-row helper called 25–100× per device will push the real history out and destroy exactly the evidence this rule exists to preserve. Add such helpers to `_CALL_LOG_EXCLUDE` and emit **one summary line per decision** instead. Maximal logging means maximal *information*, not maximal lines.

When in doubt, log it. The cost is a line in a rotating file; the cost of the alternative is a customer machine you cannot debug twice.

- Log file: `DriverVarázsló_debug.log` in `_app_data_dir()` (`<SystemDrive>\DriverVarazslo`, NOT next to the exe — it may run from a read-only USB/network share), `RotatingFileHandler` 5 MB × 2 backups. Don't swap back to plain `basicConfig(filename=...)` — the DEBUG-level log grows unbounded otherwise. Logging is configured in `driver_tool.py` **before** the `--cli` branch (it used to be after, so CLI runs logged nothing — that was fixed during the refactor on purpose; keep it that way). The handler is `_BomRotatingFileHandler` (in `driver_tool.py`): it writes a UTF-8 **BOM** at the start of every *new/empty* log file (initial creation and post-rollover) so plain Notepad reliably detects UTF-8 instead of guessing ANSI and rendering the Hungarian text as `Ã¡`-style mojibake (field-seen) — keep the BOM logic if the handler is ever touched. Note the log *content* can still contain per-tool garble for a few localized console tools (`reg.exe` emits OEM cp852, `pnputil` emits ANSI — Windows is inconsistent per tool): those lines are display-only, never parsed, and deliberately left alone rather than risking the ASCII-based parsing paths (`dism /English`, powercfg hex positions) with a global decode change.
- **Call-logging layer** (`app/common.py`: `install_call_logging`, applied to both API classes in their `api.py`): every method of `DriverToolApi` and `CliApi` — public and private, inherited included — is wrapped to log `[CALL] Class.method(args...)` on entry, `[CALL] ... -> return (elapsed)` on exit, and `[CALL] ... KIVÉTEL` with full traceback on exception (public methods at INFO, `_private` at DEBUG; arg/return reprs truncated to 200/300 chars). A small `_CALL_LOG_EXCLUDE` set skips methods that either have richer logging of their own (`emit`, `_run`, `js_log`) or run in per-keystroke/per-poll hot loops that would churn the rotating log (`_send_unicode_char`, `_read_console_screen`, ...). Static methods are skipped by design (no `self`). If you add a new hot-loop helper, add it to the exclude set; everything else gets logged automatically — no per-method logging boilerplate needed for entry/exit anymore.
- The log format includes **`[%(threadName)s]`**: parallel workers' lines interleave in the file, and without the thread name a `[CMD]` command could not be paired with its result (field-seen: a PowerShell command apparently "returning" another thread's DISM output). All background threads carry meaningful names (`task-<name>` from `_safe_thread`, plus `drivers-load`, `dup-list`, `hw-scan`, `catalog-N`, `wu-reader`, `stress-tool`/`stress-stop`, `bootfixer-dl`, `auto:<tool>`) — keep naming new threads.
- Existing layers kept: `_run` logs every subprocess command + returncode + up to 4000 chars of stdout/stderr (`[CMD]`/`[CMD_CLI]`); `emit` logs every UI push event (`[EMIT:...]`); JS errors arrive as `[JS_UI]`; stress automation diagnostics are `[STRESSTOOLS-DEBUG]` (grep that first for stress-test field reports).
- **Command timeouts + the "process won't even start" case** (both `_run`s, `app/common.py`): `_run` passes `timeout=` through to `subprocess.run` but **catches `TimeoutExpired` and returns `CommandResult(CMD_TIMEOUT_RETURNCODE, ...)` instead of raising** — a hung helper must not kill a whole AutoFix leg. Callers that care check `res.returncode == CMD_TIMEOUT_RETURNCODE`. Separately, `spawn_failed(res)` detects returncode `0xC0000142` (`STATUS_DLL_INIT_FAILED`): that is **not** "the command failed", it is "Windows could not initialize a new process" (session ending / collapsed device stack), and **every subsequent spawn will be an instant no-op**. Field-proven (Build 218): after a hung storage-driver delete, 17 further `pnputil` calls "succeeded" in 0.0s each and the leg reported `✅ Driverek eltávolítva` and rebooted, having deleted nothing. Any loop that spawns per item MUST abort on `spawn_failed` with a visible error rather than continue — a silent false success is the worst possible outcome here. `delete_driver_package` takes `timeout=` (`drivers_core.DELETE_DRIVER_TIMEOUT` = 180s) and both AutoFix delete loops honour both rules.
- **Expected non-zero exit codes**: both `_run`s take a keyword-only `ok_codes=(0,)` — codes listed there log at DEBUG as "OK - várt kód" instead of WARNING, so WARNING lines mean real anomalies. Used for: `reg delete` on a possibly-absent key (1), the idempotent final `Unregister-ScheduledTask` (1), `pnputil /delete-driver` + `wusa`/`dism /Add-Package` reboot-required (3010), `stop_stress_tests`' `taskkill` calls (128 = "no such process" — the user may have closed the tool already, or the PID is a finished Benchmark launch). Return value is unaffected — only the log level. When adding a call whose failure is a *normal* outcome, pass `ok_codes` instead of letting it cry wolf.
- **Every user action is logged**: the GUI logs every click and field change from `ui.html` (capture-phase `click`/`change` listeners → `js_log('DEBUG', '[UI-AKCIO] ...')`; text inputs only on change, never per-keystroke) so a field log replays what the user pressed and in what order. **A checkbox's `checked` in the capture-phase click handler is the value AFTER the toggle, not before** — HTML's "pre-click activation" flips checkedness before the click event is dispatched (it only reverts if someone cancels the event). The line used to be labelled `valtas_elotti` ("before change"), which made the 2026-07-27 log read as if a click on the default-on printer checkbox had done nothing (`checked=false` on both the click and the change line), when in fact that click is exactly what turned it off — `run_autofix(false)` confirmed it. Both lines report the same post-toggle value, so both are labelled as such; don't "restore" the before/after distinction, it does not exist. the CLI wraps `builtins.input` in `run_cli_mode()` (`_install_input_logging`, idempotent) so every menu choice/path/confirmation logs as `[CLI-INPUT] prompt -> value`.
- **Coverage rule: every subprocess must leave a trace, and every destructive or list-shrinking decision must name what it touched.** Audited 2026-07-24; the gaps found then are fixed and must not come back:
  - **Every `subprocess.Popen` site logs its command** before starting (`[CMD] Popen futtatása: ...`). The streaming callers (ghost script, WU installer, DISM export) don't go through `_run`, so without that line the command is invisible. The manual WU install (`_install_wu_api_sync`) was the one site missing it — it now also logs the requested `UpdateID`s/HWIDs, since "it installed nothing" is uninvestigable without them.
  - **Pure-Python destructive calls log too.** `drivers_core.force_delete_driver_files` runs `shutil.rmtree`/`os.remove` on DriverStore folders; the `takeown`/`icacls` around them were logged via `_run` but the actual deletion left no trace. It now brackets the whole operation at WARNING and names every folder/file, plus whether the path survived.
  - **Filters that silently drop rows must say what they dropped**: `filter_phantom_packages` logs the skipped packages (a "my driver vanished from the list" report was otherwise untraceable), and `parse_dism_driver_list` logs a WARNING when non-empty DISM output yields **zero** packages — that is the documented `/English`-missing failure, which previously surfaced only as a silent "0 driver".
  - **The device-set filters name what they dropped** (2026-07, same rule applied to the new code): `_filter_wu_scan_devices` logs the merged duplicate groups (`[PNP] N eszköz a szűrés után; azonos HWID-ű példányok összevonva: ...`), and `deep_catalog_candidates` logs one summary line with the per-reason drop counts (`[CATALOG] Mély szken köre: 16/99 eszköz (kizárva: osztály=11, nincs gyártói HWID=55, busz-INF=17)`) plus the dropped names at DEBUG. Both are module-level functions, so `install_call_logging` does **not** wrap them — without these explicit lines the field question "was this device even queried?" would be unanswerable. The AutoFix closing-round banner likewise reports the real device count including the deep ones (it used to print only the error-coded + generic counts, which understated a 16-device round as "1 eszköz").
  - **Per-device ghost deletions are logged by name** (`[GHOST] Törölve: ...`). The AutoFix deliberately keeps these off the UI, but the log used to show only "10 db törölve" — useless when someone reports a missing device.
- **Hot loops must be excluded — log flooding destroys the log's value.** The log is a 5 MB × 2 rotating file: a helper called once per catalog row (25–100 per device) writes two lines each and pushes the real history out. `_catalog_row_score`/`_catalog_row_is_microsoft` are in `_CALL_LOG_EXCLUDE` for exactly this (field-seen Build 228: one 2-device catalog round produced several hundred lines of pure noise). The replacement is **one summary line per decision** (`[CATALOG] Döntés: ... N sor / M HWID, legjobb pont=X, NYERTES: '...' | közeli: ...`) — that is what actually answers "why did it pick this package?".
- **No silent `except: pass`**: cleanup/cache/best-effort failures log at `logging.debug` with context; swallowed failures that *change behavior* (e.g. the AutoFix PnP JSON parse — an empty parse silently empties the device list) log at `logging.warning`. Pure value-parse fallbacks that return a semantic default (`dupdrivers_core.dup_version_key`, report `g()`/`e()`) may stay silent. Don't add new bare `except: pass` blocks.
- Both `_run` copies default `stdin` to `subprocess.DEVNULL` — do not remove: after the stress-test automation's `AttachConsole`/`FreeConsole` cycles the inherited stdin handle goes stale, and inherited-stdin + `capture_output` then fails *every* later command with `[WinError 6]` (field-proven: `taskkill` stopped working right after a stress run).

## Architecture / field-proven behavior rules

### Process model, dispatch & platform rules

- **GUI vs CLI dispatch** (`driver_tool.py` `__main__`): single-instance mutex → UAC self-elevate if not admin (both paths use the shared `_relaunch_elevated()`) → `--cli` arg or `check_webview2_runtime()` failing (min v109) routes to `run_cli_mode()` (with a WebView2 silent-install offer first in the GUI path); otherwise `pywebview` window with `DriverToolApi` as `js_api` + a 60s watchdog that falls back to CLI if `_webview_ready` never fires.
- **Process exit is always `cleanup_zombies()` + `os._exit(0)`** (`driver_tool.py`), never a plain `return`/`sys.exit()` from `__main__`: long-running helpers (`dism`, `pnputil`, PowerShell) and daemon threads can otherwise outlive the window and hold file locks / keep the single-instance mutex, and the WebView2 host thread does not always unwind. `cleanup_zombies()` taskkills our **own** process tree (`taskkill /F /T /PID <self>`). Consequence to respect: **`atexit` hooks and `finally` blocks above the exit point never run** — `os._exit` bypasses them — so cleanup that must happen (temp files, restored power settings, unregistered scheduled tasks) has to be done explicitly *before* the exit call, not registered for later. This is why `cleanup_zombies` is called manually at each exit site instead of via `atexit` (the README's claim of an `atexit` handler is wrong).
- **Unhandled exceptions are routed, not printed**: `sys.excepthook` and `threading.excepthook` log with full traceback and, if the message mentions WebView2/ICoreWebView2/.NET, set `_webview_error` so the watchdog can fall back to the CLI instead of leaving the user with a dead window.
- **GUI/CLI feature parity drifts easily**: when adding a feature to one API class, the other usually needs the equivalent (historic gaps: WU pause/resume, ghost-device deletion, `/ForceUnsigned` on offline restore — all fixed once). `CliApi.autofix()` is *intentionally* a simpler one-shot design with no reboot-chaining (documented in its printed output) — not a bug to "fix" into parity. Deliberately GUI-only (listed in the CLI's "GUI-only funkciók" menu item): Stress-Test (incl. the service-tool individual launches + Program Files install, `toolsinstall.py`), the Benchmark view (automated Cinebench R20 + FurMark run with score capture + cloud leaderboard, `app/gui/benchmark.py`), the Kijelző & Színkezelés view (`app/gui/display.py`), the manual WU scan + selective install (hwscan), the NVIDIA/AMD/Intel/OEM vendor-driver cards, store-printer report printing, and the BootFixer.cmd download button (the CLI keeps the built-in BCD repair instead). Everything else is available in both, and since the 2026-07 dedup pass the shared body always lives in an `app/<feature>_core.py` — extend the core, never duplicate into the classes.
- **Offline mode**: most driver operations check `self.target_os_path` — when set, operations target a foreign Windows volume using `dism /Image:...` instead of `/Online`. **The running system's drive root can never become the offline target**: `apply_target_os` (`app/gui/base.py`) detects when the picked folder equals `%SystemDrive%\` and stays in live mode (returns `False`, toast explains; the JS `changeTarget` then resets the target label) — `dism /Image:C:\` against the running Windows fails with error 87 ("points to a running Windows installation") and every list silently came back as "0 driver" (field log, Build 208). Always handle both branches when touching driver listing/deletion. DISM calls that parse English text output must pass `/English`, or non-English Windows/WinPE silently fails to parse. That text parsing lives in ONE place since the dedup pass — `app/drivers_core.py: parse_dism_driver_list` (it used to exist in 4 near-identical copies) — and keys off substrings like `"Published Name"`/`"Provider Name"`/`"Class Name"`; the driver version in real `dism /Get-Drivers` output is a standalone `Version :` line (**not** `"Date and Version"`, which never matched and silently left the Version column blank until field-diagnosed).
- **`_filter_wu_scan_devices` dedups by first HWID, but a duplicate must not vanish silently** (2026-07): identical devices (2 identical NICs, 7 identical host bridges — measured: 5 such groups on one live machine) collapse to one entry so the WU/Catalog lookup doesn't run N times. The dedup therefore **merges** rather than drops: `dup_count`/`dup_pnp_ids` are recorded, and if a later duplicate is error-coded while the kept one isn't, the error code is promoted onto the kept device. Without that, a dead *second* sound card / NIC never appeared in the "Problémás eszközök" list at all.
- **`_hwid_matches` requires ≥2 tokens on the narrower ID, and no longer does raw string prefixing** (2026-07): the old code accepted `w.startswith(d) or d.startswith(w)` *before* the bus/token logic, so `PCI\VEN_8086` matched every Intel PCI device, and `USB` matched `USBMMIDD` — the exact false positive the docstring promised was excluded. Matching now runs entirely on bus + token sets, with subset accepted **in both directions** (the WU ID can be more general — `ven+dev` vs `ven+dev+subsys+rev` — or more specific — the composite-USB `&MI_00` case). All documented field cases have ≥2 tokens (`ven+dev+rev` on the R9 200, `ven+cc` on amdafd, `vid+pid` on USB composites), so nothing that ever worked regresses.
- **`_filter_wu_scan_devices` device categorization is case-insensitive on `PNPClass`**, and each device dict carries the raw `pclass` alongside the human `cat` label. `Win32_PnPEntity.PNPClass` capitalization varies per device (audio reports `MEDIA` in caps), so the class comparisons lowercase both sides — a case-sensitive `== "Media"` dumped every audio device into "🔧 Egyéb" and, worse, would now misfire the generic-driver-replacement class gate that keys off `pclass`. Keep `pclass` on the dict and keep the comparisons lowercased. **The same rule applies to the `WU_SCAN_IGNORED_CLASSES` test a few lines above it** (fixed 2026-07-28, `_WU_SCAN_IGNORED_UPPER`): that one still compared the raw `pclass` against the canonical-case list, in the very same function that had already learned this lesson for the `cat` labels — so a machine reporting `VOLUME`/`COMPUTER` in caps would have let the volume object or the HAL through into the driver search. The list itself stays in readable canonical form; only the comparison is case-folded.
- **`_check_internet` (`app/gui/base.py`) must not use `socket.setdefaulttimeout`**: that sets the default for the *whole process* and never resets, so after the first check every later socket that omits an explicit timeout silently gets 3s — a single slow second would abort a large download (NVIDIA driver, stresstools.zip). Use a per-call `socket.create_connection((host, port), timeout=3)` instead (two hosts tried: `8.8.8.8:53`, then `www.microsoft.com:80`). Today every network caller passes an explicit timeout, so this never actually fired — don't reintroduce the global.
- **Every elapsed-time / deadline measurement uses `time.monotonic()`; `time.time()` is only for genuine timestamps** (2026-07-28, field-proven). A wall clock can jump: on a fresh bench machine (new CPU, test SSD, first network connection) Windows' first time sync moved the system clock **+4 hours 51 minutes** in the middle of a running AutoFix chain. It landed inside a `time.sleep(10)`, so the visible damage was only absurd logging (`_scan_and_install_wu_sync -> 12 (17742.34s)` for a step that took seconds) — the user's own report was the giveaway: *"nem volt 4 óra 31 perc kiesés egyáltalán, kb 5 perc alatt végigment az egész"*. Two minutes later it would have landed in `wu_core._iter_process_lines`, whose inactivity watchdog compares elapsed time against `inactivity_timeout` (30 min): the jump instantly reads as 4.9 hours of silence, so it would have **taskkilled a healthy, running WUA driver install** and raised `WuProcessAborted('hang')`. That is a silent-false-failure of exactly the class this file keeps collecting. An audit at the time found **57 `time.time()` uses and 0 `time.monotonic()`**; all duration/timeout/deadline sites were converted across 11 files (`wu_core`, `common`, `gui/base`, `gui/hwscan`, `gui/drivers`, `gui/stress`, `gui/stress_automation`, `gui/toolsinstall`, `cli/base`, `cli/autofix`, `driver_tool`). `time.time()` deliberately remains at 8 sites where an absolute timestamp is the point, not a duration: unique temp names (`backup_core`), file-mtime cache freshness (`gui/nvidia`, `gui/vendorgpu`), and cache-buster URLs + unique filenames (`update_core`). When adding any timing code, ask which of the two you need — "how long has this been running" is always monotonic.
- **WinPE awareness**: code checks `os.environ.get('SystemDrive') == 'X:'` to detect WinPE and redirects large temp downloads/extracts to `C:\DV_Temp` instead of the RAM-disk `X:` — this redirect must not depend on any other condition (e.g. whether an offline target OS is selected).
- **Packaging / auto-updater** (`app/gui/updater.py` + `app/common.py`): `resource_path()` resolves `ui.html` via `sys._MEIPASS` when frozen. `check_for_updates` fetches `driver_tool.py` from `raw.githubusercontent.com`, regexes `BUILD_NUMBER`, and if newer downloads and replaces `dist/DriverVarazslo.exe` — that exe is intentionally committed (`git add -f`) so the updater has something to fetch. raw.githubusercontent.com sits behind a Fastly CDN whose edge cache can serve a stale copy for minutes after a push — the `?t=<timestamp>` query only defeats client-side caching, so `check_for_updates` retries 3× with 3s pauses; testing the updater immediately after a push can still legitimately report "no update". Besides the automatic startup check there is a **hidden manual trigger**: clicking the sidebar "DRIVERVARÁZSLÓ" logo runs `checkForUpdatesManual()` (ui.html) — deliberately no visual hint and completely silent when up-to-date; only shows the standard update-confirm dialog when a newer build exists. Never let any edit lower the committed `BUILD_NUMBER` — updates are offered only on strict `new_build > BUILD_NUMBER` (a regression silently freezes updated users; happened once — see `bump_build.py`). All network downloads (`check_for_updates`, `perform_update`, `_download_stresstools`, `_download_block_script`, `bump_build.py`) use `ssl.create_default_context()` with verification **on** — never add `check_hostname = False`/`CERT_NONE`; these paths download admin-executed payloads. On a *brand-new* Windows install the root-cert store is sparse (only schannel clients trigger on-demand root fetching; Python's OpenSSL doesn't), so Python gets `CERTIFICATE_VERIFY_FAILED` for `github.com` (Sectigo/USERTrust root) while `raw.githubusercontent.com` (DigiCert) works. `_download_stresstools` and `_download_block_script` therefore fall back, on that specific error only, to PowerShell `Invoke-WebRequest` (schannel, verification still fully on; side effect: heals the machine's root store). This fallback is NOT a verification bypass and must not be turned into one.

### AutoFix — the 3-leg reboot chain

- **`autofix_stats.json` is the chain's only memory across legs** (each leg is a separate process, so nothing else survives a reboot). It lives in `_app_data_dir()`, is written by `_autofix_stats_set/add` and read by `_autofix_stats_get`, and is deleted at the end of the chain **and** in leg A. Six keys, currently the complete set — when adding one, add it here too, because "why did the chain do X on the second leg?" is answered from this file:
  | key | written by | meaning |
  |---|---|---|
  | `legs` | `_autofix_stats_add` | per-leg install counts; its length is `_autofix_leg_count()` vs `AUTOFIX_MAX_INSTALL_LEGS` |
  | `install_leg_starts` | install leg entry | counts *every* entry incl. crash resumes; gates the crash-safety task |
  | `pre_packages` | delete phase | pre-deletion package list for the "never came back" report |
  | `pending_deletes` | delete phase / sweep | packages a wedged PnP stack refused; swept at the start of the next leg |
  | `delete_rounds` | sweep | reboot-and-retry counter vs `AUTOFIX_MAX_DELETE_ROUNDS` |
  | `catalog_no_bind` | catalog closing round | packages that installed but the device didn't take — never re-downloaded on later legs |
  | `wu_failed_uids` | install leg, after `verify_failed_installs` | UpdateIDs whose install genuinely failed (post-verification). Persisted because the legs are separate processes: while this lived only in memory, **every** install leg re-attempted the same doomed package at ~2.5 min each |
  | `carry_pre_packages` | leg A | the *previous*, unfinished chain's `pre_packages`. A chain aborted mid-deletion has already removed packages that are no longer on the machine, so a fresh `pre_packages` cannot see them and the "never came back" report would silently omit exactly the most endangered ones |
- **AutoFix resume-after-reboot** (`app/gui/autofix.py`): 3-leg chain. Leg A (fresh start) shows the confirm dialog, pauses WU, schedules a task with `--resume-step1`, reboots. Leg B (a brand new process relaunched by that task) does ghost-device/driver deletion, schedules `--resume-autofix`, reboots. Leg C does the WU rescan/install, looping while new drivers keep installing. **Every reboot uses `shutdown /r /t 0 /f`** — without `/f` the unattended chain can hang forever. **Any Leg-A dialog choice that must affect Leg B cannot be a function parameter** (different OS process): append it as a flag to the scheduled-task `-Argument` string and parse it from `sys.argv` in `GuiBaseMixin.__init__` (worked example: `skip_printer_drivers`/`AUTOFIX_PRINTER_SKIP_CLASSES` in `app/wu_core.py`). **Such a flag must be re-appended by `_schedule_autofix_resume` itself, never by the call sites** (2026-07-27): of the seven scheduling sites only Leg A appended `--skip-printer-drivers`, so from Leg B onward the task was registered without it and the user's choice silently evaporated mid-chain — the resolved-value log line then contradicted itself across legs (`True` in Leg B, `False` in Leg C) on the very field question it was added to answer. It is harmless *today* only because Leg B is the sole deleting leg; the first printer-sensitive step added to the install leg would have taken the wrong branch with no trace. `run_autofix` now parks the resolved value in `self._autofix_skip_printers` and the scheduler appends it (idempotently) for every leg. The scheduled-task PowerShell is an f-string with single-quoted values — always pass exe path/args through `_ps_quote()` or an apostrophe in a username breaks the chain. Further chain mechanics that are easy to break unknowingly:
  - **The resume legs are started by the frontend, not by Python**: the scheduled task only launches the exe with the flag; `GuiBaseMixin.__init__` parses it into `self.resume_mode`/`self.resume_step1`, `get_init_data()` returns both, and **`ui.html` (in the `pywebviewready` handler) calls `startAutoFix(true)` after a 1s delay** when either is set — that's the only trigger. Consequences: (a) anything that stops the GUI from reaching `pywebviewready` (missing/broken WebView2 → CLI fallback, the single-instance mutex, a dismissed UAC prompt) silently ends the chain with no error anywhere except the debug log; (b) the auto-update check is deliberately skipped on resume legs (the `else` branch) so an update can't hijack a running chain; (c) `startAutoFix(true)` passes `skipConfirm`, so no dialog appears — the printer choice comes from argv, not from the JS `skipPrinters` value.
  - The task is `Register-ScheduledTask -TaskName "DriverVarazsloResume" -Force`, trigger `-AtLogOn`, principal `-LogonType Interactive -RunLevel Highest` (interactive+elevated is required — the GUI must be visible and admin).
  - **Leg B must never leave the machine without a scheduled task while it deletes drivers.** It used to *unregister* the task first thing and only register the next one at the very end — everything in between (restore point, ghost removal, the whole third-party delete loop, minutes of work) was an unprotected window. Field-proven (2026-07, Win10 + R9 200): the machine went down mid-delete with 9 packages already gone; no task existed, so nothing resumed, and the user found a half-stripped machine and had to restart the whole chain by hand. Leg B now **re-registers the task to `--resume-autofix` as its first action** (`-Force` overwrites) — deliberately pointing at the *next* leg, not a retry of itself: if the deletion is what killed the machine, retrying would boot-loop, whereas the install leg continues sensibly from whatever state the deletion reached.
  - **The install leg (C) arms the same safety task**, for the same reason — it is the longest and riskiest stretch of the chain (storage/chipset drivers, the poisoned-session territory), and it too used to unregister the task on entry. It is bounded by an `install_leg_starts` counter in the stats file that counts *every* entry (planned reboots and crash resumes alike); above `AUTOFIX_MAX_INSTALL_LEGS + 1` it stops arming, so a machine that never heals reboots at most once more than a normal chain and then stops. The counter dies with the stats file at the end of the chain (and in leg A).
  - **That safety task must be removed on the error/cancel path** (the `except` in `run_autofix`'s worker unregisters it): it exists only for an *unexpected* death. Without that, a user who stops the process — or any leg that raises — would find the machine resuming into the install leg at the next logon.
  - **Running from `%TEMP%` is handled explicitly**: if `_app_exe_path()` is inside `%TEMP%`, leg A copies itself to `%PUBLIC%\DriverVarazslo_Resume.exe` (`.py` from source) and schedules *that* — otherwise the app's own temp-cleanup / Windows can delete the exe between reboots and the task launches nothing.
  - **Every reboot in the chain goes through `_reboot_or_cancel(status)`** — it keeps the 5s grace window but polls `_cancel_flag` twice a second, and on cancel it **unregisters `DriverVarazsloResume` before raising** the cancel exception. The old `time.sleep(5)` + unconditional `shutdown` ignored a Cancel pressed inside that window (field-seen, Build 224: the user cancelled and the machine rebooted anyway), and without the unregister the chain would have resumed at the next logon regardless — a Cancel that only *looks* like it stopped anything. Do not re-inline a bare `shutdown` at a chain step.
  - **A requested update that never gets a `FOUND:` line must be reported** (`wu_core.unoffered_requested_titles`, used by the AutoFix rounds and the manual `_install_wu_api_sync`): the script walks its *own* search results and emits `SKIP:` for everything not in our filter, so **counting SKIP lines is meaningless** — the real signal is a requested title with no `FOUND:`. Field-seen (Build 224): "Telepítendő driverek száma: 3" followed by `TOTAL: 2`, and the third package vanished without a word (the server had started reporting it as installed after the previous round).
  - **The Store-app sync at the very end is a *bounded* synchronous wait — 10 min, then move on** (explicit user decision, Build 228, reversing the earlier fire-and-forget design): `Invoke-CimMethod -MethodName UpdateScanMethod` runs a full Store scan (measured 112s in the field) that updates the DCH companion apps (Intel GCC, Realtek Audio Console), never drivers. It *used* to be a detached `subprocess.Popen` with no wait — but the chain's final leg does NOT reboot, so the user eventually closes the app, and the exit-time `cleanup_zombies()` `taskkill /F /T` kills the whole process tree, so the fire-and-forget child usually never finished. It now runs via `self._run(..., timeout=600)`: `_run` swallows `TimeoutExpired` → `CMD_TIMEOUT_RETURNCODE`, so on the (rare) 10-min overrun we print "the Windows background will continue it" and proceed, otherwise "done". Don't revert it to a detached Popen — the taskkill-on-exit is why that silently lost the sync.
  - **The install leg re-chains itself** (this predates the 2026-07 fixes but is easy to miss): when the WU round loop ends it reboots and schedules another `--resume-autofix` leg if anything installed **or** if the round was cut short by the poisoned-session guard (`self._autofix_reboot_pending`, set by `_scan_and_install_wu_sync`) — that is how the packages skipped by the `'reboot'` abort actually get installed, on a clean boot. `AUTOFIX_MAX_INSTALL_LEGS` (10, counted from the `legs` array in `autofix_stats.json`, which survives reboots) is a **high last-resort backstop**, NOT the normal stop: per explicit user decision (Build 228) the chain runs "until a round installs zero new drivers, and *that* is done" — reaching the leg cap only happens on a pathological machine where a fresh package genuinely re-installs every leg. It was raised from 3 to 10 once the real Build-228 cause (an already-staged catalog package counted as "1 installed" every leg) was fixed in `_install_catalog_sync` (the "already exists" no-op above); the catalog closing round is also deferred when a reboot is pending. All three scheduling sites go through **`_schedule_autofix_resume(resume_flag)`** — do not re-inline the `Register-ScheduledTask` block, it used to exist in three copies.
  - **The wedged-PnP delete rule (leg B → leg C hand-off, 2026-07)**: deleting a package can wedge the device stack so that *every following* `pnputil /delete-driver` blocks for **~143s** (Windows' own internal query-remove timeout) — field case: an Intel RST `iastorhsa_ext.inf` extension, which turns a 1-minute delete phase into 45+ minutes. **Every** stalled package (`drivers_core.delete_stalled` — our `DELETE_DRIVER_TIMEOUT`=60s firing, or codes 480/482) goes onto the `pending_deletes` list in `autofix_stats.json`, even when the loop carries on — without that the package is simply never deleted *and* WU then sees it as installed, so it never gets replaced either (field-seen on Build 224: `iastorhsa_ext.inf` silently survived a full chain). On the first stall **plus** a pending reboot, `_delete_third_party_sync` also stops trying, adds the untouched remainder, and returns `'wedged'`. **It must NOT reboot there** (explicit user decision — the delete phase runs in one go, then the leg's normal reboot happens): the leftovers are swept at the *start of leg C* by `_finish_pending_deletes()`, where a fresh boot makes each one take ~0.5s (field-measured). That sweep only touches packages named in the list whose *original* INF name still matches (so a renumbered `oemXX.inf` can never take out a freshly installed driver). **Deletion repeats until it is actually finished** (explicit user requirement): if the sweep wedges again it re-defers the remainder and chains another reboot, but only while it is *making progress* — a round that deletes **zero** packages means they are undeletable (e.g. an in-use printer INF) and no reboot can help, so it gives up immediately; `AUTOFIX_MAX_DELETE_ROUNDS` (3) is the backstop. **When the sweep does finish the deletion, the leg reboots once more before installing anything** — the fresh boot both completes the removals and clears the pending-reboot state that would otherwise send the very first install straight into the `[kód=4]` wall. **`DELETE_DRIVER_TIMEOUT` must stay well below 143s** or it never fires — the first attempt used 180s and was inert.
  - **A failed WU search must never be reported as "everything is installed"** (2026-07-26). `_search_wu_api` returns `None` on failure (300s timeout or a WUA error) and `[]` when the search ran and the server offers nothing — the install leg used to collapse both with `or []`, and the no-matches branch then printed `✅ Szerveren nincs újabb valós illesztőprogram. / Minden elérhető driver telepítve!`. On a machine with a dead WU Agent that is the exact opposite of the truth, and it is what the field log preserved. Keep `wu_search_failed` separate, say the WU did not answer, and point at the catalog closing round plus a follow-up manual scan.
  - **Cancelling inside the delete phase leaves a half-stripped machine and nothing resumes** — the error path deliberately unregisters `DriverVarazsloResume` (a Cancel must not resume), so the loop's cancel branch has to state the count already deleted and tell the tech to re-run the fix. Silence here reads as "Cancel undid it", which is the opposite of what happened.
  - **`powercfg /h off` (leg B) is never turned back on**, deliberately — with hiberboot on, the "reboot" does not fully reinitialize the PnP stack. But it is a lasting, user-visible change on a customer machine, so `_emit_fast_startup_note` *queries* the state at the end of the chain (never assumes it) and says so, with the `powercfg /h on` command to undo it. **Two registry values, not one** (fixed 2026-07-28): `powercfg /h off` clears `HibernateEnabled` (`…\Control\Power`) and does **not** touch the Fast Startup checkbox `HiberbootEnabled` (`…\Control\Session Manager\Power`), which stays `1` but is inoperative — Fast Startup is built on hibernation. The code read only `HiberbootEnabled`, so after a perfectly successful `powercfg /h off` (`returncode=0` in the field log) it concluded Fast Startup had been re-enabled: it logged a false WARNING **and suppressed the user-facing note entirely** — i.e. the one thing the function exists for never happened. Fast Startup is effective iff **both** values are 1. Second rule from the same fix: the note is emitted only when `HibernateEnabled` is `0`, i.e. when our own change is actually visible. If hibernation is back on, the `powercfg /h off` did not stick, and claiming "we turned it off, undo with `powercfg /h on`" would be false in both halves — that case logs a warning and stays silent on screen. Verified offline against all 7 combinations of the two values (including both-unreadable).
  - **A crashed install leg can strand `NoAutoUpdate=1`**: the leg sets that policy for the WU search and removes it in a `finally`, which does not run on BSOD/power loss — and that value disables **all** of Windows Update, not just drivers. `_cleanup_leftover_autofix_policy` (called from `GuiBaseMixin.__init__`, same slot as `_restore_power_after_stress`) removes it at the next start, but only on **evidence it is ours**: not in a resume leg, and a leftover `autofix_stats.json` exists. Never widen that condition — an admin's deliberate policy must survive.
  - Leg A also gates on `_check_internet()` before doing anything (no net → abort with a toast, nothing is deleted), clears `autofix_stats.json` (carrying `pre_packages` over as `carry_pre_packages` first), and calls `_disable_sleep_sync()`; leg B repeats `_disable_sleep_sync()` and runs `powercfg /h off` (Fast Startup off — with hiberboot on, the "reboot" doesn't fully reinitialize the PnP stack and re-enumeration after driver deletion is unreliable).

### What actually gets a driver — the inventory

#### "Device X got no driver" — walk the chain in this order

The single most-asked field question, and the answer is spread across four subsystems, so guessing wastes a whole session (it cost three in a row before this table existed). Every step below names the **log line that settles it**, so it is answerable from a pasted log alone. Stop at the first step that explains the device — do not change any list until you know which layer dropped it.

Two shortcuts worth remembering: a device missing from step 1 can never be fixed by touching a Catalog blocklist (that mistake cost the monitor its drivers for a long time), and steps 7–11 only ever concern the **Catalog** — the WU Agent has no class filter above step 3.

**Read this first, because the obvious mental model is wrong in one important way:** it is *not* "the WU Agent sees everything, and only the Catalog has blocklists". Before either source runs, `_filter_wu_scan_devices` drops whole device classes (`WU_SCAN_IGNORED_CLASSES`) — and that filter gates **both** paths, so a class listed there is unreachable by the WU Agent too, not just by the Catalog. That is why the monitor got nothing for so long: it was never in the device list to begin with, so no Catalog blocklist change could ever have fixed it. Layer order: (1) `WU_SCAN_IGNORED_CLASSES` — applies to everything; (2) WU Agent — no further class filter on top; (3) the three Catalog entry points, which **since 2026-07-28 share one rule set**: all three take every device, minus the two checkbox-gated risk classes. When a device "gets no driver", find out which layer dropped it before changing anything — the log names every one of them.

> **THE GOVERNING RULE (explicit user decision, 2026-07-28 — this outranks every list below).** A device is excluded from the driver search in **exactly two** cases, and no third may be added:
> 1. **the user unticked it** — storage (`mc-allow-storage`) or firmware (`mc-allow-firmware`), both default off, both re-set on every dialog open, both governing *all four* rounds;
> 2. **it is not hardware** — the seven conceptual classes in `WU_SCAN_IGNORED_CLASSES` (volume objects, audio endpoints, the print queue, the HAL, non-PnP entries), plus devices with no `PNPDeviceID` and hypervisor guest devices.
>
> Everything else gets searched, in every round, on every source. There is **one** additional rule, and it is deliberately *not* a device filter: `is_specific_hwid` refuses to use a **type code** as a Catalog search key, because the Catalog answers a type code with any vendor's package for that type. The device still enters the round — only the useless key is skipped.
>
> The three earlier generations of this rule (per-round class whitelists, class blocklists, the vendor-HWID requirement, the bus-enumerator INF list) are all gone, and every one of them turned out to hide real drivers: the class lists kept a printer/keyboard/USB controller from ever being asked about, and the bus-INF list hid `Intel - System 11.7.0.1019` on a `machine.inf` node and `Intel - System 9.21` on the HD Audio controller. **If a round ever needs to be made cheaper, add threads or a cache — never a device filter.**

Four independent sources feed drivers onto a machine, and it is easy to misattribute a gap to the wrong one. **Both the manual scan and AutoFix use the same functions for all of it** — the only difference is that the manual scan lists candidates with checkboxes and AutoFix installs them unattended. Never fork a second implementation for one of the two.

| Source | Covers | Behaviour |
|---|---|---|
| **WU Agent** (`_search_wu_api` + `_match_wu_updates_to_devices`) | every present device, **no class whitelist** — chipset, GPU, audio, LAN, Bluetooth, mice, controllers, cameras | the main path; AutoFix installs automatically, manual scan lists |
| **Update Catalog — error-coded devices** (`_catalog_search_collect`) | devices with `ConfigManagerErrorCode` ≠ 0 that WU had nothing for | automatic in both paths |
| **Update Catalog — generic-driver devices** (`mark_generic_replace_candidates`) | devices running on an inbox driver, no class filter since 2026-07-28 | manual scan: pre-selected with a badge; AutoFix: closing round |
| **Update Catalog — deep scan** (`deep_catalog_candidates`, 2026-07) | **every** remaining device with a vendor-coded HWID — i.e. a device happily running an *old vendor* driver, which none of the rows above reach | manual scan: `start_hw_scan(deep=True)`, default on, checkbox `hw-deep-scan`; AutoFix: `AUTOFIX_DEEP_CATALOG` |
| **Vendor sites** | NVIDIA (download + silent install), AMD/Intel/motherboard/OEM (link-out only) | end of `start_hw_scan`, fail-silent |

**The deep scan (2026-07) is what closes the "old but working vendor driver" hole.** Before it, a device that was neither error-coded nor on an inbox driver was never asked about in the Catalog at all — so a 2023 chipset driver that worked fine simply never updated (WU considers the device healthy and offers nothing). `deep_catalog_candidates` feeds every remaining device to the same `_catalog_search_collect`, and the release gate in `_catalog_find_driver` (strictly-newer only, **by date** since 2026-07-27 — see `is_newer_release`) is what keeps it from downgrading anything. Measured live (2026-07-25, X570 + RTX 3060): 99 present devices → **16** deep candidates → 12s → 3 genuinely newer packages that the old code missed (AMD PCI 1.0.0.83→1.0.0.90, AMD PSP 5.17→5.44, plus the Realtek generic-replace), while correctly rejecting the NVIDIA row (catalog 32.0.15.9595 < installed 32.0.16.1074) and the identical-version Realtek NIC. **Exactly one filter is left: `DEEP_CATALOG_BLOCKED_CLASSES` (the two checkbox-gated risk classes).** The vendor-coded-HWID requirement and the bus-enumerator INF blocklist were removed on 2026-07-28 together with round 3's copies — **both constants (`_VENDOR_HWID_RE`, `GENERIC_REPLACE_BLOCKED_INFS`) are deleted**; a comment block marks their old spot so they don't get reintroduced as device filters. Measured immediately after, on the same Intel Q170 box: **95 devices → 91 in the combined catalog round, and the only 4 left out were the 3 storage devices and 1 firmware device the checkboxes gate** — i.e. the device set is now exactly "everything except the user's two exceptions". Cost: the full round went to **48s on 10 threads** (91 devices × up to 4 HWID queries each). Gain on that machine: 4 hits → **10**, including an Intel I219 NIC package, Intel HD Graphics 530 `31.0.101.x`, the Intel chipset `10.1.1.44`, Intel AMT Ports and the Management Engine Interface — none of which any earlier configuration would have found. One of the ten (`AlpsAlpine - System` on an Intel chipset device) looks like an OEM bundle indexed under a shared chip ID, the same shape as the Clevo-Realtek case; `inf_package_applies` plus the post-install bind check are what catch those, at the cost of a download. **`DEEP_CATALOG_BLOCKED_CLASSES` used to be deliberately narrower than the generic-replace blocklist** (HID/Display/Ports allowed, on the theory that updating an existing vendor driver to its own newer version is not the same risk as swapping Microsoft's driver for a vendor one) — **as of 2026-07-28 the two are identical** (`STORAGE_RISK_CLASSES | FIRMWARE_RISK_CLASSES`), because that distinction produced the indefensible result that a device got no better driver *because* it was on a worse one. **Storage must stay in it**: during development the deep set did pull in `Standard NVM Express Controller` and `Standard SATA AHCI Controller` before that list existed, which is exactly the `INACCESSIBLE_BOOT_DEVICE` scenario the whole project avoids.

**The list below is now mostly HISTORY — read it as the reasoning behind the two surviving exclusions, not as a live blocklist.** As of 2026-07-28 only storage and firmware are held back, both behind checkboxes, and both fully available once ticked. Every other entry that used to live here (Display, Monitor, Processor, Battery, Printer, CDROM, WPD, USB, HID/keyboard/mouse, PCI bridges) has been reversed, each after the same discovery: the exclusion was hiding a real driver. The reasons are kept because they explain *why* storage and firmware are different in kind — and because each reversal is a warning about how easy it is to write a plausible-sounding ban that costs the shop real drivers. **Do not add a new entry here**; see the governing rule above.

- **Storage controllers** (`SCSIAdapter`, `HDC`) — **from the Catalog, in AutoFix, always; from WU in AutoFix, unless the tech ticks the box**: a bad controller swap surfaces as `INACCESSIBLE_BOOT_DEVICE` at the *next* boot, where no rollback of ours can run — not even the restore point, only recovery media. **The rule used to be enforced on the Catalog side only** (2026-07-27 audit): `SCSIAdapter`/`HDC` are not in `WU_SCAN_IGNORED_CLASSES`, so they sailed through to `_match_wu_updates_to_devices` and AutoFix would have installed a WU-offered NVMe/AHCI driver unattended — the code and this document disagreed, and it stayed hidden only because WU happened to offer nothing for the field machine's controller. Resolved by **explicit user decision**: not a silent ban (WU packages are WHQL and the server itself vets applicability, which is a different risk class from a scraped Catalog row) but a second checkbox on the AutoFix confirm dialog — `mc-allow-storage`, **default off, and forced back off every time the dialog opens** because it is a per-machine, boot-critical judgement, not a remembered setting. `wu_core.filter_autofix_risky_devices` applies it (together with the firmware switch) to the WU device list and names every dropped device in the log. The choice rides the chain through `--allow-storage-drivers` exactly like the printer flag (both appended by `_schedule_autofix_resume`, never by call sites). **Firmware has its own, second checkbox** (`mc-allow-firmware`, also default off and reset on every open, explicit user decision 2026-07-27). It is deliberately *not* folded into the storage switch, because the failure mode is a category worse: a firmware update rewrites non-volatile memory (UEFI/BIOS, SSD controller, TPM, dock), no restore point or Windows reinstall can undo it, an interrupted flash kills the device in hardware, and a TPM flash can invalidate BitLocker keys. This one closed a real hole rather than a theoretical one: `Firmware` was never in `WU_SCAN_IGNORED_CLASSES`, so **AutoFix has always been able to flash firmware unattended** whenever WU offered it — the Catalog-side block was cosmetic at the time, because firmware devices failed the then-existing vendor-HWID test and `c_firmware.inf` was on the then-existing bus-INF list. **Both of those safety-by-accident mechanisms are gone since 2026-07-28**, so the `Firmware`-class gate in `filter_autofix_risky_devices` is now the *only* thing holding firmware devices back — do not weaken it on the assumption that something else catches them. The gate is enforced at **two levels**, and both are needed: `filter_autofix_risky_devices` drops `Firmware`-class devices, and `filter_firmware_updates` drops firmware *packages* (`is_firmware_update`: `DriverClass == Firmware`, or `\bfirmware\b` in the title/model) — because an SSD firmware package pairs with the *storage controller* and a dock firmware with a *USB* device, so the device-class filter alone would miss them. The title fallback is deliberately generous and every skipped package is logged by name, so over-filtering stays visible in the field log. **The checkbox governs BOTH AutoFix sources** — the WU device list (`filter_autofix_risky_devices`) *and* the Catalog deep scan (`deep_catalog_candidates(include_risky=…)`). It was WU-only for one iteration; that was rejected as confusing (explicit user decision): the tech makes one decision about storage drivers, not one per source. The manual scan always passes `include_risky=True` and renders any hit with the red badge, unticked; the gain over Microsoft's inbox NVMe/AHCI driver is ~nil on modern hardware; and this project already has a field case of a vendor storage driver (Intel RST `iastorhsa_ext.inf`) wedging the PnP stack for ~143s per package. **Since 2026-07-27 the *manual* scan does look them up** (`deep_catalog_candidates(include_risky=True)`, `STORAGE_RISK_CLASSES`) and shows any hit with a red `⛔ KOCKÁZATOS` badge, **not pre-selected**, plus a `[CATALOG] KOCKÁZATOS … bevonva` WARNING in the log naming the devices — explicit user decision: a tech looking at the screen may take that risk, an unattended chain may not. **That badge must come from `wu_core.device_risk_marker`/`mark_device_risk`, applied at every entry point into the pool, not just the deep scan** (fixed 2026-07-28): the flag was set inside `deep_catalog_candidates` only, so the *same* NVMe controller rendered red-and-unticked or silent-and-pre-ticked depending on which source happened to find it — the error-coded `leftover` list and every WU match arrived unmarked, and "select all → install" then put a boot-critical driver on with no warning shown. The WU side additionally checks the *package* with `is_firmware_update` for the same reason `filter_firmware_updates` exists (an SSD firmware pairs with the storage controller, a dock firmware with a USB device). The short list label lives in Python (`RISKY_CLASS_LABEL`/`FIRMWARE_CLASS_LABEL` → `risk_label`), because ui.html used to hardcode the storage wording — "a Windows nem indul el" — onto firmware hits too, which is neither true nor the actual danger. Never pass `include_risky=True` from AutoFix except from the dialog's own switch. **The checkbox gate must sit at the TOP of the AutoFix catalog closing round, on the whole device list — not per branch** (fixed 2026-07-28): the round feeds the Catalog from three sources (error-coded + generic-replace + deep scan), the gate lived only on the deep one, and `problem_devs` was a raw `[d for d in devices_now if d.get('err_code')]`. Neither `_catalog_search_collect` nor `_catalog_find_driver` filters by class, so **a single error code was enough to bypass both checkboxes** and have AutoFix install an NVMe/AHCI or firmware package unattended — the one outcome this whole section exists to prevent. `filter_autofix_risky_devices` now runs once on `devices_now` (with `log_tag`/`context` so its log line names the *catalog* round, not the WU one), which also means a future fourth source cannot reintroduce the hole. The same argument applies to the manual scan's `leftover` list — see the risky-badge rule below. **`DiskDrive` is in `STORAGE_RISK_CLASSES`, not in `WU_SCAN_IGNORED_CLASSES`** (moved 2026-07-27; this paragraph claimed the opposite for a while): the disk normally runs on the universal `disk.inf` with no replacement on offer, but rather than ban it outright it rides the storage checkbox like the controllers — measured on a live box, `KINGSTON SA400S37480G [DiskDrive]` is one of the devices the unticked box holds back. What actually helps an SSD is a **firmware** update, which has its own checkbox.
- ~~**Display, from the Catalog**~~ — **reversed.** The old reasoning (the NVIDIA/AMD/Intel cards are a strictly better source, the Catalog is always older) holds only for a machine *already on a vendor GPU driver*, and such a device is not a generic-replace candidate anyway. On a box stuck on the Microsoft Basic Display Adapter the vendor cards deliver nothing in AutoFix (AMD/Intel are link-out only, the NVIDIA check runs in the manual scan alone), so the Catalog was the only source and we were refusing it. Live-measured after the reversal: an Intel HD Graphics 530 picked up `Intel Corporation - Display - 31.0.101.x` from the Catalog. The release gate still prevents a downgrade.
- ~~**Monitor**~~ — **reversed 2026-07-27 (explicit user decision).** The old reasoning ("EDID/colour metadata, not a functional driver") was the wrong test: a vendor monitor INF installs an EDID override *and the factory ICC colour profile*, which is exactly the half that makes `colorprofile_core`'s reset land on a correct default instead of a bare sRGB guess. Monitor is now out of `WU_SCAN_IGNORED_CLASSES` (so the WU Agent sees it at all — that filter gates **both** sources), out of `DEEP_CATALOG_BLOCKED_CLASSES`, and a normal generic-replace candidate (it was added to the then-existing `GENERIC_REPLACE_CLASSES` whitelist; since that whitelist was removed on 2026-07-28 it simply is not excluded by anything), so "Generic PnP Monitor" → vendor monitor driver goes through with the usual rollback net. `_VENDOR_HWID_RE` had to learn the `MONITOR\ACI27FA` shape too (no `VEN_`/`VID_` token, but still a specific vendor+model). Nothing here can be boot-critical.
- **Processor / Battery** — also removed from `WU_SCAN_IGNORED_CLASSES` the same day: AMD/Intel chipset bundles do ship processor power-management drivers and OEMs do ship battery/charge-controller drivers, and neither carries boot risk. They cost nothing in the Catalog paths, because `ACPI\…` IDs fail the `_VENDOR_HWID_RE` vendor-HWID test anyway — only the WU Agent path picks them up.
- **`Printer`, `CDROM`, `WPD` were removed from the device filter too, and `DiskDrive` moved under the storage checkbox** (2026-07-27, explicit user decision: "MINDEN kapjon drivert, semmi ne legyen kizárva, kivéve amit checkboxszal nem engedek"). The printer one fixed a genuine asymmetry: the printer checkbox only ever protected drivers from *deletion*, while `Printer` sat in `WU_SCAN_IGNORED_CLASSES`, so with the box unticked AutoFix deleted the printer driver **and could never look for a replacement**. The checkbox keeps its meaning (don't delete the existing one) — its label now says so — but a printer can get a driver in both positions.
- **Two hidden filters in `_filter_wu_scan_devices` were also opened up, and all of them now log what they dropped.** They had excluded devices for four separate reasons while logging *none* of them, so "why did device X get nothing?" was unanswerable from a field log — a direct violation of the log-everything rule this file opens with, hiding in the one function every driver decision starts from. (a) The name test was a raw `"virtual" in name` substring match that threw out **real hardware** — `Intel(R) Virtual Buttons`, the volume/power buttons on most business laptops and 2-in-1s — and is now `_VIRTUAL_DEVICE_NAME_RE`, word-bounded hypervisor names only (`vmware|virtualbox|vbox|qemu|parallels|hyper-v|xen|virtio`). (b) The blanket `ROOT\` prefix skip is gone: most root-enumerated devices are Microsoft software objects that no source ships a package for, but application-installed drivers live there too (ViGEmBus, VPN TAP adapters), and skipping them also kept a broken one off the "Problémás eszközök" list entirely. The Catalog paths drop them anyway on the vendor-HWID test, so the cost is a few extra in-memory comparisons. **If you ever add an exclusion here, log it in the same `dropped` dict** — a silent filter in this function is how three separate exclusions stayed invisible through several rounds of "does it now cover everything?".
- What remains excluded is only what a driver cannot exist for: `Volume`/`VolumeSnapshot` (the volume object, not the disk or controller behind it — both of those are driverized), `Endpoint`/`AudioEndpoint` (`SWD\MMDEVAPI\…` audio *endpoints* — the speaker/mic entries, not the sound card, which is `MEDIA`), `PrintQueue` (`SWD\PRINTENUM\…`, the queue, not the printer), `LegacyDriver` (a non-PnP driver entry with no device behind it), and `Computer` (the HAL — replacing it means the machine does not boot, and nothing ships a package for it anyway).
- **Keyboard/mouse/HID**: vendors ship *software* (Synapse etc.), not drivers; where a real WHQL package exists the WU path already installs it (field-confirmed: Razer `rz00b9dev.inf`).
- ~~**USB controllers/hubs — for the *generic→vendor swap* only**~~ — **no longer excluded anywhere (2026-07-28)**, when the generic-replace class lists were removed. The old argument (Microsoft's driver is the correct one on modern chipsets, and a failed swap takes out the keyboard and mouse — the very input needed to recover) survives only as a caution, not a rule: the rollback net runs unattended in the same process, so it does not need the user's input to revert, and the measurement below applies here too — nearly every USB-class device is already dropped by the bus-INF rule (`usbxhci.inf`/`usbhub3.inf`/`usb.inf`) or the vendor-HWID rule, so the class entry was protecting almost nothing. **In the deep scan `USB` had already stopped being blocked** (2026-07-27): measured against the field device list, every USB-class device was *already* dropped by one of the other two filters — `usbxhci.inf`/`usbhub3.inf`/`usb.inf` by the bus-INF rule, `USB\ROOT_HUB30` by the vendor-HWID rule — so the class entry protected nothing. The single case it did catch was a controller running a genuine **vendor** USB driver (`oemNN.inf`), which is exactly the case that should be updated, and which the inbox-version guard in `_catalog_find_driver` still protects from a generic→vendor swap by the back door. Same finding applies to `FIRMWARE` (`UEFI\RES_{…}`), `PROCESSOR` (`ACPI\AUTHENTICAMD…`) and `COMPUTER` (`COMPUTER\{GUID}`): all three fail the vendor-HWID test on their own, so listing them was documentation of an intent the code never had to enforce. **`DEEP_CATALOG_BLOCKED_CLASSES` is now exactly `STORAGE_RISK_CLASSES | FIRMWARE_RISK_CLASSES`, and it is the *only* filter the deep scan has** — the bus-INF and vendor-HWID rules that this paragraph used to lean on no longer exist. **Do not add a class back here.** The product rule is that the blocklist has exactly two entries: what the user unticks, and what is not hardware (`WU_SCAN_IGNORED_CLASSES`). If a wrong-vendor package shows up, the cause is a type-code search key, not a missing class ban — check `is_specific_hwid` first.
- ~~**PCI bridges / root ports / ACPI nodes**~~ — **this entry was wrong and is gone (2026-07-28).** The claim ("no vendor driver exists at all") was never measured, only assumed, and it was the justification for `GENERIC_REPLACE_BLOCKED_INFS`. When the filter came off, a `machine.inf` "Motherboard resources" node returned `Intel - System 11.7.0.1019` and the HD Audio *controller* returned `Intel - System 9.21` — real chipset drivers that had been silently unreachable for as long as the list existed. Bus/enumerator devices are now queried like everything else; the ones that genuinely have nothing simply return zero rows, which costs a request and answers the question honestly.
- **Printer, PrintQueue, AudioEndpoint, Battery, Processor, Computer, Volume, CDROM, WPD**: excluded at the device-filter level (`WU_SCAN_IGNORED_CLASSES`).

**Boot-path protection is the one exception on the *delete* side (`wu_core._collect_boot_path_protection` / `_is_boot_path_protected`, 2026-07-26, used by BOTH AutoFix paths).** The blocklists above only ever governed *installing*; the delete phase had no class filter at all and `drivers_core.delete_driver_package` calls `pnputil /delete-driver … /uninstall /force` — i.e. it removes an in-use, boot-critical storage driver too (CLAUDE.md already documents the Intel RST case surviving only by *stalling*). On plain AHCI/NVMe that is harmless: Microsoft's inbox `storahci`/`stornvme` takes over. **Behind Intel VMD or an RST RAID volume it is not** — the inbox stack may not cover the controller, and the result is `INACCESSIBLE_BOOT_DEVICE` at the next boot, the one failure mode where none of our rollbacks (restore point included) can ever run, because the machine cannot start. So before deletion the code resolves the device chain carrying `%SystemDrive%` (WMI `Win32_LogicalDiskToPartition` → `…DiskDriveToDiskPartition` → `Win32_DiskDrive.PNPDeviceID`, falling back to `Get-Partition`/`Get-Disk`, then walking `DEVPKEY_Device_Parent` up to 12 levels) and protects every third-party package on it, exactly like the printer protection (published **and** original INF name, since a reinstall renumbers `oemNN.inf`). Two rules that must not be softened: (a) this is **targeted, not class-based** — a class blocklist here would gut the "strip everything" design, and measured live (2026-07-26, WD Blue SN580) the chain resolves to `disk.inf` → `stornvme.inf` → `pci.inf` → `acpi.inf` → `hal.inf`, i.e. all inbox, so **zero** packages get protected and the fix behaves exactly as before; (b) if the chain cannot be resolved at all, it **fails safe** to protecting all `BOOT_FALLBACK_PROTECT_CLASSES` (`SCSIAdapter`/`HDC`/`DiskDrive`) rather than falling back to the old unprotected behaviour — an unnecessarily retained storage driver is at worst stale, a wrongly deleted one is a machine that will not boot.

**Asymmetry worth remembering**: the AutoFix *delete* phase removes third-party packages regardless of class (bar the printer opt-out and the boot-path protection above), but the *reinstall* only reaches classes that survive `WU_SCAN_IGNORED_CLASSES`. A deleted **printer** driver therefore never comes back through us — which is exactly why the printer checkbox exists and why leaving it on is the shop-safe default.

### WU + Catalog engine (shared by AutoFix and the manual scan)

- **WU driver scan/install — shared core (`app/wu_core.py`)**: the PnP query+filter (`WU_PNP_QUERY_PS` + `_filter_wu_scan_devices`), WU↔device matching (`_match_wu_updates_to_devices` → `_hwid_matches`: **prefix match OR same-bus token-subset**, plus title↔name fallback, without which SoftwareComponent packages never match. The token rule is not a nicety: Windows composes hardware IDs as `VEN&DEV&SUBSYS&REV`, while WU frequently ships `VEN&DEV&REV` — SUBSYS sits *between* the tokens, so neither string is a prefix of the other. Field-proven (2026-07, Win10 + Radeon R9 200): `pci\ven_1002&dev_6811&rev_00` never matched `PCI\VEN_1002&DEV_6811&SUBSYS_30001682&REV_00`, so AutoFix **deleted the vendor GPU driver and silently never reinstalled it** — the machine finished the "successful" run on the Microsoft Basic Display Adapter, error-code-free, so even the summary looked clean. Class-scoped `&cc_` package IDs were unreachable for the same reason. IDs with no bus prefix — bare `usbmmidd` — stay exact/prefix-only, since anything looser false-positives on them), and the WUA installer PowerShell (`_build_wu_install_ps`) exist in exactly ONE copy, used by all three consumers: GUI manual install (`app/gui/hwscan.py`: `start_hw_scan` pool + `_install_wu_api`, filtering by exact `UpdateID`s with HWID-prefix fallback), GUI AutoFix (`_scan_and_install_wu_sync`), CLI AutoFix (FÁZIS 6, `match_system_devices=True`). **Never copy this logic back into a class** — the duplicated era produced the "AutoFix works, manual install silently broken for a whole release" bug (Build ~192). Baked-in rules: downloads are **synchronous `$DL.Download()`** — never `BeginDownload($null,...)` (null callbacks throw NullReferenceException instantly; that was the Build-192 regression; hang protection is the Python-side cancel `taskkill`); selection filters by exact `UpdateID` because distinct WU packages can share one HWID (field-seen: 3 selected → 4 installed with HWID-only filtering); with no filter args the script installs NOTHING (`EMPTY`). The script emits a line protocol (`INIT/SEARCH/FOUND/SKIP/TOTAL/DLONE/INSTONE/OK/OKRB/FAIL/EMPTY/DONE/ERROR`) parsed by all three callers — adding a marker means updating all three reader loops (`OKRB` = success but `$IR.RebootRequired`; counted as success everywhere, surfaced as a reboot warning in the manual GUI path via `self._wu_reboot_required`). **All three reader loops go through `wu_core._iter_process_lines`** (reader thread + queue): cancel is checked every 0.5s even when the script emits nothing, and a watchdog taskkills the process after 30 min of silence (`WuProcessAborted('cancel'|'hang')`) — the old direct `for line in process.stdout` blocked forever (dead Cancel button) when the in-script WUA search hung; don't revert to direct iteration. **The "poisoned session" rules (2026-07, field-diagnosed twice on a Dell OptiPlex 7060 — Builds 214 and 218) — all three live in `wu_core` and are used by both AutoFix paths:**
  - `is_reboot_pending(run)` (+`PENDING_REBOOT_PS`): once a *storage/chipset* driver installs (field case: Intel RST `iaAHCIC`), Windows goes pending-reboot and the WUA then returns `orcFailed(4)` for **every remaining package in that session — after a fixed ~143s wait each**. 8 leftovers = ~20 wasted minutes per round. `_install_abort_reason(consecutive_failures, reboot_pending)` is the shared decision: `'reboot'` if pending, else `'failstreak'` after `WU_MAX_CONSECUTIVE_FAILURES` (3) consecutive install failures (the net for a session that rots without setting the flags), else None. It is wired in through the new `abort_check=` parameter of `_iter_process_lines`, which kills the installer process and raises `WuProcessAborted(reason)` — callers never touch the PID.
  - **The pending-reboot query runs only after an install FAILURE, never after `OKRB`** — deliberate: in the field log the OKRB'd Display driver was followed by three more packages that installed fine, so bailing on mere reboot-*need* would sacrifice good installs. Failure is the evidence; reboot-need is not.
  - `verify_failed_installs(failed_titles, pkgs_before, pkgs_after)`: **a `[kód=4]` is not proof of failure.** All 8 "failed" packages in the field log were sitting in the DriverStore afterwards — the WUA verdict was a false negative. After every round the third-party package list is re-read and any failed title whose version shows up among the newly added packages is counted as a **success** (and never added to `install_failed_uids`). Never report a WUA install failure to the user without this check.
  - `_filter_wu_older_duplicates(matches, wu_by_uid)`: WU offers a package's whole history (field: 10 `iigd_ext` Extension packages for one Intel UHD 630, from 2018), and AutoFix used to install every one of them. Keeps only the newest per `(HardwareID, DriverClass, DriverProvider, DriverModel)` family. That key is deliberately narrow: a wrong merge means a needed driver never installs, while a missed merge only restores the old behaviour.
- `_filter_wu_downgrades` (+`_iso_date_or_none`) is the AutoFix **downgrade guard**: WU can offer a package *older* than the installed driver (field-relevant right after a vendor NVIDIA install); matches whose `DriverVerDate` is strictly older than the installed driver's date are skipped — but NEVER for error-coded devices (any driver beats none), and **NEVER when the currently installed driver is an inbox (Windows built-in) one** (`_is_inbox_driver`: published INF is not `oemNN.inf`, or provider is Microsoft). That second exception is not optional: AutoFix deletes the vendor package, Windows immediately drops its own generic driver on the device, and an inbox driver's date is always newer (it ships with the OS) — so a pure date comparison locks the vendor driver out *forever*. Field-proven (2026-07, X670): `atihdwt6.inf` (AMD HDMI audio, 2021-07-13) was skipped in all three rounds because the inbox `hdaudio.inf` replacing it reports 2026-05-16, and the machine ended the run with one fewer driver than it started with. This is why `_get_installed_driver_info` also selects `DriverProviderName` + `InfName`. The manual scan doesn't filter, it only flags (`downgrade: true` pool items render an orange warning and are not pre-selected) — using the same inbox exception.
- **Printer protection 2.0 (`app/wu_core.py`: `_collect_printer_protection` + `_is_printer_protected`, used by BOTH AutoFix paths)**: class-based skipping (`AUTOFIX_PRINTER_SKIP_CLASSES`) alone was NOT bulletproof — multifunction printer packages spread across USB/Ports/SYSTEM classes (field-seen: `mvusbews.inf`, `hppscnd.inf`, `hpbuio70l.inf`), and deleting those broke customer printers/scanners. Before third-party deletion the code now also protects (a) every INF actually used by present printing components (`Get-PrinterDriver` InfPath + present Printer/PrintQueue/Image devices' `DEVPKEY_Device_DriverInfPath`) and (b) every package whose provider matches a printer vendor present on the machine (`PRINTER_VENDOR_KEYWORDS`; deliberately over-protective — WU restores e.g. HP laptop drivers anyway, a broken customer printer is unrecoverable). **INF matching must check both the published (`oemXX.inf`) and original (`hpc1320u.inf`) names** — `Get-PrinterDriver` reports original names, PnP `DriverInfPath` reports published ones (live-verified on the shop machine).
- **NIC safety net (`app/wu_core.py`: `_export_net_driver_backup`/`_restore_net_driver_backup`, both AutoFix paths)**: AutoFix deletes the LAN/Wi-Fi driver too, and if neither inbox nor WU covers the NIC (field-seen: fresh AM5 + Realtek 2.5GbE), the machine strands offline while the chain needs internet. Before deletion, Net-class packages are exported (`pnputil /export-driver`) to `<app_data>\netdrv_backup`; on the resume leg (GUI) / after install (CLI), if `_check_internet()` fails the backup is reinstalled + rescan.
- **NIC rescue pack — REMOVED (explicit user decision, 2026-07-28)**: `app/nicpack_core.py` + `app/gui/nicpack.py`/`app/cli/nicpack.py`, the GUI "🛟 LAN Mentőcsomag" button/chip, the CLI menu item AND the AutoFix no-net last-resort branch are all deleted. It solved the no-NIC-driver → no-internet bootstrap via a hand-built `nicpack.zip`, but the shop never used it — their standing practice is a USB→RJ45 adapter with a built-in driver, which covers the same emergency with zero maintenance (the zip was a manually curated release asset that would have rotted). The AutoFix no-net message now recommends exactly that adapter. The `netdrv_backup` export/restore safety net (which backs up the machine's own Net drivers before deletion) is unrelated and **stays**. Don't reintroduce the pack; if the no-net rescue ever needs strengthening, extend `netdrv_backup`, not a curated zip.

### Vendor-site driver sources (GPU + motherboard)

- **Vendor-latest NVIDIA driver check (`app/gui/nvidia.py`)**: WU's GPU drivers lag months behind; after each manual scan `_check_nvidia_driver()` queries NVIDIA's public services (lookup XML TypeID=3 cached 7 days in app-data → `AjaxDriverService DriverManualLookup`, DCH first then standard; osID 135 for Win11 build≥22000 else 57) for the *real* PCI NVIDIA GPU (`VEN_10DE` — virtual displays excluded), converts installed `DriverVersion` `32.0.15.6636` → NVIDIA `566.36` (last-5-digits rule), and emits `nvidia_driver_info` for the UI card; `install_nvidia_driver()` downloads with MB progress and runs the installer silently (`-s -noreboot`, returncode 1 = ok-but-reboot; cancel works during download only — never kill a GPU installer mid-flight). Product matching: exact name else longest-substring (so "RTX 3060" doesn't shadow "RTX 3060 Ti"); everything is fail-silent so a scan can never break on NVIDIA's servers. Live-verified: GT 710→475.14, RTX 3060→610.74.
- **AMD/Intel vendor check (`app/gui/vendorgpu.py`) + OEM card (`app/gui/oemdrivers.py`) — LINK-OUT ONLY, deliberately**: unlike NVIDIA, AMD/Intel have no stable public download API, and both block referer-less direct exe downloads — so these cards compare versions and open the official page (`open_vendor_driver_page`, https-only guard), they must NOT be "upgraded" to auto-download scraped installers. AMD's latest comes from the *official* GPUOpen `amd-vulkan-versions` repo `amdversions.xml` (cached 3 days; its `<windows-version>` e.g. `32.0.31021.5001` compares directly against `Win32_VideoController.DriverVersion`; newest WHQL by release-date). Intel's comes from the stable-ID download page 785597 (highest `\d+.0.101.\d+` in the page text) and is offered **only** for the modern unified driver family (installed version matches `^\d+\.0\.101\.` or an Arc card) — legacy iGPUs can't apply it. The OEM card deep-links Dell by Service Tag (`.../servicetag/<tag>/drivers`), Lenovo by serial search, HP generic page + serial shown for manual entry. **When `Win32_ComputerSystem.Manufacturer` is a placeholder (`To Be Filled By O.E.M.`, `Default string`, …) — i.e. a self-built machine, which is a large share of shop intake — it falls back to `Win32_BaseBoard` (`BOARD_VENDOR_PAGES`: ASRock/ASUS/MSI/GIGABYTE/Biostar) and shows the board's support page + the board model to type into their search.** That fallback exists because the vendor chipset/audio/LAN drivers for desktop boards are only available there: WU does not offer them, so on a self-built box the onboard audio stays on Microsoft's generic `hdaudio.inf` and the NIC on the inbox driver (field-confirmed 2026-07-24 on an ASRock B450M Pro4 — both still generic after a full, error-free AutoFix chain), and before this the card was simply skipped, leaving the tech no pointer at all. Board links are deliberately the vendor's **support/download landing page**, not a model deep-link (those rot, and MSI/Gigabyte sit behind bot protection) — same reasoning as the HP branch. Only `_is_placeholder`-filtered values are trusted; an unknown board vendor still emits nothing. The card payload carries `title`/`desc` from Python (`renderOemCard` in ui.html falls back to the old wording) because the OEM copy ("gép", "dokkoló") is wrong for a motherboard. All three run at the end of `start_hw_scan`, fail-silent like the NVIDIA check. (A full OEM *catalog* integration — Dell CatalogPC.cab / Lenovo per-MT XML with silent installs — was consciously deferred: blind-shipping untested silent OEM installers to customer machines is riskier than the link-out.)

### DriverStore duplicate cleanup & boot repair

- **DriverStore duplicate cleanup (`app/gui/dupdrivers.py`; the GUI panel lives in the *Temp Fájlok Törlése* view since 2026-07 — it used to sit in the Drivers view, whose freed spot now holds the AutoFix quick-launch hero card)**: groups third-party packages by *original* INF name, keeps the **newest release** per group (date first, version only as a same-date tiebreak — `dup_release_key`, same rule as everywhere else since 2026-07-27; the date comes from the DISM `Date :` line, which `parse_dism_driver_list` now parses into an ISO `date` field), offers the rest for deletion. Version-only sorting used to mark the *newer* package as the deletable duplicate whenever a vendor renumbered its scheme; when date and version disagree the group logs `[DUPDRV] … a DÁTUM dönt, nem a verzió` with both candidates, since that is the only line answering "why did it keep the lower version number?". Packages with no parseable date fall back to the old version ordering. Safety rules baked in: published INFs actively used by present devices (`Win32_PnPSignedDriver` `InfName` set) are never deletable (shown locked); if that query fails the whole delete is refused (`active_infs is None` → everything marked active); only `oemXX.inf` names are ever deleted; delete tries `pnputil /delete-driver` plain first, `/force` only on failure; **`drivers_core.delete_succeeded` treats `3010` as success on the return code alone** — it is `ERROR_SUCCESS_REBOOT_REQUIRED`, the package *is* gone — and its localized text fallback matches both Hungarian stems (`törl` for törlés/törlése **and** `töröl` for törölve/törölt; one alone misses the other, which silently listed successfully-deleted packages under "nem sikerült eltávolítani"). **The negative markers must be tested BEFORE the positive stems** (`DELETE_FAILURE_MARKERS` then `DELETE_SUCCESS_MARKERS`, 2026-07-26): the text branch only runs when the return code is *not* 0/3010 — i.e. exactly in the failure case — and the Hungarian pnputil failure reads "A(z) oem12.inf illesztőprogram-csomag **törlése** nem sikerült", which contains the positive `törl` stem, so the old positive-only check reported a **failed delete as success**. That is the same silent-false-success class as the Build 218 `0xC0000142` case, and it blanked the AutoFix "could not be removed" list while the phase still printed `✅ Driverek eltávolítva`. The markers are accent-free prefixes where possible (`nem siker`, plus `torl`/`torol`/`eltavolit` mirrors) because pnputil emits ANSI and its output arrives mojibake'd in the field; the delete worker re-checks the active set at delete time (UI state can be stale). **Automatic closing cleanup**: `dupdrivers_core.auto_cleanup_duplicates(run, log, get_drivers)` is the unattended twin (same safety rules, fail-silent — a cleanup error must never fail the install) and runs at the end of every driver install: GUI manual install (`install_selected_wu`, live system only), GUI AutoFix final leg (right before `_emit_autofix_summary`), CLI AutoFix (after FÁZIS 6, only if something installed).
- **BCD button = BootFixer.cmd downloader (`app/gui/bcd.py`)**: per explicit user decision the "BCD Boot Hiba Javítása" GUI button no longer runs the built-in bcdboot/bootrec repair — it downloads the user's own `BootFixer.cmd` (raw.githubusercontent.com/egonixaimgod/boot_javito_tool/main/BootFixer.cmd, same fresh-Windows cert fallback as block.bat) into `_app_data_dir()` and the UI explains how to run it manually; the app NEVER executes it. The built-in automatic repair (after offline driver restore, and the CLI's `repair_bcd_standalone_cli` menu item) lives in `app/bcd_core.py: repair_bcd` — canonical flow: diskpart EFI-partition lookup + `bcdboot /s <EFI> /f UEFI`, falling back to `bcdboot /f ALL`, then `bootrec` — and must never be wired to the GUI button.

### Manual scan pipeline

- **Manual scan — hybrid pipeline (`app/gui/hwscan.py`)**: the scan now (1) surveys installed driver versions+dates once (`_get_installed_driver_info`, returns `{PNP: {'version','date'}}`) and shows "telepítve: X · date" next to every offer (offer side also shows `wu_date` from `DriverVerDate`/catalog row); (2) after a successful WU search runs a **catalog top-up** for error-coded devices WU returned nothing for — the pool is therefore MIXED (WU items carry `update_id`, catalog items carry `url`), so `install_selected_wu` is a **per-item dispatcher**: one `_safe_thread` worker creates a restore point, then calls `_install_wu_api_sync` then `_install_catalog_sync` (both return `(success, fail, cancelled)` and must NOT emit `task_start`/`task_complete` — the dispatcher owns the lifecycle), and on success emits `offer_rescan` (UI banner offering a new scan — chipset/USB drivers surface new devices); (3) emits a `problems` list (devices with `ConfigManagerErrorCode` ≠ 0, code descriptions in `PNP_ERROR_CODE_DESCRIPTIONS`, `has_fix` flag, `pnp_id`) rendered as a red section in the UI so unresolved devices are never silent — rows with quick-fixable codes get a button calling `fix_problem_device(pnp_id, code)` (22 → `Enable-PnpDevice`, others → disable+enable cycle; synchronous, deliberately bypasses `_task_busy`). The old catalog install path downloaded every cab TWICE (a vestigial sequential loop + the threaded worker) — the sequential loop was removed; don't reintroduce it.
- **Manual scan — WU-API timeout policy & Catalog fallback (`app/gui/hwscan.py`)**: `_search_wu_api` runs the WUA search with a 300s timeout; on timeout it restarts the WU services (that heals the *next* search) but deliberately does **NOT** retry the search itself — field-proven (cloned Windows on brand-new AM5 hardware, 2026-07, twice in a row) that the post-restart retry times out identically, doubling the wait to ~10.5 min for zero benefit. Callers handle the `None` return on their own: manual scan falls back to the Catalog, AutoFix breaks out of the WU rounds (and still runs its catalog closing round). The **Catalog engine** (`_catalog_fetch_rows`/`_catalog_find_driver`/`_catalog_search_collect`; `_catalog_search` is the pool-appending wrapper) scrapes `catalog.update.microsoft.com` on 10 threads, and per device queries **all of its *specific* HWIDs** (max 4; `wu_core.is_specific_hwid`, 2026-07-28 — **type-code IDs are never used as a search key**, and a device with no specific ID at all is skipped with a DEBUG line naming the IDs). That rule exists because the Catalog answers a type code with *any vendor's* package for that type, and once round 3 lost its device-level filters the damage was immediate and measured on an Intel Q170 box: `ACPI\PNP0501` (serial port) returned an **LG** package, `ACPI\PNP0A08` and `USB\ROOT_HUB30` each returned an **AMD** package — on an Intel machine. The USB hub is the instructive one: it *has* an Intel-specific ID (`USB\ROOT_HUB30&VID8086&PIDA12F`), but the AMD row pulled in via the generic key had a newer date and won the row selection. Filtering the *query key* rather than the *device* removed all four bogus hits, kept every legitimate one, and halved the round (13.9s → 6.9s). Do not "fix" a wrong-vendor catalog match by excluding the device — check whether a type code got used as a key. The synthesized base ID goes through the same test) plus the synthesized **base vendor HWID** (`wu_core.base_vendor_hwid` — strips `&SUBSYS_`/`&REV_`/`&CC_`), then **unions every returned row into one candidate set** before choosing. Both halves of that are load-bearing and were measured (2026-07-24, Realtek ALC892): (a) the old code stopped at the *first* HWID that returned rows and its comment claimed a more generic HWID "would return the same" — false, the SUBSYS-scoped key returns a 2021 package (6.0.9136.1) while the base key returns the 2026 one (6.0.9992.1); (b) the device's own `HardwareID` list contained **only** SUBSYS-scoped IDs, so without synthesizing the base key that newer package is unreachable entirely. Rows are **scored for the host OS/arch** (`_catalog_row_score` on the tag-stripped `<tr>` text: arm64 rows excluded on x64, Win11-only rows excluded on Win10, Server rows deprioritized; if every row is excluded it falls back to all rows), and among the best-scoring rows the **newest `Last Updated` date wins, with version only as the tiebreak** — *not* highest version: one vendor ships mutually incomparable version schemes for the same device (measured on the Realtek NIC: `Realtek - Net - 1168.19.704.2024` from 2024-07-03 vs `Realtek Net Driver Update (10.79.50.1003)` from 2025-10-02 — by version the 2024 package "wins" by three orders of magnitude). `wu_core._parse_driver_version` (tiebreak only) counts only ≥3-component number sequences as versions, so "2.5GbE" doesn't parse as 2.5; row order on the catalog page is NOT newest-first; it lives in `wu_core` because the AutoFix duplicate/verification filters use it too. Results **that are not a newer *release* than the device's currently installed driver are skipped** (`_get_installed_driver_info`) — without this the fallback re-offered a driver installed 3 minutes earlier, and this same filter is what makes the AutoFix catalog closing round terminate (the WU API path doesn't need it: the server applies `IsInstalled=0`). **"Newer" means newer by DATE, with the version only as a same-date tiebreak** — one shared definition for the whole project, `wu_core.is_newer_release` / `release_rank` (**explicit user decision, 2026-07-27**: "kit érdekel milyen verziót adnak neki, ha dátum szerint van újabb, az mehet fel"). This gate was the last purely version-based decision on the install path (the WU side's `_filter_wu_downgrades` and the catalog's own row selection were already date-first), and the mismatch cost real drivers: measured on the field machine, AMD SMBus sat on **5.12.0.38 from 2017-08-30** while the catalog offered `System Driver Update (2.0.0.26)` from **2025-12-03** — by version the 2017 package "wins" and the box kept a driver eight years old. Do not revert this to a version comparison. Two properties make it safe, both verified against that log: (a) it does not loop, because the catalog's *Last Updated* runs a day **behind** the installed INF's DriverVer date for the same package (AMD PCI `2025-09-08` vs `2025-09-09`, AMD PSP `2026-03-15` vs `2026-03-16`, Realtek NIC `2025-10-02` vs `2025-10-03`), so every already-current package still evaluates to "not newer"; (b) **when the installed driver is an inbox one and the device is not a `generic_ok` candidate, the date rule is skipped and the old version comparison stands** — an inbox driver carries a Windows date (`input.inf` says 2006-06-21), so date-first would silently turn the deep scan into a generic→vendor swapper on exactly the classes (HID, keyboard, mouse) that `mark_generic_replace_candidates` deliberately excludes, and without its rollback verification. That decision stays where it belongs. When date and version disagree the choice is logged at INFO (`[CATALOG] Dátum szerint ÚJABB, verzió szerint nem`), because "why did it install a lower version number?" is otherwise unanswerable from a paste. Install (`_install_catalog_sync(pool, task_id=...)` — task_id lets AutoFix reuse it on the 'autofix' channel) goes cab-download → `expand` → INF-presence check → `pnputil /add-driver /install` (or `dism /Add-Driver` for offline target). **A pnputil "success" is only a real install when something *new* actually landed**: `Added driver packages: 0` (nothing applied) AND the "already exists in the system" case (every `added successfully` line is a re-add of a package already staged in a previous leg — `Added driver packages: N` with N>0 but all marked `(Already exists in the system)`) are both treated as **no-ops** (counted as skipped, never success). The second check is not optional — a generic-replace candidate that stages fine but never *binds* (field: Realtek UAD audio stays on `hdaudio.inf`) would otherwise report "1 installed" every leg forever, an infinite reboot loop (field-seen, Build 228, capped only by `AUTOFIX_MAX_INSTALL_LEGS`). With the no-op detection the candidate installs once, and on the next leg its package is already in the store → 0 installs → the chain terminates on its own. **A pnputil "added successfully" is not proof the device took the driver, either** (2026-07-25, two cases in one run): the Catalog answers a *base* vendor HWID (`HDAUDIO\FUNC_01&VEN_10EC&DEV_0892`) with every OEM-specific variant of that chip, and newest-date wins — which handed an ASRock board a **Clevo-laptop** Realtek package. It staged fine (`Added driver packages: 4`) and never bound; the device stayed on `hdaudio.inf`. Same run, an NVIDIA catalog package (32.0.15.9595) lost to the incumbent 32.0.15.9186 because that one matches a **more specific** HWID (Windows ranks specificity above version/date). Both reported `✅ telepítve`, and the chain re-downloaded them every leg. Two guards now: (a) **before** install, `wu_core.inf_package_applies(ext_dir, dev_hwids)` scans the extracted INFs for a HWID matching the device's *real* `all_hwids` (returns `None` = undecidable → never blocks); (b) **after** install, the device's INF is re-read and compared against `installed_inf` captured at search time — unchanged means it didn't bind, so it counts as **skipped, not success** (crucial: a false success chains another AutoFix leg). Installs that returned `3010`/"reboot is needed" are exempt from (b) — they legitimately bind at next boot (field: AMD PSP). Non-binding items land on `self._catalog_no_bind`, which the AutoFix round persists to `catalog_no_bind` in `autofix_stats.json` so later legs don't re-download them, **and which the closing summary now names to the user** (`_emit_catalog_no_bind`): these are packages the chain proved to exist and be newer, so silently discarding them with the stats file left the shop with no idea a newer driver was available — the remedy (vendor card for a GPU, board vendor's page for onboard devices) is actionable, so it must be printed. **Guard (a) may only veto when we actually parsed the right INF** (2026-07-27, RTX 3060): a driver cab holds several INFs, and `_read_text_best_effort` returned *nothing usable* for the NVIDIA display INF while the ANSI `nvhda.inf` parsed fine — so `inf_ids` was non-empty (158 HDAUDIO ids) and the "no match" branch vetoed a **legitimately newer** package (catalog 32.0.15.9595 > installed 32.0.15.9186), after downloading 1.1 GB for it, on two separate legs. Two rules came out of it: `_read_text_best_effort` now detects **BOM-less UTF-16** (the `latin-1` fallback never raises, so such a file decodes "successfully" into `P\x00C\x00I\x00…` and silently yields zero ids), and `inf_package_applies` returns `None` instead of `False` when **not one** extracted id sits on the device's own bus (device is `PCI\…`, ids are all `HDAUDIO\…` ⇒ we did not read the INF that matters). That bus test is what keeps the Clevo-Realtek case working — there the device *and* the INFs are both `HDAUDIO\`, so the veto still fires. Both functions log per-INF id counts, because "which INF did we actually read?" is the only question that could have settled this from the field log.

**Catalog cab downloads get 3 attempts, not one** (2026-07-27): these payloads are hundreds of MB (a GPU package is 1.1 GB), so a mid-transfer `[WinError 10054]` ("connection forcibly closed by the remote host") is ordinary, not exceptional — in the field one killed the NVIDIA download after 18s and it was booked as a permanent failure, while the identical URL came down fine on the next leg. Retries pause 3s and **delete the partial file first** (same reasoning as the stresstools.zip rule: the leftover eats exactly the disk the retry needs), and each attempt logs its number and the final byte count. **The attempt loop covers download + size check + expand + INF-presence, not just the download** (2026-07-28, field log from the dev box): a server can close the connection early *without* an exception — `http.client` returns a short read silently on chunked reads — so the NVIDIA cab arrived as 139 MB of 1,221,644,925 bytes and was logged as `Letöltve … 1. próbálkozásra`; `expand` then failed with rc=1, **which nothing checked**, and the failure surfaced as the misleading permanent error "nincs .inf a csomagban" while the retry designed for exactly this never fired. Hence: (a) the received size is compared to `Content-Length` and a short file is a failed attempt; (b) an `expand` rc≠0 or an INF-less tree is also a failed attempt (corrupt cab → delete cab + ext dir, re-download), not a terminal error. The catalog `pnputil /add-driver` call passes `ok_codes=(0, 259, 3010)` — 259 (no-op/up-to-date) and 3010 (reboot required) are expected outcomes the code already branches on, and they produced 4 false WARNINGs in an otherwise clean field run. `.msu` links go through `wusa /quiet /norestart` (offline: `dism /Add-Package`), `.exe` links are skipped with a clear message (never silently run an unknown installer). **Multi-INF packages: the unused INFs are unstaged right after install** (`_cleanup_unused_staged_infs`, 2026-07-28, field-seen on the dev box): `pnputil /add-driver <dir>\*.inf /subdirs /install` stages EVERY INF in the package whether or not any present device matches it, and one Razer catalog cab carries the whole Razer product line as separate INFs — a single AutoFix run inflated the machine from 19 third-party packages to **219** (measured: 201 staged `rz*` INFs, none bound to any device). The pnputil output tells each INF's fate per block: an INF with an `installed on device` / `up-to-date on device` line is in use by a present device and **stays**; the rest are deleted with a plain `pnputil /delete-driver` (no `/uninstall`, no `/force` — if anything does use one, pnputil refuses and it stays, which the logic tolerates). Runs only for multi-INF packages (a single-INF no-bind is the bind-check's job) and never when the install requires a reboot (binding settles at next boot — same principle as the bind-check exemption). pnputil still enforces signature + INF applicability, but catalog matching is inherently less precise than WUA's server-side evaluation: it's the B-plan for machines where the WU Agent is broken, not full parity.
- **Persistent no-bind memory (`catalog_no_bind.json` in `_app_data_dir()`, 2026-07-28)**: the chain-scoped `catalog_no_bind` list in `autofix_stats.json` dies with the chain, so the manual scan run right after a finished AutoFix re-offered — **pre-selected** — the very packages the chain had just proven don't bind (field log, 2026-07-28: 4 of the 5 manual-scan catalog hits were exactly the chain's no-bind list: Clevo-Realtek audio, Razer USB composite, AMD ISA bridge, NVIDIA 32.0.15.9595 — and the user reasonably read that as "AutoFix left drivers uninstalled"). `_install_catalog_sync` now records every no-bind/veto item (key: `(pnp_id, wu_title)`, with reason + date) into the persistent file via `_no_bind_record`, and `_catalog_search_collect` marks matching hits `prev_no_bind` — the UI shows them **unticked** with a `↷ korábban nem vette át az eszköz` badge. Three deliberate limits: it only *marks* (the user can still tick and retry — a wrongly recorded package must stay reachable); the AutoFix rounds do **not** consult it (a fresh chain deletes+reinstalls drivers, so re-trying there is correct, and its own stats list already prevents within-chain repeats); and a later install that the bind-check **verifies** as taken removes the entry (`bound_ok` → `_no_bind_record` removal), so the file can't go stale-forever. A *newer* catalog release has a different title, so it is never masked by an old entry.
- **"Vendor driver instead of the Windows generic one" (`wu_core.mark_generic_replace_candidates` + the `generic_replace` flag; used by BOTH the manual scan and AutoFix)**: the WU Agent never offers a replacement for a device Windows considers fine, so a machine can finish a flawless AutoFix chain with its onboard audio on Microsoft's generic `hdaudio.inf` and its NIC on the inbox driver — while the chip vendor's own package sits in the Microsoft Update Catalog (measured 2026-07-24, ASRock B450M Pro4: Realtek MEDIA 6.0.9992.1 and Realtek Net 10.79.50.1003 both present in the Catalog, zero offers from the WU Agent). Devices whose current driver is inbox (`_is_inbox_driver`) are therefore marked `generic_ok` and fed to the Catalog engine alongside the error-coded ones — the manual scan lists them with a `🏭 most Windows alapdriver → gyári elérhető` badge (pre-selected, the tech can uncheck), the AutoFix closing round installs them automatically. Rules that must not be softened:
  - **For a marked device the version comparison is SKIPPED entirely.** An inbox driver's version is the Windows build (`10.0.26100.8457`) and the vendor's is its own scheme (`6.0.9992.1`), so the generic always looks "newer" and the better driver would always lose. Same trap the WU path already handles in `_filter_wu_downgrades`. This cannot loop: after a successful install the device runs on `oemNN.inf` with a vendor provider, so `is_generic_replace_candidate` no longer marks it (and `added_zero` already guards the AutoFix reboot loop).
  - **Candidate selection has NO class filter** (2026-07-28, explicit user decision — "ITT IS MINDENT KERESSEN, kivéve amit checkboxszal nem engedek"). It used to carry both a 16-entry class whitelist (`GENERIC_REPLACE_CLASSES`) and a class blocklist (`GENERIC_REPLACE_BLOCKED_CLASSES`); **both constants are gone**. What killed them was an asymmetry nobody could defend: a printer / keyboard / USB controller sitting on a Windows inbox driver was never asked about here, while the *same* device on a vendor driver was picked up fine by the deep scan — i.e. a device got no better driver *because* it was on a worse one. What remains is **only** the two checkbox-gated risk classes, exactly as in the WU path and the deep scan (`is_generic_replace_candidate(dev, inst, allow_storage=, allow_firmware=)`; manual scan passes True/True with the red badge, AutoFix passes the dialog's values). **The bus-enumerator INF blocklist and the vendor-coded-HWID requirement were removed from this round too** (same day, same decision: "menjen ki minden driver, mindenre keressen, maximum nem talál"). Measured live on an Intel Q170 box: candidates went 6 → 66, the round took **6.9s on 10 threads**, and it found **two genuinely new packages the old filters had been hiding** — `Intel - System 11.7.0.1019` on a `machine.inf` "Motherboard resources" node and `Intel - System 9.21` on the HD Audio *controller*. So the old belief that these devices "have no vendor driver at all" was simply wrong for chipset nodes. If this round ever gets slow, the fix is more threads or a result cache — **not** a new device filter. **Consequence to keep in mind: with the storage checkbox ON, this branch can swap the inbox NVMe/AHCI driver for a vendor one, and `_verify_generic_replacements` cannot catch that failure** — it surfaces at the next boot. That is the informed trade the checkbox exists to offer (its warning text names recovery media); it is not a reason to reintroduce a class ban. **Processor is a measured non-candidate, not a banned one** (2026-07-28, live query): a CPU enumerates as `ACPI\GenuineIntel_-_Intel64_Family_6_Model_94` and the Catalog returns **0 rows** for it (and for `ACPI\ACPI000C`), while the PCI chipset device on the same machine returned 25 — so the AMD/Intel "chipset driver" reaches the box through its PCI devices (rounds 1 and 4), never through the processor node. Relaxing `_VENDOR_HWID_RE` to admit `ACPI\` would buy network round-trips and nothing else. **Display is NOT excluded** (and the code comment claiming it was is gone as of 2026-07-28): there is no class list left to exclude it from — this branch only ever runs on a device *currently on an inbox driver*, i.e. a machine stuck on the Microsoft Basic Display Adapter, where the "the vendor card is a better source" argument has nothing to work with (AMD/Intel are link-out only and the NVIDIA check runs in the manual scan alone). On a machine already on a vendor GPU driver the device is not a candidate at all, so the vendor cards keep their monopoly exactly where it matters.
  - **Every replacement is verified and rolled back if it fails** (`_verify_generic_replacements`, runs after the batch): the published `oemNN.inf` names are captured from the pnputil output, the devices' `ConfigManagerErrorCode` is re-read once the PnP stack settles, and any device that went error-coded gets its freshly installed package deleted + a rescan, at which point Windows re-binds the inbox driver automatically. **Error code 0 alone is not success** — it also re-reads the device's INF, because a package can install cleanly while the device stays on the Microsoft driver (field 2026-07-25: the run printed `✅ gyári driver működik` for the Realtek audio and, minutes later in the same summary, correctly listed that device as still on `hdaudio.inf`). Still-inbox after install is reported as a warning, not a success, and nothing is rolled back (the generic driver never left). A device that vanished from the present-device list is reported but **not** rolled back (typically an unplugged USB device — don't discard a good driver over a query miss). This "try it, verify, revert" net is only sound because the inbox driver never leaves the machine, which is exactly why the storage exclusion above is not negotiable.

### AutoFix extras & reporting

- **AutoFix extras on top of the shared core (`app/gui/autofix.py`)**: per-UID `attempt_counts` allows ONE retry of a failed install before permanent exclusion (successes drop out server-side via `IsInstalled=0`; the old first-offer-permanent-exclusion turned one transient download error into a permanently skipped driver); after the WU rounds a **catalog closing round** runs `_catalog_search_collect` + `_install_catalog_sync(task_id='autofix')` on still-error-coded devices (the AutoFix twin of the manual hybrid top-up — before this, a device WU had nothing for stayed broken even when the Catalog had a driver); the no-internet rescue restores the saved Net-driver backup (the nicpack.zip last-resort branch was removed 2026-07-28, explicit user decision — the failure message recommends the shop's USB-RJ45 adapter instead); per-leg install counts persist in `<app_data>\autofix_stats.json` (legs are separate processes) and the final leg emits a summary (`_emit_autofix_summary`: chain-total installs + **packages that never came back** + remaining error-coded devices) then deletes the stats file (leg A also clears it so a stale chain can't pollute the next run). **The "never came back" report (`_emit_missing_packages`) is mandatory, not cosmetic**: AutoFix deletes every third-party package assuming WU will restore whatever the machine really uses, and that assumption is sometimes false — field-seen (2026-07) `vigembus.inf` (ViGEmBus, a driver installed by a *user application*, which WU does not carry at all) and `amdafd.inf` (its `pci\ven_1002&cc_040300` generic class HWID never matches a present device, so the pairing can't find it) both vanished permanently and silently. We cannot reinstall them (there is no source), but the shop must know they're gone. The delete phase writes the pre-deletion package list to `pre_packages` in the stats file, and the comparison keys on the **original** INF name (`oemNN.inf` gets renumbered on reinstall). Read `pre_packages` *before* `_autofix_stats_total_and_clear()` — that call deletes the file. **The report splits into three buckets, and that split is load-bearing**: a bare "this INF name is gone" list misleads badly — measured 2026-07-25 it flagged 12 packages, of which `nv_dispi.inf` was simply superseded by `nvle.inf` (same vendor, same class) and 11 Razer packages were replaced by one generic `rz00b9dev.inf` while the mouse stayed plugged in and working. So: *lecserélődött* (same provider **and** class present now), *a gyártó másik csomagja* (same provider, other class), and only the rest is a real disappearance — which is the only bucket that gets the "plug the device in / reinstall the program" advice. **The two benign buckets are screen-capped at 15 items** (`BUCKET_SCREEN_MAX`, 2026-07-28): the first post-bloat run classified 175 ex-Razer INFs as *lecserélődött* and the item wall scrolled every useful summary line off screen; above the cap one line says how many more there are and the full name list goes into the log (the delete phase names every package anyway). The real-disappearance bucket is deliberately never capped — that is the actionable list.
  - **Deleting EVERY third-party package is the whole point of AutoFix — never "improve" it into selective deletion** (explicit user decision, 2026-07). This is a repair-shop tool run on machines whose drivers are already bad; the design is *strip everything, let WU put back clean current drivers*. So a package disappearing is NOT a bug to fix by protecting the package, and no "skip drivers that look important / are in use / have no WU match" filter may be added. The only opt-out is the printer checkbox (see Printer protection 2.0), which the user drives. The single legitimate follow-up is **reporting**: `_emit_missing_packages` must state the two real causes — (1) **the device was not plugged in during the fix**, so WU could not offer a driver for it (WU and `_match_wu_updates_to_devices` only ever match *present* hardware: a disconnected BT dongle / controller / printer loses its driver and cannot get it back automatically), (2) it was an application-installed driver WU never carries — and must tell the shop the actual remedy: plug the device in, then run a scan in "Driver Keresés és Telepítés". Field-confirmed on the 2026-07-24 run (`rtkfilter.inf` Realtek Bluetooth + `sie_usb_device.inf` Sony, both for unplugged devices); the old wording blamed WU ("a Windows Update nem ismeri") and offered only "reinstall the program", which is wrong for case (1).
  - **Failed (non-stalled) package deletions are reported too** (`_delete_third_party_sync` collects them via `drivers_core.delete_succeeded` and lists them): a `pnputil` refusal like "at least one device is currently using the specified INF" used to be dropped on the floor while the phase still printed a clean `✅ Driverek eltávolítva` — the same silent-false-success class of bug as the Build 218 `0xC0000142` case. It is not an error (the chain carries on), it just must not be invisible.
  - **The closing summary also reports what stayed on a Windows inbox driver** (`_emit_driver_health`, 2026-07): the quietest failure mode is a device that ends the chain error-code-free on Microsoft's generic driver because neither WU nor the Catalog had a vendor package (field-measured on an ASRock B450M: onboard audio + LAN both generic after a flawless chain). **The report's filter is deliberately NARROWER than the search's, and they are now separate functions** — do not re-unify them. Until 2026-07-28 the list was "exactly `is_generic_replace_candidate`", which was correct while that predicate still carried a class whitelist + bus-INF blocklist + vendor-HWID test. That same day those three filters were removed *from the search* (the governing rule: ask the Catalog about everything), and the report — sharing the predicate — silently inherited the widening: the field run printed **`🏭 87 eszköz Windows-alapdriveren maradt`** (PCI bridges, DMA controller, system timer, WAN Miniports) against only `ℹ️ További 5 eszköz … és ez így HELYES` — the exact inversion of what is useful, and the same 42-of-which-40-noise failure an earlier measurement had already shown. The two questions genuinely differ: *"is it worth asking the Catalog?"* is yes for everything (a miss costs seconds), while *"does the tech have a TODO here?"* is only yes where a vendor driver can exist at all. `_health_report_worth_listing` (in `app/gui/autofix.py`, report-only) applies two tests: `is_specific_hwid` (a type-coded ID like `ACPI\VEN_PNP&DEV_0100` has no vendor package by construction) and `wu_core.HEALTH_REPORT_SKIP_INFS` (Windows bus/input/software-device INFs). **`hdaudio.inf` and `monitor.inf` are deliberately NOT in that skip list** — a chip on Microsoft's generic audio driver and a "Generic PnP Monitor" are the two most actionable findings the report exists for (the monitor case doubly so: the vendor monitor INF is what supplies the factory ICC profile that `colorprofile_core`'s reset assumes is there). Measured live on the dev machine after the fix: 98 devices → 71 on inbox drivers → **3 listed**, all three real (BenQ monitor on `monitor.inf`, HP LaserJet on `wsdprint.inf`, Realtek ALC221 on `hdaudio.inf`). Everything else on an inbox driver is reported as a single count.
  - **`🎉 MINDEN LÉPÉS KÉSZ!` is only emitted when no further leg is chained** (it now reads `EZ A KÖR KÉSZ!`): it used to print at the end of every install leg, immediately followed by a reboot, which reads as "finished" plus an unexplained restart.

### Kijelző & Színkezelés view (`app/gui/display.py` + `app/display_core.py`)

GUI-only view added 2026-07-31 on explicit user request, because Windows 11 scatters these settings across three places (Settings > Display > HDR, the legacy Color Management control panel, the Store-only HDR Calibration app) and none of them answers the two questions the shop actually has: *what can this panel really do*, and *is the machine's colour management even intact*. Every API below was probed on real hardware before a line of the view was written (AOC AG276QZD2 QD-OLED, DisplayPort, RTX 3060) — the captured sample lives in the `display_core.py` module docstring, and it is what the parsers were built against.

- **HDR is toggled through DisplayConfig, and the RETURN CODE IS NOT THE SUCCESS TEST — the read-back is.** `set_hdr` tries `DISPLAYCONFIG_DEVICE_INFO_SET_HDR_STATE` (16, Win11 24H2+) first and falls back to the older `SET_ADVANCED_COLOR_STATE` (10) **only if the state did not actually change**, because the old call can enable WCG instead of HDR. Measured live: type 16 flipped the panel to `activeColorMode=2`, 8→10 bits, and back again cleanly. The struct `size` fields must match Windows' definitions exactly — a wrong size makes `DisplayConfigSetDeviceInfo` return 0 while doing nothing, which is exactly the silent-false-success class this project keeps getting bitten by. That is why the verdict is always "did the re-read change?".
- **Read both advanced-colour APIs, prefer the new one, never rely on only one.** `GET_ADVANCED_COLOR_INFO` (9) exists on every Win10/11 and gives supported/enabled/bits/encoding; `GET_ADVANCED_COLOR_INFO_2` (15) exists from Win11 24H2 and additionally separates **HDR from WCG** (`hdrSupported`/`hdrUserEnabled`/`wcgSupported`/`wcgUserEnabled`) and reports the active colour mode. `read_hdr_state` fills from the old one and then overwrites with the new one when available, so an older Windows still renders a complete card instead of an empty one.
- **The nit values come from the EDID's CTA-861 HDR Static Metadata block, and they are the MANUFACTURER'S CLAIM, not a measurement** — the UI says so in as many words. Software cannot measure luminance without a colorimeter, and promising otherwise would be the one thing a shop tool must not do. Decoding is `nits = 50 * 2^(raw/32)` for peak and frame-average; the minimum is derived from the peak. Measured on the dev panel: peak 1015, frame-average 254, black 0.0006 nit — textbook QD-OLED.
- **A monitor has SEVERAL EDID entries in the registry and only one of them is the real one.** Live measurement found three `DISPLAY\AOCA610\…` instances for one physical panel: two 128-byte stubs with no CTA extension (⇒ no HDR data at all) and one 384-byte full EDID. `collect_edids` therefore keeps the **longest** EDID per instance key, and `match_edid` resolves the DisplayConfig device path (`\\?\DISPLAY#AOCA610#5&…&UID28931#{guid}`) to `AOCA610\5&…&UID28931`, falling back to the model's largest EDID when the exact instance is absent. Matching on the model alone, or taking the first entry found, would silently report "this monitor has no HDR data" on a monitor that does.
- ****The calibration switch lives in `ICM\Calibration`, not in the `ICM` root** — my first cut of `calibration_management()` read the root and therefore returned `None` on a machine where the value was sitting at 0 one key deeper, i.e. it was blind to precisely the state the view exists to surface (`colorprofile_core` has always written the correct path). It now reads **both** locations and a 0 anywhere wins over a 1 elsewhere: a missing value must never be reported as "fine" while the other location says otherwise. `set_calibration_management(enabled)` writes both values, and **both directions are legitimate** (explicit user decision): 1 is the Windows default and merely *permits* a profile's gamma curve to load (it enables nothing by itself), while 0 is a deliberate lock used on a wide-gamut OLED whose owner wants the native, unmanaged picture and wants to be sure nothing — an update, a vendor tool, another app — can load a gamma ramp behind their back. The view therefore offers a toggle with the current state shown, not a one-way "repair" button.
- `registered_profiles_report` exists because of a real, invisible breakage found on the dev box during this work.** `HKCU\…\ICM\RegisteredProfiles\sRGB` pointed at `srgb_to_gamma2p2_300_mhc2.icm`, a file some third-party HDR tool had left registered and then deleted. Consequence: **every** `mscms` call on that machine returned `ERROR_FILE_NOT_FOUND`, and no Windows UI mentions it anywhere. The view detects it, names the exact registry values, and `repair_registered_profiles` removes **only** entries whose file is provably missing (intact ones are never touched, every removal is logged by name at WARNING first). Windows falls back to its own built-in default, so the removal is the repair, not damage.
- **The view reports the MONITOR's driver (`monitor_driver`, `generic_monitor`), because "what is the factory state?" has no single answer.** On a monitor running the generic `monitor.inf` there is no factory ICC at all, so a linear ramp genuinely *is* the out-of-box state (measured: the dev box's AOC is `Generic PnP Monitor`). On a monitor that has a vendor INF, that INF installs **and associates** a factory ICC — there the out-of-box state is *not* linear, and a chain that stripped the vendor monitor package took the profile with it. Note this second path is **not** `colorprofile_core`: the ordinary third-party driver deletion removes the monitor's `oemNN.inf` too, and that is correct and must stay. The remedy is to get the vendor monitor driver back (Monitor is in the driver search since 2026-07-27), not to weaken the deletion.
- **The GPU gamma ramp is read and drawn, because it is the only DIRECT fact about the colour path.** `read_gamma_ramp` opens a DC on the specific display (`CreateDCW` with the GDI name, not the desktop DC — on a multi-monitor box each output can carry a different ramp) and calls `GetDeviceGammaRamp`. A linear ramp proves nothing is correcting the signal, whatever the profile list says; a modified one proves something *is*, even when no association is visible. The view therefore shows a LINEÁRIS/MÓDOSÍTVA badge, the max deviation from linear, and a 17-point SVG curve per channel against a dashed reference — a badge alone would not say *which way* it deviates. `GAMMA_LINEAR_TOLERANCE` is 64/65535 (~0.1%), not 0, because driver rounding makes an untouched ramp jitter by a few units; measured on the dev box an untouched ramp gives exactly 0. This is also what settles "did my change take effect?" questions: disabling calibration management does not clear an already-loaded ramp — that survives until the next logon/reboot, and the box is where the technician sees it actually go linear.
- **Count the association VALUES, not the keys** — the same lesson `colorprofile_core` already records: the `ProfileAssociations\Display\{GUID}\NNNN` subkeys are mostly empty containers and the profile is a *value* inside them. `_read_assoc_branch` walks down to the values and handles both `REG_SZ` and `REG_MULTI_SZ`.
- **Profile association is written STRAIGHT TO THE REGISTRY, never through mscms** (solved 2026-07-31 after three failed attempts). Every association API is a silent no-op on this Windows 11: `WcsAssociateColorProfileWithDevice` returns TRUE and writes nothing (elevated and not, system and per-user scope), the matching disassociate then reports `ERROR_PROFILE_NOT_ASSOCIATED_WITH_DEVICE`, and the legacy `AssociateColorProfileWithDeviceW` returns FALSE with no error set. Removing the stale `RegisteredProfiles` entry did **not** change this — that hypothesis was measured and killed. What works: write `ICMProfile` (REG_MULTI_SZ) + `UsePerUserProfiles`=1 to `HKCU\…\ICM\ProfileAssociations\Display\{class-GUID}\{instance}`, where both trailing components come straight out of the monitor's `DeviceID` (`MONITOR\AOCA610\{4d36e96e-…} 3`). Verified end to end: Windows' own Color Management control panel immediately showed the profile with **(default)** and "Use my settings for this device" ticked. `InstallColorProfileW` is the one mscms call that does work, so profile *installation* goes through it. If anyone ever moves this back to the API, the acceptance test is exactly that control-panel check — a TRUE return proves nothing here.
- **Still NOT in this view:** ICC generation and the guided nit test.
- The Windows-side tools (`colorcpl`, `dccw`, `ms-settings:display-hdr`, the Store HDR Calibration app) are reachable as **link-outs**, and `open_windows_color_tool` only ever runs commands from the `WINDOWS_COLOR_TOOLS` table — the key coming from JS is looked up, never executed, so the frontend cannot be talked into launching an arbitrary program.

### AutoFix: two standing product decisions (2026-07-31)

- **The AutoFix must not touch colour profiles in any way.** See the `app/colorprofile_core.py` bullet for the evidence; the short version is that the *same* reset improved one machine and wrecked another, so it is the technician's call, made in a view that shows what it is doing — not a silent side effect of a driver fix. `app/gui/autofix.py` and `app/cli/autofix.py` both carry an explicit comment at the old call site.
- **The closing Windows Update pause is `AUTOFIX_WU_PAUSE_DAYS` = 3650 days (~10 years), not 7** (`app/wusettings_core.py`). The shop hands machines back with WU not starting on its own: the fix has just installed a coherent driver set, and the worst outcome is Windows overwriting it days later. Note what this is and is not — it is a **pause**, not a disable, so the customer resumes it with one click in Settings > Windows Update; security updates are not permanently cut off. All three AutoFix pause sites use the constant, so the value is changed in exactly one place.

### Background task concurrency

- **Background task concurrency (`DriverToolApi` only, `app/gui/base.py`)**: long tasks run via `self._safe_thread(task, target)` — a single `self._task_busy` gate rejects a second concurrent task (shared state: `_cancel_flag`, `hw_updates_pool`), and `_cancel_flag` is reset *only after* the busy-check passes (never reset it in the calling method — a rejected call would clear a cancel-in-progress). `start_hw_scan()` uses its own `_hw_scanning` flag + emits `hw_scan_result` on every exit path, but still participates in `_task_busy`. Individual stress-tool launches bypass `_task_busy` deliberately (narrower `_stresstools_download_lock` guards the shared-ZIP step); `load_drivers()` also bypasses (harmless read-only refresh); `stop_stress_tests()` bypasses (must work mid-task).

- **Stress-test tools — admin-elevated launches (HWiNFO64)** (`app/gui/stress.py`): `_launch_stress_exe` tries `subprocess.Popen`; on `winerror == 740` falls back to `ShellExecuteExW` + `SEE_MASK_NOCLOSEPROCESS` (struct in `app/win32.py`) to get a real hProcess → PID. **Do not "simplify" to plain `ShellExecuteW`** — it returns no PID, which used to silently no-op HWiNFO64's automation/positioning/kill (field-diagnosed via debug log). If ShellExecuteExW returns no handle (UAC dismissed), automation is skipped for that run — the name-based kill sweep exists for that case.
- **Stress-test tools — unattended input automation** (`app/gui/stress_automation.py`, sequences in `app/stress_defs.py`); per-tool Win32 techniques discovered on real hardware — do not regress:
  - *Linpack*: **`SendInput`-simulated real keystrokes** into its console — NOT `stdin=PIPE` (broke launch with `CREATE_NEW_CONSOLE`). **Prompt-verified**: `_read_console_screen()` (AttachConsole + `CONOUT$` + `ReadConsoleOutputCharacterW`) polls until the expected prompt substring appears (60s/step) — never type blind on a timer. `Linpack.exe` is a Bat2Exe-wrapped `.bat`: menus read with `choice` (ONE key, no Enter), run-count with `set /p` (line + Enter) — hence the per-step needs-Enter flag in `LINPACK_PROMPT_SCRIPT`; a stray Enter after a `choice` menu leaves CR in the buffer, the next `set /p` reads empty, and the batch dies silently ~1s after the RAM answer (the long-mysterious field crash). v1.1.8 flow: `2` → RAM option → `10000` → `Y` → `N` (app manages power) → `N` (HWiNFO runs) → Enter. RAM option from `_pick_linpack_ram_option()`: largest option fitting *total* RAM (`_get_ram_gb()`, rounded up) **and** *available* RAM minus ~1.5GB headroom (total-only pick page-thrashed a 12GB box). `SetForegroundWindow` is verified via `GetForegroundWindow()` re-read — Windows silently refuses foreground-stealing.
  - *FurMark / Prime95 / HWiNFO64*: **`BM_CLICK` via `PostMessageW`** — not coordinate clicks (DPI/position-immune, no focus needed) and deliberately NOT `SendMessageW` (blocks until the handler returns; FurMark's button opens a *modal* CAUTION dialog → the "GO" step could never run; field log: stuck 50s). Sequence steps support localized label alternatives (`['Indítás', 'Start']`), `skip_if_found` (Prime95's GIMPS welcome only on first launch — `prime.txt` `StressTester=1` afterwards), `optional`+`timeout` (HWiNFO's post-Start update notifier, dismissed via `Bezárás`/`Close`; `HWiNFO64.INI` `CheckForUpdate=0` suppresses it at source, the step is the net), and `exact` (short labels like `OK`/`Igen` would substring-match Hungarian `...ok` text). `_normalize_ctrl_text()` strips accelerator `&` **and collapses whitespace runs** — real texts include `L&3` and `Just  &Stress Testing` (double space); each alone broke Prime95 in the field. Steps are located with `_find_pid_window_with_child_text()` (60s poll), not `_find_window_for_pid()` (largest-window logic misses small dialogs). The *last* step is verified by `_verify_final_click()` (button must disappear; retries with PostMessage then bounded `SendMessageTimeoutW` 3s).
  - *Console apps* (`_find_console_window_for_pid`): console windows belong to hidden `conhost.exe`, so PID-based `EnumWindows` never finds them — AttachConsole/`GetConsoleWindow`/FreeConsole instead; these mutate process-global state, so every call is serialized through `self._console_attach_lock`.
  - **A Linpack prompt's timeout is a *stillness* clock, not a total budget**: `_auto_answer_console` restarts the `STRESS_STEP_TIMEOUT` countdown on every console-screen change (`_console_screen_is_progressing`), with `CONSOLE_PROMPT_MAX_WAIT` (900s) as the absolute ceiling. On a fresh/cloned Win11 24H2+ the Linpack launcher notices WMIC is missing (it became an optional feature) and **installs it itself via DISM** — a percentage bar crawling for minutes, which blew the fixed 180s cap and aborted the automation under a perfectly healthy program (field log, 2026-07: aborted at `[= 37.8% =]`, then the second run completed in 4.4s because WMIC was by then installed). While the screen is redrawing, the program is working — only true stillness counts as a hang. The same field case exposed a second trap: that WMIC notice ends in a bare `Press any key to continue . . .` **before the menu**, so the console isn't slow, it's *blocked* — our expected prompt would never arrive on its own. `_console_is_blocked_on_keypress` detects a keypress-wait marker in the last 3 screen lines that is **not** the prompt we're currently waiting for, and after `CONSOLE_UNBLOCK_AFTER` seconds of stillness sends one Enter (max `CONSOLE_UNBLOCK_MAX` times). Both guards are needed: the stillness clock alone would still have timed out at the pause.
  - **Window layout waits for the real main window** (`_find_main_window_for_pid`, `STRESS_MAIN_WINDOW_WAIT`/`STRESS_SPLASH_TITLE_MARKERS`): HWiNFO64 spends 20–60s detecting sensors while showing only an "Elemzés…" dialog and no visible main window. Plain `_find_window_for_pid` (largest visible titled window) therefore either found nothing at all ("nem található ablak a pozicionáláshoz") or laid out the tiny splash box into the bottom-right quadrant — both field-seen in the same session. Linpack still goes through `_find_console_window_for_pid` (conhost owns its window).
  - Poll timeouts are deliberately long (`STRESS_STEP_TIMEOUT = 180` in `app/stress_defs.py`, shared by dialog search, console-window search and every Linpack prompt) and `start_stress_tests()` staggers launches by 3s — a loaded machine can take ~a minute to show a dialog even on strong hardware (real capture: FurMark GO at 56s — the old 60s cap was nearly exceeded there, and slow dual-core/HDD machines DID exceed it). Err long, not short.
  - **Slow-machine hardening (2026-07)**: (a) Linpack typing is focus-dependent (SendInput goes to the FOREGROUND window) — after every typed answer the console screen is re-read and must CHANGE; if not, focus is re-taken and the answer retyped (max 3 rounds), with a fresh screen re-check before each retype so a slow redraw never causes double input. (b) `_auto_click_sequence`/`_auto_answer_console` return True/False; `_launch_stress_exe(result_sink=, result_key=)` collects per-tool outcomes and the `task_complete` status names the tools whose automation did NOT finish ("Kézi beállítás kellhet: ...") — process-started is no longer reported as full success. (c) The automation-join ceiling is 600s, and if any automation thread is STILL alive at the ceiling, window layout/minimize is SKIPPED entirely (positioning mid-automation steals focus from Linpack typing and minimizes unanswered dialogs — the old fixed-30s-timer field bug).
  - The three long-standing field failures (Prime95 welcome-skip + `&`-matching, FurMark SendMessage deadlock, Linpack v1.1.8 answers + stray Enter) were root-caused with live repros (2026-07) and verified by confirming actual load. For new field reports: grep `STRESSTOOLS-DEBUG` first, prefer adding logging over guessing timing fixes.
- **Stress-test tools — diagnostics**: every Win32 call in the automation path has its return value checked and logged (`_send_unicode_char`/`_send_vk` return whether SendInput injected). `_debug_dump_pid_windows(pid, context)` enumerates every window+child for a PID on any "not found" path. - **Stress-test tools — post-launch window layout** (`_position_stress_windows` in `app/gui/stress_automation.py`): runs only after **all automation threads finish** (each `_launch_stress_exe` appends its thread to `thread_sink`; `start_stress_tests` waits with a 240s ceiling + ~3s settle) — a fixed 30s timer used to fire mid-automation. The spec's `Analysis(['driver_tool.py'])` follows the `app/` package imports automatically — no `hiddenimports` needed for new `app/` modules as long as they're reachable through normal imports (a module imported only dynamically WOULD need adding). The spec embeds `icon_drivervarazslo.ico` + `version_info.txt` (keep populated/synced — unsigned exe with stale version info trips Defender) and disables UPX for the same reason. The icon is a 6-image multi-resolution ICO (16/32/48/64/128/256 px, 8-bit) since Build 199 — if it's ever regenerated, keep all sizes (the pre-199 icon was a single tiny image). `build.bat` needs `@echo off` + `chcp 65001`.
- **Run from source**: `python driver_tool.py` (GUI, self-elevates via UAC) or `python driver_tool.py --cli`.
- `DriverVarazslo.spec`, `version_info.txt`, and `dist/DriverVarazslo.exe` are intentionally tracked in git — the exe is what the in-app updater downloads.
