> A CLAUDE.md 2026-10-11 előtti teljes szövegéből **szó szerint áthelyezve**, eredeti sorrendben. A tömör, érvényes szabályok a CLAUDE.md-ben vannak; ha a kettő eltér, a CLAUDE.md a mérvadó, és ezt a fájlt is javítani kell. A szövegben lévő `(#…)` hivatkozások a régi egyfájlos szerkezetre mutatnak: a cél-szekciót `grep`-pel keresd a `docs/terep/` mappában.

## Code layout (refactored 2026-07 from a single 8000-line driver_tool.py)

- **`driver_tool.py`** — thin entry point ONLY: the `BUILD_NUMBER` literal + the `__main__` block (single-instance mutex, UAC self-elevation via `_relaunch_elevated()`, logging setup, GUI-vs-CLI dispatch, WebView2 install offer + watchdog). **The `BUILD_NUMBER = <int>` line must stay in this file, at column 0, forever**: every already-deployed exe's auto-updater downloads *this file* from GitHub and regexes `^BUILD_NUMBER\s*=\s*(\d+)` out of it (and `bump_build.py` edits it here) — moving it to another file would permanently freeze all fielded installs on their current build. At startup the entry point copies it into `app.common.BUILD_NUMBER` (a module attribute defaulting to 0); **all other code reads `common.BUILD_NUMBER`**, never imports it from `driver_tool` (that would re-execute the module and duplicate state).
- **`app/`** — everything else, one file per feature (roughly one per sidebar menu item):
  - `app/common.py` — **2026-09-28 óta itt van a `relaunch_detached` (a program új, önálló példánya: mutex-elengedés, saját `_MEI` mappa, `cmd /c start` - a CLI-váltás ÉS a WebView2/.NET telepítés utáni újraindítás közös útja) és a `gui_attempt_failed_cleanly` (a GUI-őr jelzője túlélt kísérlet után).** Shared plumbing: WebView2 runtime check, `is_admin`, `resource_path` (frozen `sys._MEIPASS` vs `_PROJECT_ROOT`), `_ps_quote`, `_app_data_dir`, `_app_exe_path()` (see below), the command-result helpers used by both `_run`s (`CommandResult`, `CMD_TIMEOUT_RETURNCODE`, `STATUS_DLL_INIT_FAILED`/`spawn_failed` — see Logging), the `_webview_ready`/`_webview_error` events (single instances shared by GUI code and the entry-point watchdog — do not recreate them elsewhere), the `BUILD_NUMBER` holder, and the call-logging layer (`install_call_logging`, see Logging below). **Régi Windows (7/8/8.1) réteg (2026-08-13):** `default_run` (közös minimál futtató azoknak a modul-szintű hívásoknak, ahol nincs API-példány — az updater és a belépési pont használja), `ensure_console` (konzol + `sys.stdout` biztosítása; windowed exe-ben a `sys.stdout` **None**, ott a `print()` magától elszállna), `windows_version`/`is_legacy_windows`, `check_dotnet_framework` (a pythonnet 3.x minimuma **.NET 4.7.2** = Release 461808), `file_version` (ctypes-os fájlverzió, subprocess nélkül), és a **GUI-összeomlás-őr** (`gui_env_signature`/`gui_attempt_begin`/`gui_crash_check`/`gui_attempt_succeeded`) — lásd a [Régi Windows-támogatás](#régi-windows-támogatás-win-7--8--81) szekciót.
  - `app/prereq.py` — **indulási előfeltételek: felmérés, automatikus javítás, döntés a GUI-ról** (2026-08-13, explicit user decision: *"gondolkodj elore milyen problemak johetnek elo es az exe indulas elott oldja meg"*). `collect_environment`/`log_environment` a `[PREREQ]` napló-blokkot adja (Windows, admin, szabad lemezhely, .NET, WebView2 runtime+SDK, pywebview, PowerShell-generáció, TLS 1.2 állapot, pnputil-szintaxis) — ez a blokk teszi egy régi gépről érkező hibajelentést önmagában megválaszolhatóvá. `install_dotnet_framework` letölti (a közös, certutil-ig lemenő letöltővel) és `/passive /norestart`-tal telepíti a .NET 4.8-at; `gui_blocker` mondja meg, van-e olyan hiányzó előfeltétel, ami miatt a felület el sem indulhat. **A TLS 1.2 schannel-beállítást szándékosan CSAK OLVASSA**: rendszerszintű biztonsági beállítás egy ügyfél gépén, újraindítást igényel, és az elsődleges letöltési út (a Python saját OpenSSL-je) amúgy sem függ tőle — de ha egy letöltés a PowerShell/certutil ágon hasal el, ez a napló-sor mondja meg, miért. A modul semmit nem módosít a felhasználó jóváhagyása nélkül.
  - `app/win32.py` — **2026-09-28 óta:** `driver_store_folders` (a csomagok DriverStore-mappájának hash-es neve, `SetupGetInfDriverStoreLocationW`) és `system_uptime_seconds` (`GetTickCount64`, a lánc-idő méréséhez). ctypes structs/constants (SendInput, console screen buffer, `ShellExecuteExW`, `GlobalMemoryStatusEx`, recycle bin, `get_work_area` via `SPI_GETWORKAREA` — the FurMark frame compensation uses it to tell a window frame from a clipped window; the **DisplayConfig (CCD)** structs + info-type constants used by the Kijelző view's HDR handling — their `size` fields are checked against the Windows definitions, so no field may be added or removed). **2026-09-17 óta itt van az ESZKÖZFA-olvasó is** (`enumerate_device_nodes` — cfgmgr32, subprocess és admin nélkül, 0,23-0,38 mp; `read_class_filters`, `read_hardware_identity`, `platform_role`): ez a használat-felderítés ÉS a gép-térkép KÖZÖS forrása, lásd [A gép felépítése](#a-gép-felépítése--melyik-driver-melyik-alkatrészé-2026-09-17).
  - `app/wu_core.py` — the WU scan/install **shared core** (see its own bullet below).
  - `app/stress_defs.py` — stress-test constants: `STRESS_TOOLS`, `STRESS_TOOLS_BULK`, `STRESS_TOOL_ARGS`/`STRESS_FURMARK_LABEL` (see below), `STRESS_KILL_IMAGES`, `STRESS_CLICK_SEQUENCES`, `LINPACK_PROMPT_SCRIPT`, `LINPACK_RAM_OPTIONS`, `STRESS_POWER_SETTINGS`/`STRESS_POWER_REG_KEY`. **`STRESS_TOOL_ARGS` applies to the BULK launch only** (`start_stress_tests`) — the per-tool cards deliberately launch with no arguments at all, so the tech configures the program by hand (standing decision). Today it holds one entry: FurMark starts at **3840×2160 / 8× MSAA / `/xtreme_burning`, `/run_mode=2` (burn-in), with NO `/max_time`** so it runs until the tech stops it (explicit user decision, 2026-07-31 — "ott mehet végtelenig amíg le nem állítom"). **The 4K here is deliberately NOT the benchmark's 1024×768, and the two must not be "unified"**: windowed FurMark renders at most the screen size (see the measurement in the `benchmark_defs.py` bullet), which is fatal for a *measurement* — it would rank monitors — but exactly right for a *burn*, where it simply means "render the biggest image this machine can". Only the MSAA value is imported from `benchmark_defs.py`; the size lives here. It deliberately omits `/log_score`: a stress run is not a measurement and must not append to the score file the Benchmark view parses. Two knock-on rules: `_launch_stress_exe` takes `args=` and passes them on **both** the `Popen` and the elevated `ShellExecuteExW` path (`lpParameters` — otherwise an elevated FurMark would silently start with its own defaults), and `STRESS_CLICK_SEQUENCES['furmark']` lost its `'GPU stress test'` step (with `/nogui` there is no settings window to click) while keeping the `GO` CAUTION-dialog step as **optional, 20s** — the benchmark's own `/nogui` runs are the evidence that the dialog does not appear, but if some version shows it, the stress test must not stall. **`/run_mode=2` + "no `/max_time` means unlimited" is the one part not yet verified on real hardware** — the Geeks3D docs give `/max_time` a 60000 ms default but describe burn-in as running "until the user presses the ESC key"; if a field run ever stops itself after ~a minute, the fix is an explicit unlimited switch (the program's own `startup_options.xml` expresses it as `time_based_benchmark="0"` + `max_time="0"`).
  - `app/benchmark_defs.py` — benchmark constants: `BENCH_TOOLS` (Cinebench R20 + Unigine Heaven + FurMark exe-lookup patterns, searched in the shared `stresstools.zip`), the automated-run constants (`CINEBENCH_CLI_ARGS` — the CLI multi-core flags whose stdout carries the "CB <score>" line; `FURMARK_CLI_ARGS`/`FURMARK_BENCH_TIME_MS` — `/nogui /benchmark /max_time=10000 /log_score`; `CINEBENCH_TIMEOUT_S`, `FURMARK_EXIT_GRACE_S`), the pre-benchmark app-closing constants (`CLOSE_APPS_PROTECTED`, `CLOSE_APPS_WAIT_S`) and `BENCHMARK_API_URL_DEFAULT` (the cloud leaderboard endpoint default). **The FurMark measurement runs at 1024×768 + 8× MSAA + `/xtreme_burning`, windowed, 10s — the load comes from the sampling and the burn-in mode, NOT from the resolution** (explicit user decision, 2026-07-31; `FURMARK_BENCH_WIDTH`/`_HEIGHT`/`FURMARK_MSAA`). Why the resolution is deliberately small: **windowed FurMark cannot render bigger than the screen**, so any nominal above the smallest shop monitor would make the leaderboard rank *monitors* — see the measurement two paragraphs down. Why the load is still enough: 8× MSAA takes the per-frame sample count from 786k to 6.3M, and Xtreme burn-in roughly halves the frame rate on top of that (measured on the dev box's HD 530: 28 → 14 frames in the same 10 s window), so the total is ~10× the old `1024×768`/`0× MSAA` — a modern card lands in the tens of FPS, where the driver/CPU frame-submission path cannot be the limit. The Xtreme mode also matches the shop's manual practice (the FurMark install on the dev box carries `xtreme_burn_in="1"`), and it is a power virus by design: on a weak PSU or a dying card the machine can drop out mid-measurement and produce no result — an accepted trade. (The GUI's neighbouring post-FX switch has **no** CLI flag in FurMark 1.x — only `startup_options.xml` — so it is deliberately not forced into the run; writing that file would also leak into the benchmark's own runs from the same folder.) **The previous generation of this rule — "the settings deliberately mirror the shop's old hand-written FurMark script" (2026-07-29: `1024×768`, `/msaa=0`, `/enable_dyn_bkg=1 /bkg_img_id=2`, on the grounds that the technicians know those FPS ranges by heart) — is fully reversed and must not be reinstated**: the user's instruction was to forget that script entirely. The animated-background flags went with it, and measurement settled the question they were based on: the installed FurMark's `startup_options.xml` has `dynamic_bkg_image="1"`, i.e. the background is animated by default and `/enable_dyn_bkg=1` never did anything — while `/bkg_img_id=2` *did* silently swap the default image 0 for image 2 (this file used to claim 2 *was* the default; it is not). So what is left in the command line is operational only, plus the two load switches: `/nogui /benchmark /max_time /width /height /msaa /xtreme_burning /log_score /disable_catalyst_warning /nomenubar`. Two consequences: leaderboard rows uploaded **before** this change are not comparable (no settings column in the sheet — delete them by hand), and an old/low-VRAM card's driver may silently drop the sample count — hence `parse_furmark_scores` now also parses **`[MSAA=…]`** and a mismatch against the requested value logs a WARNING, exactly like the resolution check. Windowed, **never fullscreen**: a panel that cannot do the requested mode would produce **no result at all**, while a clipped window still produces one.

    **WINDOWED FURMARK NEVER RENDERS BIGGER THAN THE SCREEN — measured, do not re-litigate** (2026-07-31). This cost most of a session, twice, because **FurMark's own UI says otherwise**: its header (`Burn-in test, 3840x2160 (8X MSAA)`) and the `width`/`height` fields of `furmark-gpu-monitoring.xml` echo the *requested setting*, not the rendered image. The only honest source is the `/log_score` score file's `[Resolution=…]`. The decisive run, with the packaged FurMark **1.39.3.0**, on a 1080p monitor, identical settings (`/nogui /benchmark /max_time=10000 /msaa=8`, no Xtreme):

    | requested | `[Resolution=…]` | frames / 10 s |
    |---|---|---|
    | 3840×2160 | `1924x1061` | 13 |
    | 1280×720 | `1264x681` | **28** |
    | 3840×2160 (repeat) | `1924x1061` | 14 |

    Had it really rendered 4K, the 720p request would have produced the *same* frame count; it produced double, and the pixel ratio (2.04 Mpx vs 0.86 Mpx = 2.37×) accounts for it. So the render is the window's **client area**, capped by the display. That is why the nominal size must fit every shop screen: above it, a 4K-monitor machine would render 4× the pixels of a 1080p one under the very same command line — a far worse distortion than anything else in this file. Same lesson as the colour-profile case, and as the 1.19-vs-1.39 flag differences below: what a tool *displays* is not a measurement.

    **Reference measurements — what each switch actually costs** (2026-08-03, Intel HD Graphics 530, 1024×768, 10 s runs). These are the only numbers we have for estimating a future "let's change it to X" request, so use them instead of guessing: MSAA ladder with Xtreme on — `0×` **6.2 FPS**, `2×` 3.6, `4×` 2.1, `8×` **1.3** (clean ~1.7× per doubling, and the score file's `[MSAA=…]` confirmed the requested value every time); Xtreme burn-in costs about **half** the frame rate (2.4 → 1.3 at 8× MSAA); run mode is irrelevant (`/benchmark` 1.3 vs `/run_mode=2` 1.2); the dynamic background is **unmeasurable** (1.3 either way — which is also why the old script's `/enable_dyn_bkg=1` was pointless). **Third case of FurMark's UI contradicting reality, same day:** the user tried to reproduce the app's 1.1 FPS by hand on that machine with `1024x768` + `8X MSAA` + Xtreme set in the GUI, and got **7 FPS**. The ladder identifies it immediately — 7 is the `0×` level (6.2), not the `8×` level (1.3) — i.e. the GUI run did not apply the anti-aliasing despite its header reading `1024x768 (8X MSAA)`, while our CLI runs are backed by two independent proofs (`[MSAA=8]` in the score file *and* the FPS landing exactly on the 8× rung). When a hand-run and an automated result disagree, compare FPS levels against this ladder — never the on-screen caption.

All older shapes are still parsed as fallbacks, and the last entry always wins (the file is an append log). Two extras the same line made possible: the rendered `[Resolution=…]` is compared against the requested size and a mismatch logs a WARNING (see `benchmark_defs.py`), and **FurMark returns the frame count as its exit code** (`returncode=618` next to `[FRAMES=618]`), which is logged as a cross-check that the parsed result belongs to *this* run. Run 1 is the **cold run** (FurMark loading itself, compiling shaders, allocating the larger MSAA buffers) and runs 2–3 are the real measurement, so a background kick during one of them can no longer decide the result. Do not "optimize" this back to one run, and do not replace it with a shorter throwaway warm-up: the second mechanism (transient background load *during* the measured run) needs two real runs. **A machine's FIRST-EVER measurement gets one extra run** (`FURMARK_BENCH_MAX_EXTRA_RUNS`): until the window frame is known, run 1 still asks for the nominal size — it is what *teaches* the frame — so it renders smaller and cannot compete.     - **The leaderboard's dedup key is `machine_row_id(MachineGuid, name)` — the machine AND the typed name, never the bare GUID** (field-proven 2026-07-30, and it cost a real measurement). It also closes a second hole the shop is exposed to: **on a cloned Windows image several physical machines carry the same `MachineGuid`**, so the bare GUID would have had different machines overwriting each other's results too. Key shape: `<guid>|<readable-slug>-<6 hex of the normalized name>` — the slug because a human reads that sheet, the hex because accent-folding + truncation can map two *different* names onto one slug (`Gép 1` vs `gep-1`), which would be the same silent overwrite again; the name is normalized (casefold + collapsed whitespace) first, so a rerun typed with different capitalization or a trailing space still updates rather than duplicating. The refresh now has its own `try` and only logs a WARNING (`core_fetch_leaderboard` swallows its own errors into an `error` key, so this only fires on something genuinely unexpected — which is exactly when a false failure report does the most damage).
    - **The pre-benchmark "close everything" step is graceful-only, and its filter needs the window TITLE, not just the handle.** The run dialog offers to close running programs first (background Chrome/Steam/updaters steal CPU+GPU and make scores low and jittery); on yes, `_close_running_apps_sync` runs `build_close_apps_ps`. Rules that must not be softened: (a) it calls **`CloseMainWindow()` (WM_CLOSE), never `Stop-Process`/taskkill** — identical to clicking the window's X, so an app with unsaved work prompts and *stays open*; those are reported, never forced (a benchmark must not cost the customer their unsaved document); (b) the target filter is `MainWindowHandle -ne 0 **-and MainWindowTitle**` — measured on a live dry run, handle-only also selected **`svchost.exe`** (it has a title-less window), and a WM_CLOSE to a service host can stop services; a real user app always has a title. `CLOSE_APPS_PROTECTED` (shell, our own exe + WebView2, system hosts incl. svchost, and the tech's diagnostic windows: taskmgr/regedit/eventvwr…) is the second line of defence; (c) every attempted close is logged **by name with its window title** at WARNING before it happens, and the survivors are logged too — this is a destructive-ish action on someone else's machine. Verify changes here with the listing-only dry run (strip the `CloseMainWindow` call and the sleep) rather than by closing real windows.
