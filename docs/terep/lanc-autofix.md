### AutoFix — the 3-leg reboot chain

- **`autofix_stats.json` is the chain's only memory across legs** (each leg is a separate process, so nothing else survives a reboot). It lives in `_app_data_dir()`, is written by `_autofix_stats_set/add` and read by `_autofix_stats_get`, and is deleted at the end of the chain **and** in leg A. *(2026-10-11, repó-audit: az írás ATOMIKUS lett — `_autofix_stats_write`: ideiglenes fájl + `fsync` + `os.replace`; az `_add` és a `_total_and_clear` is a közös `_autofix_stats_read`/`_set`-en megy. Előtte minden `_set` `open(p, 'w')`-vel előbb KIÜRÍTETTE a fájlt, és egy olvasási hiba után `data = {}` lett, naplózás nélkül. Egy BSOD/áramszünet az írás ezredmásodperceiben tehát a teljes lánc-memóriát elvihette, a `keep_packages`-szel (a technikus kézi döntéseivel) együtt, és a következő `_set` véglegesen felülírta. Terepen ezt nem mértük, a kódból következik. Most az olvashatatlan fájl ERROR-t ír, és `.corrupt` néven félrekerül. Teszt: `tests/test_field_regressions.py`, `ChainState`. Az alábbi „Six keys" lista történeti: a teljes, mai kulcslista a CLAUDE.md 13. fejezetében van.)* Six keys, currently the complete set — when adding one, add it here too, because "why did the chain do X on the second leg?" is answered from this file:

  | `pre_packages` | delete phase | pre-deletion package list for the "never came back" report |

  | `delete_rounds` | sweep | reboot-and-retry counter vs `AUTOFIX_MAX_DELETE_ROUNDS` |

- **AutoFix resume-after-reboot** (`app/gui/autofix.py`): 3-leg chain. Leg A (fresh start) shows the confirm dialog, pauses WU, schedules a task with `--resume-step1`, reboots. Leg B (a brand new process relaunched by that task) does ghost-device/driver deletion, schedules `--resume-autofix`, reboots. Leg C does the WU rescan/install, looping while new drivers keep installing. **Every reboot uses `shutdown /r /t 0 /f`** — without `/f` the unattended chain can hang forever. **Any Leg-A dialog choice that must affect Leg B cannot be a function parameter** (different OS process): append it as a flag to the scheduled-task `-Argument` string and parse it from `sys.argv` in `GuiBaseMixin.__init__` (worked example: `skip_printer_drivers`/`AUTOFIX_PRINTER_SKIP_CLASSES` in `app/wu_core.py`). **Such a flag must be re-appended by `_schedule_autofix_resume` itself, never by the call sites** (2026-07-27): of the seven scheduling sites only Leg A appended `--skip-printer-drivers`, so from Leg B onward the task was registered without it and the user's choice silently evaporated mid-chain — the resolved-value log line then contradicted itself across legs (`True` in Leg B, `False` in Leg C) on the very field question it was added to answer. It is harmless *today* only because Leg B is the sole deleting leg; the first printer-sensitive step added to the install leg would have taken the wrong branch with no trace. `run_autofix` now parks the resolved value in `self._autofix_skip_printers` and the scheduler appends it (idempotently) for every leg. The scheduled-task PowerShell is an f-string with single-quoted values — always pass exe path/args through `_ps_quote()` or an apostrophe in a username breaks the chain. Further chain mechanics that are easy to break unknowingly:
  - **The resume legs are started by the frontend, not by Python**: the scheduled task only launches the exe with the flag; `GuiBaseMixin.__init__` parses it into `self.resume_mode`/`self.resume_step1`, `get_init_data()` returns both, and **`ui.html` (in the `pywebviewready` handler) calls `startAutoFix(true)` after a 1s delay** when either is set — that's the only trigger. Consequences: (a) anything that stops the GUI from reaching `pywebviewready` (missing/broken WebView2 → CLI fallback, the single-instance mutex, a dismissed UAC prompt) silently ends the chain with no error anywhere except the debug log; (b) the auto-update check is deliberately skipped on resume legs (the `else` branch) so an update can't hijack a running chain; (c) `startAutoFix(true)` passes `skipConfirm`, so no dialog appears — the printer choice comes from argv, not from the JS `skipPrinters` value.
  - The task is `Register-ScheduledTask -TaskName "DriverVarazsloResume" -Force`, trigger `-AtLogOn`, principal `-LogonType Interactive -RunLevel Highest` (interactive+elevated is required — the GUI must be visible and admin).
  - **`-Settings` is mandatory, and its absence silently kills the chain on any laptop running on battery** (field-proven 2026-08-05, Dell Latitude 7400, confirmed by the user: *"IGEN AKKSIROL MENT A LAPTOP"*). Without `-Settings`, `Register-ScheduledTask` takes the Windows defaults, and those are `DisallowStartIfOnBatteries = True` + `StopIfGoingOnBatteries = True` (verified live: `New-ScheduledTaskSettingsSet` prints exactly that) — i.e. **the resume task refuses to start unless the machine is on AC power**. The symptom is maximally misleading: registration succeeds and reports `State: Ready`, the machine reboots normally, and then nothing happens — no error anywhere, and `schtasks /query /tn DriverVarazsloResume /v` reports `Last Result: 267011` (= *the task has never run*). The log is equally silent, because the exe never starts: the giveaway is that the post-reboot session shows **no `--resume-*` argument and `Futtatasi konyvtar: C:\Users\<u>\Desktop`** instead of `C:\Windows\system32` — that is a human double-click, not the task. This stayed hidden for as long as machines sat on the bench with an Ethernet cable *and* a charger; the Wi-Fi mode is what surfaced it, because a laptop tested over Wi-Fi is typically unplugged. The registration therefore passes `New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -StartWhenAvailable -ExecutionTimeLimit ([TimeSpan]::Zero)`: start on battery (the actual fix), do not abort mid-leg if the charger is pulled, catch up if a logon start was missed, and no 72-hour cap on a chain that may sit through a long install. Offline-tested (the generated `-Settings` line is asserted, and its effect verified by building the settings object live).
  - **Leg B must never leave the machine without a scheduled task while it deletes drivers.** It used to *unregister* the task first thing and only register the next one at the very end — everything in between (restore point, ghost removal, the whole third-party delete loop, minutes of work) was an unprotected window. Field-proven (2026-07, Win10 + R9 200): the machine went down mid-delete with 9 packages already gone; no task existed, so nothing resumed, and the user found a half-stripped machine and had to restart the whole chain by hand. Leg B now **re-registers the task to `--resume-autofix` as its first action** (`-Force` overwrites) — deliberately pointing at the *next* leg, not a retry of itself: if the deletion is what killed the machine, retrying would boot-loop, whereas the install leg continues sensibly from whatever state the deletion reached.
  - **The install leg (C) arms the same safety task**, for the same reason — it is the longest and riskiest stretch of the chain (storage/chipset drivers, the poisoned-session territory), and it too used to unregister the task on entry. It is bounded by an `install_leg_starts` counter in the stats file that counts *every* entry (planned reboots and crash resumes alike); above `AUTOFIX_MAX_INSTALL_LEGS + 1` it stops arming, so a machine that never heals reboots at most once more than a normal chain and then stops. The counter dies with the stats file at the end of the chain (and in leg A).
  - **That safety task must be removed on the error/cancel path** (the `except` in `run_autofix`'s worker unregisters it): it exists only for an *unexpected* death. Without that, a user who stops the process — or any leg that raises — would find the machine resuming into the install leg at the next logon.
  - **Running from `%TEMP%` is handled explicitly**: if `_app_exe_path()` is inside `%TEMP%`, leg A copies itself to `%PUBLIC%\DriverVarazslo_Resume.exe` (`.py` from source) and schedules *that* — otherwise the app's own temp-cleanup / Windows can delete the exe between reboots and the task launches nothing.
  - **Every reboot in the chain goes through `_reboot_or_cancel(status)`** — it keeps the 5s grace window but polls `_cancel_flag` twice a second, and on cancel it **unregisters `DriverVarazsloResume` before raising** the cancel exception. The old `time.sleep(5)` + unconditional `shutdown` ignored a Cancel pressed inside that window (field-seen, Build 224: the user cancelled and the machine rebooted anyway), and without the unregister the chain would have resumed at the next logon regardless — a Cancel that only *looks* like it stopped anything. Do not re-inline a bare `shutdown` at a chain step.
  - **A requested update that never gets a `FOUND:` line must be reported** (`wu_core.unoffered_requested_titles`, used by the AutoFix rounds and the manual `_install_wu_api_sync`): the script walks its *own* search results and emits `SKIP:` for everything not in our filter, so **counting SKIP lines is meaningless** — the real signal is a requested title with no `FOUND:`. Field-seen (Build 224): "Telepítendő driverek száma: 3" followed by `TOTAL: 2`, and the third package vanished without a word (the server had started reporting it as installed after the previous round).
  - **The Store-app sync at the very end is a *bounded* synchronous wait — 10 min, then move on** (explicit user decision, Build 228, reversing the earlier fire-and-forget design): `Invoke-CimMethod -MethodName UpdateScanMethod` runs a full Store scan (measured 112s in the field) that updates the DCH companion apps (Intel GCC, Realtek Audio Console), never drivers. It *used* to be a detached `subprocess.Popen` with no wait — but the chain's final leg does NOT reboot, so the user eventually closes the app, and the exit-time `cleanup_zombies()` `taskkill /F /T` kills the whole process tree, so the fire-and-forget child usually never finished. It now runs via `self._run(..., timeout=600)`: `_run` swallows `TimeoutExpired` → `CMD_TIMEOUT_RETURNCODE`, so on the (rare) 10-min overrun we print "the Windows background will continue it" and proceed, otherwise "done". Don't revert it to a detached Popen — the taskkill-on-exit is why that silently lost the sync. **[2026-09-27: a lépés ÁTKERÜLT `app/storeapps_core.py`-ba (`run_store_update_scan`), és ELŐTTE a program most maga telepíti a driverek által KÉRT, de hiányzó Store-alkalmazásokat — a régi hívás csak frissített, hiányzót nem telepített, és a `ReturnValue`-t sem nézte (mindig „kész"-t írt). Lásd [A driver-alkalmazások a Store-ból](#a-driver-alkalmazások-a-store-ból-a-program-telepíti-mert-a-windows-a-fix-után-nem-fogja-2026-09-27-élőben-mérve).]**
  - **The install leg re-chains itself** (this predates the 2026-07 fixes but is easy to miss): when the WU round loop ends it reboots and schedules another `--resume-autofix` leg if anything installed **or** if the round was cut short by the poisoned-session guard (`self._autofix_reboot_pending`, set by `_scan_and_install_wu_sync`) — that is how the packages skipped by the `'reboot'` abort actually get installed, on a clean boot. `AUTOFIX_MAX_INSTALL_LEGS` (10, counted from the `legs` array in `autofix_stats.json`, which survives reboots) is a **high last-resort backstop**, NOT the normal stop: per explicit user decision (Build 228) the chain runs "until a round installs zero new drivers, and *that* is done" — reaching the leg cap only happens on a pathological machine where a fresh package genuinely re-installs every leg. It was raised from 3 to 10 once the real Build-228 cause (an already-staged catalog package counted as "1 installed" every leg) was fixed in `_install_catalog_sync` (the "already exists" no-op above); the catalog closing round is also deferred when a reboot is pending. All three scheduling sites go through **`_schedule_autofix_resume(resume_flag)`** — do not re-inline the `Register-ScheduledTask` block, it used to exist in three copies.
  - **The wedged-PnP delete rule (leg B → leg C hand-off, 2026-07)**: deleting a package can wedge the device stack so that *every following* `pnputil /delete-driver` blocks for **~143s** (Windows' own internal query-remove timeout) — field case: an Intel RST `iastorhsa_ext.inf` extension, which turns a 1-minute delete phase into 45+ minutes. **Every** stalled package (`drivers_core.delete_stalled` — our `DELETE_DRIVER_TIMEOUT`=60s firing, or codes 480/482) goes onto the `pending_deletes` list in `autofix_stats.json`, even when the loop carries on — without that the package is simply never deleted *and* WU then sees it as installed, so it never gets replaced either (field-seen on Build 224: `iastorhsa_ext.inf` silently survived a full chain). On the first stall **plus** a pending reboot, `_delete_third_party_sync` also stops trying, adds the untouched remainder, and returns `'wedged'`. **It must NOT reboot there** (explicit user decision — the delete phase runs in one go, then the leg's normal reboot happens): the leftovers are swept at the *start of leg C* by `_finish_pending_deletes()`, where a fresh boot makes each one take ~0.5s (field-measured). That sweep only touches packages named in the list whose *original* INF name still matches (so a renumbered `oemXX.inf` can never take out a freshly installed driver). **Deletion repeats until it is actually finished** (explicit user requirement): if the sweep wedges again it re-defers the remainder and chains another reboot, but only while it is *making progress* — a round that deletes **zero** packages means they are undeletable (e.g. an in-use printer INF) and no reboot can help, so it gives up immediately; `AUTOFIX_MAX_DELETE_ROUNDS` (3) is the backstop. **When the sweep does finish the deletion, the leg reboots once more before installing anything** — the fresh boot both completes the removals and clears the pending-reboot state that would otherwise send the very first install straight into the `[kód=4]` wall. **`DELETE_DRIVER_TIMEOUT` must stay well below 143s** or it never fires — the first attempt used 180s and was inert.
  - **A failed WU search must never be reported as "everything is installed"** (2026-07-26). `_search_wu_api` returns `None` on failure (300s timeout or a WUA error) and `[]` when the search ran and the server offers nothing — the install leg used to collapse both with `or []`, and the no-matches branch then printed `✅ Szerveren nincs újabb valós illesztőprogram. / Minden elérhető driver telepítve!`. On a machine with a dead WU Agent that is the exact opposite of the truth, and it is what the field log preserved. Keep `wu_search_failed` separate, say the WU did not answer, and point at the catalog closing round plus a follow-up manual scan.
  - **Cancelling inside the delete phase leaves a half-stripped machine and nothing resumes** — the error path deliberately unregisters `DriverVarazsloResume` (a Cancel must not resume), so the loop's cancel branch has to state the count already deleted and tell the tech to re-run the fix. Silence here reads as "Cancel undid it", which is the opposite of what happened.
  - **`powercfg /h off` (leg B) is never turned back on**, deliberately — with hiberboot on, the "reboot" does not fully reinitialize the PnP stack. But it is a lasting, user-visible change on a customer machine, so `_emit_fast_startup_note` *queries* the state at the end of the chain (never assumes it) and says so, with the `powercfg /h on` command to undo it. **Two registry values, not one** (fixed 2026-07-28): `powercfg /h off` clears `HibernateEnabled` (`…\Control\Power`) and does **not** touch the Fast Startup checkbox `HiberbootEnabled` (`…\Control\Session Manager\Power`), which stays `1` but is inoperative — Fast Startup is built on hibernation. The code read only `HiberbootEnabled`, so after a perfectly successful `powercfg /h off` (`returncode=0` in the field log) it concluded Fast Startup had been re-enabled: it logged a false WARNING **and suppressed the user-facing note entirely** — i.e. the one thing the function exists for never happened. Fast Startup is effective iff **both** values are 1. Second rule from the same fix: the note is emitted only when `HibernateEnabled` is `0`, i.e. when our own change is actually visible. If hibernation is back on, the `powercfg /h off` did not stick, and claiming "we turned it off, undo with `powercfg /h on`" would be false in both halves — that case logs a warning and stays silent on screen. Verified offline against all 7 combinations of the two values (including both-unreadable).
  - **A crashed install leg can strand `NoAutoUpdate=1`**: the leg sets that policy for the WU search and removes it in a `finally`, which does not run on BSOD/power loss — and that value disables **all** of Windows Update, not just drivers. `_cleanup_leftover_autofix_policy` (called from `GuiBaseMixin.__init__`, same slot as `_restore_power_after_stress`) removes it at the next start, but only on **evidence it is ours**: not in a resume leg, and a leftover `autofix_stats.json` exists. Never widen that condition — an admin's deliberate policy must survive.
  - Leg A also gates on `_check_internet()` before doing anything (no net → abort with a toast, nothing is deleted), clears `autofix_stats.json` (carrying `pre_packages` over as `carry_pre_packages` first), and calls `_disable_sleep_sync()`; leg B repeats `_disable_sleep_sync()` and runs `powercfg /h off` (Fast Startup off — with hiberboot on, the "reboot" doesn't fully reinitialize the PnP stack and re-enumeration after driver deletion is unreliable).

**2. A WEBVIEW2-TELEPÍTÉS UTÁNI ÚJRAINDÍTÁS AZ ISMERT `_MEI`-CSAPDÁBA FUTOTT** (`common.relaunch_detached`). ### AutoFix extras & reporting

- **AutoFix extras on top of the shared core (`app/gui/autofix.py`)**: per-UID `attempt_counts` allows ONE retry of a failed install before permanent exclusion (successes drop out server-side via `IsInstalled=0`; the old first-offer-permanent-exclusion turned one transient download error into a permanently skipped driver); after the WU rounds a **catalog closing round** runs `_catalog_search_collect` + `_install_catalog_sync(task_id='autofix')` on still-error-coded devices (the AutoFix twin of the manual hybrid top-up — before this, a device WU had nothing for stayed broken even when the Catalog had a driver); the no-internet rescue restores the saved Net-driver backup (the nicpack.zip last-resort branch was removed 2026-07-28, explicit user decision — the failure message recommends the shop's USB-RJ45 adapter instead); per-leg install counts persist in `<app_data>\autofix_stats.json` (legs are separate processes) and the final leg emits a summary (`_emit_autofix_summary`: chain-total installs + **packages that never came back** + remaining error-coded devices) then deletes the stats file (leg A also clears it so a stale chain can't pollute the next run). **The "never came back" report (`_emit_missing_packages`) is mandatory, not cosmetic**: AutoFix deletes every third-party package assuming WU will restore whatever the machine really uses, and that assumption is sometimes false — field-seen (2026-07) `vigembus.inf` (ViGEmBus, a driver installed by a *user application*, which WU does not carry at all) and `amdafd.inf` (its `pci\ven_1002&cc_040300` generic class HWID never matches a present device, so the pairing can't find it) both vanished permanently and silently. We cannot reinstall them (there is no source), but the shop must know they're gone. The delete phase writes the pre-deletion package list to `pre_packages` in the stats file, and the comparison keys on the **original** INF name (`oemNN.inf` gets renumbered on reinstall). Read `pre_packages` *before* `_autofix_stats_total_and_clear()` — that call deletes the file. **The report splits into three buckets, and that split is load-bearing**: a bare "this INF name is gone" list misleads badly — measured 2026-07-25 it flagged 12 packages, of which `nv_dispi.inf` was simply superseded by `nvle.inf` (same vendor, same class) and 11 Razer packages were replaced by one generic `rz00b9dev.inf` while the mouse stayed plugged in and working. So: *lecserélődött* (same provider **and** class present now), *a gyártó másik csomagja* (same provider, other class), and only the rest is a real disappearance — which is the only bucket that gets the "plug the device in / reinstall the program" advice. **The two benign buckets are screen-capped at 15 items** (`BUCKET_SCREEN_MAX`, 2026-07-28): the first post-bloat run classified 175 ex-Razer INFs as *lecserélődött* and the item wall scrolled every useful summary line off screen; above the cap one line says how many more there are and the full name list goes into the log (the delete phase names every package anyway). The real-disappearance bucket is deliberately never capped — that is the actionable list.
  - **Deletion preview with per-package opt-out (`get_autofix_delete_preview`, 2026-08-05, explicit user decision)**: the confirm dialog now has a second column listing **every package that will be deleted**, each with a checkbox (all ticked by default), and — crucially — **what each driver is actually for**. Rows are locked (greyed, not clickable) when the program would keep them anyway: `boot` **always**, `printer` while the printer toggle is on, `wifi` while Wi-Fi mode is on — and the left-hand toggles re-render the list live. The grouping is computed **by the same functions the delete phase uses** (`_collect_printer_protection`, `collect_wifi_protection`, `_is_boot_path_protected` — note the last one is a 3-tuple + a `detected=False` fail-safe branch, so call the shared predicate instead of testing INF membership yourself; the offline test caught exactly that mistake). If preview and reality ran on separate logic, the preview would eventually lie to the technician. **The boot lock has TWO different causes and the UI must say which one** (2026-08-05, first question the panel got asked in the field): with the chain resolved, the package is provably on the system disk's path (dev box: `disk.inf` → **`oem11.inf`/`iaahcic.inf`, service `iaStorA`** → `pci.inf` → `acpi.inf` → `hal.inf` — i.e. an Intel RST controller carrying the boot volume, the exact `INACCESSIBLE_BOOT_DEVICE` case); with the chain **un**resolved, the fail-safe protects every `BOOT_FALLBACK_PROTECT_CLASSES` package instead, and claiming "it is on the boot path" would assert more than we know — the same overreach as the retracted colour-profile inference. `get_autofix_delete_preview` therefore returns `boot_detected` alongside the rows, and the lock text branches on it; the JS default is `true` (the stricter wording) so the pre-fill render can never under-state a lock. Performance: the list renders **instantly** from the already-loaded `drivers` array in the Drivers view (a fresh `dism /Get-Drivers` is 15–50 s and must never block a modal), and the usage/grouping data is filled in asynchronously — same pattern as the Wi-Fi detection. **But "renders instantly" was not enough, and the async fill must GATE the dialog** (2026-08-07, field report from a Dell laptop): until the backend answers, every pre-filled row carries `group: 'normal'`, so **no lock can be drawn at all** — the tech ticked "keep printer drivers", watched nothing happen for ~2 minutes, and reasonably concluded the checkbox was broken. Three changes, and they belong together: (a) the JS **passes its already-loaded driver list** into `get_autofix_delete_preview(known_drivers)`, so the backend skips the `dism` call entirely (that was the bulk of the wait; it still falls back to querying when the list is empty); (b) the four collectors (`collect_driver_usage`, `_collect_printer_protection`, `collect_wifi_protection`, `_collect_boot_path_protection`) run in a 4-thread pool — they are independent and only touch `self._run` (measured on the dev box: **16.0 s serial → 6.7 s parallel**); (c) while the call is in flight the dialog is **honestly disabled** — a sticky "Elemzés folyamatban" strip on the list, all toggles + row checkboxes + Mind/Egyik se disabled, and the **Igen button disabled** and relabelled, because a fix started on ungrouped data would silently ignore the protections. `mcResetLayout` re-enables the button, or a Mégse here would leave every later confirm dialog stuck.

  - **ONE CATALOG PACKAGE PER DEVICE PER CHAIN — `catalog_done` in `autofix_stats.json`, or the chain loops until the leg cap** (2026-08-25, field-proven, ASUS Vivobook Go E1504FA, Build 272). The chain ran all **10** legs and burned ~40 minutes; after leg 2 every single leg installed exactly **one** package: an **AMD Radeon catalog cab, 762 MB, re-downloaded eight times** (~6 GB). Every individual step was behaving correctly, which is why it was invisible: (1) the package installed — `Added driver packages: 3` — so the round counted 1 install and `should_chain` fired; (2) `_cleanup_unused_staged_infs` correctly unstaged 3 of its 5 INFs, since no present device used them; (3) the **next** leg therefore saw the package as not installed again — the parent device's version was unchanged because the driver had bound to the **child interface** (`a csomag az eszköz gyerek-interfészére kötött rá (a szülő marad oem8.inf, ez így helyes)`) — and re-downloaded it; (4) back to step 1. **`catalog_no_bind` could not catch this**, because it is not a no-bind case: the package installed *and* bound. The fix records every catalog item the chain **attempts** (not just the ones that fail) into `catalog_done`, and later legs skip those keys. It is written **before** `_install_catalog_sync` runs, so a crash or reboot mid-install cannot restart the same multi-hundred-MB download. Safe by construction: within one chain, re-installing the same package on the same device is redundant by definition — either it worked, or it did not bind and `catalog_no_bind` owns that case. The list dies with the stats file, so a later fix tries again. **The OEM round needed the identical guard and did not get it at the same time — `oem_done`, added 2026-08-26 after the same loop reappeared there** (HP EliteDesk 800 G1, Build 277): the whole-machine `HP driver pack sp92706` was re-downloaded and re-installed on every leg (16:14, 16:21, 16:26, 16:31, ~7 minutes each) until the technician aborted the chain. `_oem_already_current` structurally cannot catch this case: a whole-machine pack has **no device** (`dev is None`), so that function returns "install it" by definition, and the pack's version cannot be compared against any single device's driver version. When a per-chain guard is added to one install path, check every other install path for the same hole.
  - **RE-ENUMERATION ONLY WORKS WITH A REBOOT — learned the hard way, on customer machines** (`app/gui/rebind.py`, 2026-08-25). The repair for a device stuck on an inbox driver is to remove its PnP node so Windows re-selects a driver from scratch. Three field runs taught three things, in order:
    - **`pnputil /remove-device` + `/scan-devices` WITHOUT a reboot repairs nothing, and leaves the machine worse.** Measured (Build 273, T580): 8 devices removed, **0** rebound, and the technician took delivery of a laptop whose touchpad was now broken *by the repair button*. The node is gone and the running PnP stack does not rebuild the binding. `_rebind_device` therefore returns **`'fixed' | 'needs_reboot' | 'failed'`**, the manual button offers the restart and states plainly that the affected devices do not work until then, and the AutoFix runs the repair **before its settle reboot** so the chain's own restart completes it. This is the whole mechanism behind the accidental discovery that started it: the technician pulled the SSD, put it back, and the touchpad worked — the cure was not the removal, it was the **boot that followed**.
    - **Do not try to work out which package the device needs — let Windows decide.** The first implementation matched staged DriverStore INFs to devices by hardware ID and got it wrong in both directions, verified on the machine's own disk: `extract_inf_hardware_ids` keeps only IDs containing an underscore, so `ACPI\LEN009B` is invisible and **the Synaptics package could never be matched to the very touchpad the feature exists for** *(the underscore blind spot itself was FIXED on 2026-09-26 — the ACPI short form is now extracted; see [A keresés vakfoltjai](#a-keresés-vakfoltjai--négy-rétegen-ugyanaz-az-acpi-hiba-2026-09-26-asrock-b450m-pro4-élőben-mérve))*, while the loose `_hwid_matches` paired `intelgnssdriver.inf` (Intel GPS) and `appleusbvhci.inf` (Apple USB) onto a generic USB composite device. Removing the node and rebooting needs no package guess at all, and cannot end worse than it started: if nothing better exists, Windows re-binds the same inbox driver.
    - **The candidate set is EVERYTHING on an inbox driver except storage, firmware and the boot chain — the class WHITELIST was reversed on 2026-08-25 (explicit user decision) and must not be reinstated.** The user's instruction, verbatim: *"mindent rugjon meg ami nem boot kritikus, nyilvan a tarolo es firmware ne legyen megrugva, de ezen kívül MINDEN meg lehet rúgva… ha van gyári driver akkor inkább az legyen fent mint az inbox, kivéve a vezérlő és a firmware"*. The whitelist (`REBIND_ALLOWED_CLASSES`: Mouse/HIDClass/Keyboard, Media, Net/Bluetooth, Camera/Image/Biometric, SmartCardReader, Monitor) repeated the mistake this file already records for the generic-replace class lists: a **video card** stuck on the Microsoft Basic Display Adapter, a card reader, or a chipset node did not get the vendor driver **already sitting on the machine**, purely because its class was not listed. What replaced it (`REBIND_BLOCKED_CLASSES` = `STORAGE_RISK_CLASSES | FIRMWARE_RISK_CLASSES`) plus two non-class guards:
      - **The system disk's whole device chain is excluded by INSTANCE ID, not by class** (`_rebind_boot_chain_ids`, reusing the delete phase's `_collect_boot_path_protection`). The class list cannot cover this: measured on the dev box the chain is `WD Blue SN580 [DiskDrive] → NVMe controller [SCSIAdapter] → **PCI Express Root Port [System]** → Root Complex [System] → ACPI [System]`, i.e. the port carrying the boot NVMe is `System` class and the class rule would happily rip it out of a running system. If the chain cannot be resolved, `_rebind_boot_chain_ids` returns `None` and the candidate filter falls back to skipping `REBIND_BOOT_FALLBACK_CLASSES` (`SYSTEM`, `COMPUTER`) — same fail-safe reasoning as `BOOT_FALLBACK_PROTECT_CLASSES`.
      - **`is_specific_hwid` stays.** A type-coded device (system timer, PCI bridge) cannot have a vendor package by construction, so re-enumerating it is guaranteed to return the same inbox driver — pure cost, no gain. This is not a device filter in the search sense; nothing is being hidden.
      - The Build-274 measurement that justified the whitelist is still **true** and is now an accepted trade, not a bug: the round does select the TPM, the USB host controller, the root hubs and PCIe ports. Removing a TPM *node* is not `tpm.msc → Clear` (BitLocker keys are untouched); removing the USB controller node, however, **kills the keyboard and mouse until the reboot** — which is why the manual button now takes its consent **up front** and then **reboots by itself** after a 10 s countdown (`_rebind_finish_reboot`). The old flow asked "shall I reboot?" *after* the sweep, i.e. exactly when the technician could no longer click anything.
      - Measured after the change (dev box, ASRock B450M Pro4): **36 → 62 candidates**, 6 boot-chain devices excluded, and the newly reachable ones include the GPU/audio-controller/card-reader class of device the whitelist had been hiding. INF reads are cached per package (`_rebind_pkg_ids`) — without it the widened set would re-read the same few INFs 62× (~1200 file reads).
    - **THE SWEEP RUNS AT THE END OF THE CHAIN, AND THE CHAIN DOES NOT CLOSE UNTIL IT HAS** (`_autofix_closing_rebind`, `rebind_done` in `autofix_stats.json`, explicit user decision 2026-08-25: *"a lánc végén telibe ez fusson le és csak akkor legyen vége a láncnak ha ez lefutott… amikor visszajovok a kavezasrol minden hibatlanul mukodjon"*). Placement is load-bearing: **after** the settle reboot, **before** the closing report — so the sweep decides on a settled machine, the nodes it removes are re-discovered by the reboot it triggers, and `_emit_driver_health` describes the final state instead of a half-dismantled one. It runs the **same** `_rebind_sweep` core as the manual button (two copies would drift, and a field log could not tell which ran). Three behaviours worth keeping: nothing removed ⇒ **no** reboot, the closing continues in the same leg; an exception is swallowed (WARNING) because this is a convenience repair, never a precondition for closing the chain; and a Cancel *after* nodes were removed **still reboots** — a machine handed over without a keyboard is worse than one extra restart — but unregisters the resume task, so the chain stops there.
  - **A 3-CHARACTER ACPI VENDOR CODE IS A SPECIFIC HARDWARE ID — `is_specific_hwid` silently said otherwise, and it hid the exact device this whole feature was written for** (`_HWID_VENDOR_TOKEN_RE`, fixed 2026-08-25). The regex demanded `(?:VEN|VID)_?[0-9A-Z]{4}`, i.e. four characters after the prefix. PCI/USB ids do have four (`VEN_8086`, `VID_046D`), but ACPI devices carry the **three**-character PnP vendor code — and the ThinkPad T580 touchpad is `ACPI\VEN_LEN&DEV_009B`. It therefore failed the test, with three silent consequences: the Microsoft Catalog was **never queried** for it, the closing health report could **never** list it (the "vendor-coded input device" exemption CLAUDE.md documents was dead code for precisely that device), and it could not become a re-enumeration candidate either — the touchpad was invisible to the feature built to fix touchpads. Now `[0-9A-Z]{3,4}(?![0-9A-Z])`; the trailing guard stops a 3-char match from biting into a 4-char code. Regression-tested over 11 specific ids (incl. `ACPI\VEN_MSFT&DEV_0101`, `ACPI\SYNA30A0`, PCI/USB/HDAUDIO/MONITOR forms) and 10 type codes that must still be refused (`ACPI\PNP0501`, `ACPI\VEN_PNP&DEV_0100`, `USB\ROOT_HUB30`, `*PNP0501`…) — the type-code rule from the catalog-key section is unchanged.
  - **The health report's "vendor-coded input" exemption must not fire for USB peripherals** (`_USB_PERIPHERAL_HWID_RE`, 2026-08-25). `_VENDOR_CODED_RE` matches `VID_`, and **every** USB mouse/keyboard/headset carries one, so the exemption pulled the whole HID skip list back into the report: measured on the dev box the closing summary listed **36** devices of which **34** were external peripherals correctly running Microsoft's HID drivers — the "42 rows of which 40 are noise" failure this filter exists to prevent, inverted. Integrated input devices (`ACPI\VEN_LEN&DEV_009B`, `ACPI\SYNA30A0`) are never `VID_`/`PID_` shaped, so the exemption still covers exactly what it was written for. Same measurement also added `hidtelephonydriver.inf` (USB headset volume keys) to `HEALTH_REPORT_SKIP_INFS`. Result on that machine: **36 → 3** rows, all real (onboard audio on `hdaudio.inf`, the monitor on `monitor.inf`, and the NVMe controller the storage checkbox held back).
  - **A DRIVER CAN INSTALL AND STILL FAIL TO START — and the fallback to the inbox driver makes the error code ZERO, so the chain reports success while the device is degraded** (`_fix_driver_regressions`, 2026-08-25, field-proven twice on the same ThinkPad T580). The machine's own `setupapi.dev.log` recorded it verbatim: `Installing best driver (oem19.inf) on device 'ACPI\LEN009B'` → `Strong Name=oem19.inf:…:LENOVO_GROUP53_InterTouch_Win8_Inst:19.3.4.228` → `Start: ACPI\LEN009B` → `Device 'ACPI\LEN009B' not started: Device has problem: 0x0a (CM_PROB_FAILED_START)`. Windows then fell back to the generic `msmouse.inf` PS/2 path, which starts perfectly — so `ConfigManagerErrorCode` was 0, the closing report printed `✅ Nem maradt hibakódos eszköz a rendszerben!`, and the technician got a laptop whose touchpad stuttered, jumped and lost tracking (and, the day before, whose UltraNav buttons did nothing). **The error code can never catch this class of failure**, because the fallback is by definition healthy. Three rules came out of it:
    - **The delete phase snapshots every device that runs on a VENDOR driver (`pre_device_drivers` in `autofix_stats.json`), and the final leg compares.** A device that was on a vendor driver before and is on an inbox one after is a **regression**, reported loudly and repaired — no version arithmetic, no error codes, just before-vs-after.
    - **Repair escalates, and the second step is the one that actually works: re-enumerate the device** (`pnputil /remove-device` + `/scan-devices`, falling back to `Disable-PnpDevice`/`Enable-PnpDevice` below Win10 1903). Re-running `pnputil /add-driver …/install` alone often changes nothing, because Windows considers the current driver adequate; removing the device node forces driver selection **from scratch**. This is the software equivalent of what the technician did by accident — pulling the SSD and putting it back, after which the Synaptics driver bound correctly and the touchpad worked. **Never re-enumerate a storage device** (`STORAGE_RISK_CLASSES`): a boot-path node vanishing for a few seconds can take the running system with it, while an input device disappearing briefly is harmless in an unattended chain.
    - This is **not** the banned "back up the old driver and restore it" pattern. The package being re-bound is the one *this chain just installed*, sitting staged in the DriverStore (`wu_core.driverstore_package_inf`); we are finishing an install that failed on a live system, not preserving the machine's pre-fix state.
    - Related reporting fix: `msmouse.inf`/`input.inf` are in `HEALTH_REPORT_SKIP_INFS`, so the degraded touchpad was not merely unreported — the summary actively said *"billentyűzet/egér - ezekhez gyári driver nem is létezik"*, which is false for a precision touchpad whose vendor package sits in Lenovo's own catalog. `_health_report_worth_listing` now exempts **vendor-coded** input devices (`ACPI\VEN_LEN&DEV_009B`) from that skip list; a plain USB mouse on `msmouse.inf` is still correctly silent.
  - **THE CHAIN ENDS WITH A SETTLE REBOOT — the closing cleanup, health report and summary must run on a machine that has booted since the last install** (2026-08-25, field case). Until this, the last install leg finished *without* rebooting: it printed "kész", and the machine was handed over in whatever half-settled state the final round left it — including anything the **catalog closing round installed in that same leg**, whose `3010`/reboot-pending results never got their boot. The `_emit_driver_health` report was computed in that same unsettled state, so it could warn about devices that were about to be fine. Field case (ThinkPad T580, 2026-08-24): the chain provably installed the correct Lenovo/Synaptics UltraNav driver — the machine's own `setupapi.dev.log` records `Strong Name=oem17.inf:…:LENOVO_GROUP53_InterTouch_Win8_Inst:19.3.4.228:acpi\len009b` followed by `Start:` — yet the technician took delivery of a machine whose trackpad buttons did not work and reasonably concluded the program had broken it. **The same machine, untouched, worked after a later boot.** So: when the round would close the chain, it instead sets `settle_done` in `autofix_stats.json`, schedules one more `--resume-autofix` and reboots; the returning leg sees the flag and goes straight to the closing. Exactly **one** extra reboot is possible — the flag lives in the stats file, which survives reboots and is cleared both at chain start (`_autofix_stats_clear`) and at chain end (`_autofix_stats_total_and_clear`). Do not "optimize" this away to save a minute: without it the chain can hand back a machine that is one boot short of correct, which is precisely what the [acceptance criterion](#the-acceptance-criterion-for-the-one-click-fix-press-it-walk-away-come-back-to-a-finished-machine) forbids.
  - **`🎉 MINDEN LÉPÉS KÉSZ!` is only emitted when no further leg is chained** (it now reads `EZ A KÖR KÉSZ!`): it used to print at the end of every install leg, immediately followed by a reboot, which reads as "finished" plus an unexplained restart.

### AutoFix: two standing product decisions (2026-07-31)

- **The AutoFix must not touch colour profiles in any way.** See the (now deleted) `app/colorprofile_core.py` bullet for the evidence — the colour reset is a manual button in the Kijelző view since 2026-09-22; the short version is that the *same* reset improved one machine and wrecked another, so it is the technician's call, made in a view that shows what it is doing — not a silent side effect of a driver fix. `app/gui/autofix.py` and `app/cli/autofix.py` both carry an explicit comment at the old call site.
- **The closing Windows Update pause is `AUTOFIX_WU_PAUSE_DAYS` = 3650 days (~10 years), not 7** (`app/wusettings_core.py`). The shop hands machines back with WU not starting on its own: the fix has just installed a coherent driver set, and the worst outcome is Windows overwriting it days later. Note what this is and is not — it is a **pause**, not a disable, so the customer resumes it with one click in Settings > Windows Update; security updates are not permanently cut off. All three AutoFix pause sites use the constant, so the value is changed in exactly one place. **Since 2026-08-25 it is the confirm dialog's sixth checkbox (`mc-wu-pause`, `--no-wu-pause`, explicit user decision)**, and it differs from the other five in two deliberate ways: (a) it defaults **ON** and is re-set to ON on every dialog open, because the ~10-year pause is the shop's normal practice and switching it off is the conscious deviation — the opposite of the storage/firmware switches; (b) consequently the **negative** travels as the chain flag (`--no-wu-pause`), so an older scheduled task whose `-Argument` predates the switch still produces the familiar pausing behaviour. **The checkbox governs only the state the machine is HANDED BACK in, never the pause during the chain**: WU stays paused across the legs regardless, because otherwise Windows installs drivers behind the chain's back between reboots and overwrites the coherent set we are building. With the box unticked the final leg calls `wusettings_core.resume_wu` right before the closing message, and a failure there is reported on screen — a machine going back to the customer in a different WU state than the technician chose must never be silent. Propagation is `_schedule_autofix_resume`'s job like every other flag (offline-tested over all 64 combinations).
