### Kijelző & Színkezelés view (`app/gui/display.py` + `app/display_core.py`) — A 2026-07-31-I ELSŐ VÁLTOZAT (a mérései érvényesek, a FELÜLET-leírás a fenti újraírással elavult)

GUI-only view added 2026-07-31 on explicit user request, because Windows 11 scatters these settings across three places (Settings > Display > HDR, the legacy Color Management control panel, the Store-only HDR Calibration app) and none of them answers the two questions the shop actually has: *what can this panel really do*, and *is the machine's colour management even intact*. Every API below was probed on real hardware before a line of the view was written (AOC AG276QZD2 QD-OLED, DisplayPort, RTX 3060) — the captured sample lives in the `display_core.py` module docstring, and it is what the parsers were built against.

- **HDR is toggled through DisplayConfig, and the RETURN CODE IS NOT THE SUCCESS TEST — the read-back is.** `set_hdr` tries `DISPLAYCONFIG_DEVICE_INFO_SET_HDR_STATE` (16, Win11 24H2+) first and falls back to the older `SET_ADVANCED_COLOR_STATE` (10) **only if the state did not actually change**, because the old call can enable WCG instead of HDR. Measured live: type 16 flipped the panel to `activeColorMode=2`, 8→10 bits, and back again cleanly. The struct `size` fields must match Windows' definitions exactly — a wrong size makes `DisplayConfigSetDeviceInfo` return 0 while doing nothing, which is exactly the silent-false-success class this project keeps getting bitten by. That is why the verdict is always "did the re-read change?".
- **Read both advanced-colour APIs, prefer the new one, never rely on only one.** `GET_ADVANCED_COLOR_INFO` (9) exists on every Win10/11 and gives supported/enabled/bits/encoding; `GET_ADVANCED_COLOR_INFO_2` (15) exists from Win11 24H2 and additionally separates **HDR from WCG** (`hdrSupported`/`hdrUserEnabled`/`wcgSupported`/`wcgUserEnabled`) and reports the active colour mode. `read_hdr_state` fills from the old one and then overwrites with the new one when available, so an older Windows still renders a complete card instead of an empty one.
- **The nit values come from the EDID's CTA-861 HDR Static Metadata block, and they are the MANUFACTURER'S CLAIM, not a measurement** — the UI says so in as many words. Software cannot measure luminance without a colorimeter, and promising otherwise would be the one thing a shop tool must not do. Decoding is `nits = 50 * 2^(raw/32)` for peak and frame-average; the minimum is derived from the peak. Measured on the dev panel: peak 1015, frame-average 254, black 0.0006 nit — textbook QD-OLED.
- **A monitor has SEVERAL EDID entries in the registry and only one of them is the real one.** Live measurement found three `DISPLAY\AOCA610\…` instances for one physical panel: two 128-byte stubs with no CTA extension (⇒ no HDR data at all) and one 384-byte full EDID. `collect_edids` therefore keeps the **longest** EDID per instance key, and `match_edid` resolves the DisplayConfig device path (`\\?\DISPLAY#AOCA610#5&…&UID28931#{guid}`) to `AOCA610\5&…&UID28931`, falling back to the model's largest EDID when the exact instance is absent. Matching on the model alone, or taking the first entry found, would silently report "this monitor has no HDR data" on a monitor that does.
- ****The calibration switch lives in `ICM\Calibration`, not in the `ICM` root** — my first cut of `calibration_management()` read the root and therefore returned `None` on a machine where the value was sitting at 0 one key deeper, i.e. it was blind to precisely the state the view exists to surface (`colorprofile_core` has always written the correct path). It now reads **both** locations and a 0 anywhere wins over a 1 elsewhere: a missing value must never be reported as "fine" while the other location says otherwise. `set_calibration_management(enabled)` writes both values, and **both directions are legitimate** (explicit user decision): 1 is the Windows default and merely *permits* a profile's gamma curve to load (it enables nothing by itself), while 0 is a deliberate lock used on a wide-gamut OLED whose owner wants the native, unmanaged picture and wants to be sure nothing — an update, a vendor tool, another app — can load a gamma ramp behind their back. The view therefore offers a toggle with the current state shown, not a one-way "repair" button.
- `registered_profiles_report` exists because of a real, invisible breakage found on the dev box during this work.** `HKCU\…\ICM\RegisteredProfiles\sRGB` pointed at `srgb_to_gamma2p2_300_mhc2.icm`, a file some third-party HDR tool had left registered and then deleted. Consequence: **every** `mscms` call on that machine returned `ERROR_FILE_NOT_FOUND`, and no Windows UI mentions it anywhere. The view detects it, names the exact registry values, and `repair_registered_profiles` removes **only** entries whose file is provably missing (intact ones are never touched, every removal is logged by name at WARNING first). Windows falls back to its own built-in default, so the removal is the repair, not damage.
- **The view reports the MONITOR's driver (`monitor_driver`, `generic_monitor`), because "what is the factory state?" has no single answer.** On a monitor running the generic `monitor.inf` there is no factory ICC at all, so a linear ramp genuinely *is* the out-of-box state (measured: the dev box's AOC is `Generic PnP Monitor`). On a monitor that has a vendor INF, that INF installs **and associates** a factory ICC — there the out-of-box state is *not* linear, and a chain that stripped the vendor monitor package took the profile with it. Note this second path is **not** `colorprofile_core`: the ordinary third-party driver deletion removes the monitor's `oemNN.inf` too, and that is correct and must stay. The remedy is to get the vendor monitor driver back (Monitor is in the driver search since 2026-07-27), not to weaken the deletion.
- **The GPU gamma ramp is read and drawn, because it is the only DIRECT fact about the colour path.** `read_gamma_ramp` opens a DC on the specific display (`CreateDCW` with the GDI name, not the desktop DC — on a multi-monitor box each output can carry a different ramp) and calls `GetDeviceGammaRamp`. A linear ramp proves nothing is correcting the signal, whatever the profile list says; a modified one proves something *is*, even when no association is visible. The view therefore shows a LINEÁRIS/MÓDOSÍTVA badge, the max deviation from linear, and a 17-point SVG curve per channel against a dashed reference — a badge alone would not say *which way* it deviates. `GAMMA_LINEAR_TOLERANCE` is 64/65535 (~0.1%), not 0, because driver rounding makes an untouched ramp jitter by a few units; measured on the dev box an untouched ramp gives exactly 0. This is also what settles "did my change take effect?" questions: disabling calibration management does not clear an already-loaded ramp — that survives until the next logon/reboot, and the box is where the technician sees it actually go linear.
- **Count the association VALUES, not the keys** — the same lesson `colorprofile_core` already records: the `ProfileAssociations\Display\{GUID}\NNNN` subkeys are mostly empty containers and the profile is a *value* inside them. `_read_assoc_branch` walks down to the values and handles both `REG_SZ` and `REG_MULTI_SZ`.
