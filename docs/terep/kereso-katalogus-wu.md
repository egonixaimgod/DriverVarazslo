### What actually gets a driver — the inventory

#### "Device X got no driver" — walk the chain in this order

The single most-asked field question, and the answer is spread across four subsystems, so guessing wastes a whole session (it cost three in a row before this table existed). Every step below names the **log line that settles it**, so it is answerable from a pasted log alone. Stop at the first step that explains the device — do not change any list until you know which layer dropped it.

| # | Question | Log line that answers it | If this is the culprit |
|---|---|---|---|
| 1 | Was the device even in the scan list? | `[PNP] N eszköz a szűrés után…` + `[PNP] N eszköz kizárva a driver-keresésből (nincs PNPDeviceID=…, virtuális gép eszköze=…, osztály=…)`, names at DEBUG under `[PNP] Kizárva (<ok>)` | `_filter_wu_scan_devices` / `WU_SCAN_IGNORED_CLASSES` / `_VIRTUAL_DEVICE_NAME_RE` |

Two shortcuts worth remembering: a device missing from step 1 can never be fixed by touching a Catalog blocklist (that mistake cost the monitor its drivers for a long time), and steps 7–11 only ever concern the **Catalog** — the WU Agent has no class filter above step 3.

**Read this first, because the obvious mental model is wrong in one important way:** it is *not* "the WU Agent sees everything, and only the Catalog has blocklists". Before either source runs, `_filter_wu_scan_devices` drops whole device classes (`WU_SCAN_IGNORED_CLASSES`) — and that filter gates **both** paths, so a class listed there is unreachable by the WU Agent too, not just by the Catalog. That is why the monitor got nothing for so long: it was never in the device list to begin with, so no Catalog blocklist change could ever have fixed it. Layer order: (1) `WU_SCAN_IGNORED_CLASSES` — applies to everything; (2) WU Agent — no further class filter on top; (3) the three Catalog entry points, which **since 2026-07-28 share one rule set**: all three take every device, minus the two checkbox-gated risk classes. When a device "gets no driver", find out which layer dropped it before changing anything — the log names every one of them.

> **THE GOVERNING RULE (explicit user decision, 2026-07-28 — this outranks every list below).** A device is excluded from the driver search in **exactly two** cases, and no third may be added:
> 1. **storage or firmware** — **2026-09-02 óta ez már nem kapcsoló, hanem RÖGZÍTETT SZABÁLY**, lásd [Tároló és firmware: véglegesen tiltva](#tároló-és-firmware-véglegesen-tiltva-nincs-hozzá-kapcsoló-2026-09-02). Korábban két, alapból kikapcsolt jelölőnégyzet volt rá (`mc-allow-storage`/`mc-allow-firmware`, illetve `hw-allow-storage`/`hw-allow-firmware`); azok eltűntek, a szűrők maguk változatlanul működnek;
> 2. **it is not hardware** — the seven conceptual classes in `WU_SCAN_IGNORED_CLASSES` (volume objects, audio endpoints, the print queue, the HAL, non-PnP entries), plus devices with no `PNPDeviceID` and hypervisor guest devices.
>
> Everything else gets searched, in every round, on every source. There is **one** additional rule, and it is deliberately *not* a device filter: `is_specific_hwid` refuses to use a **type code** as a Catalog search key, because the Catalog answers a type code with any vendor's package for that type. The device still enters the round — only the useless key is skipped.
>
> The three earlier generations of this rule (per-round class whitelists, class blocklists, the vendor-HWID requirement, the bus-enumerator INF list) are all gone, and every one of them turned out to hide real drivers: the class lists kept a printer/keyboard/USB controller from ever being asked about, and the bus-INF list hid `Intel - System 11.7.0.1019` on a `machine.inf` node and `Intel - System 9.21` on the HD Audio controller. **If a round ever needs to be made cheaper, add threads or a cache — never a device filter.**

Four independent sources feed drivers onto a machine, and it is easy to misattribute a gap to the wrong one. **Both the manual scan and AutoFix use the same functions for all of it** — the only difference is that the manual scan lists candidates with checkboxes and AutoFix installs them unattended. Never fork a second implementation for one of the two.

| Source | Covers | Behaviour |
|---|---|---|
| **WU Agent** (`_search_wu_api` + `_match_wu_updates_to_devices`) | every present device, **no class whitelist** — chipset, GPU, audio, LAN, Bluetooth, mice, controllers, cameras | the main path; AutoFix installs automatically, manual scan lists |
| **Update Catalog — error-coded devices** (`_catalog_search_collect`) | devices with `ConfigManagerErrorCode` ≠ 0 that WU had nothing for | automatic in both paths |
| **Update Catalog — generic-driver devices** (`mark_generic_replace_candidates`) | devices running on an inbox driver, no class filter since 2026-07-28 | manual scan: pre-selected with a badge; AutoFix: closing round |
| **Update Catalog — deep scan** (`deep_catalog_candidates`, 2026-07) | **every** remaining device with a vendor-coded HWID — i.e. a device happily running an *old vendor* driver, which none of the rows above reach | manual scan: `start_hw_scan(deep=True)`, default on, checkbox `hw-deep-scan`; AutoFix: `AUTOFIX_DEEP_CATALOG` |
| ~~**Vendor sites (GPU)**~~ | ~~NVIDIA/AMD/Intel~~ | **TÖRÖLVE 2026-09-02** (explicit user decision) — lásd lentebb. A gép/alaplap-gyártói link-kártya (`oemdrivers.py`) MARAD, az nem videokártya. |
| ~~**OEM vendor catalog**~~ | ~~Lenovo/Dell/HP~~ | **TÖRÖLVE 2026-09-02** (explicit user decision) — a modulok sincsenek meg; a gépazonosítás `app/machine_core.py`-ban él tovább |

**Storage and firmware devices are PERMANENTLY excluded in BOTH paths — no checkbox, no flag, no way to enable them** (2026-09-02, explicit user decision; see [Tároló és firmware: véglegesen tiltva](#tároló-és-firmware-véglegesen-tiltva-nincs-hozzá-kapcsoló-2026-09-02)). Until then it was two default-off checkboxes per path (`mc-allow-storage`/`mc-allow-firmware`, `hw-allow-storage`/`hw-allow-firmware`).

**The deep scan (2026-07) is what closes the "old but working vendor driver" hole.** Before it, a device that was neither error-coded nor on an inbox driver was never asked about in the Catalog at all — so a 2023 chipset driver that worked fine simply never updated (WU considers the device healthy and offers nothing). `deep_catalog_candidates` feeds every remaining device to the same `_catalog_search_collect`, and the release gate in `_catalog_find_driver` (strictly-newer only, **by date** since 2026-07-27 — see `is_newer_release`) is what keeps it from downgrading anything. Measured live (2026-07-25, X570 + RTX 3060): 99 present devices → **16** deep candidates → 12s → 3 genuinely newer packages that the old code missed (AMD PCI 1.0.0.83→1.0.0.90, AMD PSP 5.17→5.44, plus the Realtek generic-replace), while correctly rejecting the NVIDIA row (catalog 32.0.15.9595 < installed 32.0.16.1074) and the identical-version Realtek NIC. **Exactly one filter is left: `DEEP_CATALOG_BLOCKED_CLASSES` (the two checkbox-gated risk classes).** The vendor-coded-HWID requirement and the bus-enumerator INF blocklist were removed on 2026-07-28 together with round 3's copies — **both constants (`_VENDOR_HWID_RE`, `GENERIC_REPLACE_BLOCKED_INFS`) are deleted**; a comment block marks their old spot so they don't get reintroduced as device filters. Measured immediately after, on the same Intel Q170 box: **95 devices → 91 in the combined catalog round, and the only 4 left out were the 3 storage devices and 1 firmware device the checkboxes gate** — i.e. the device set is now exactly "everything except the user's two exceptions". Cost: the full round went to **48s on 10 threads** (91 devices × up to 4 HWID queries each). Gain on that machine: 4 hits → **10**, including an Intel I219 NIC package, Intel HD Graphics 530 `31.0.101.x`, the Intel chipset `10.1.1.44`, Intel AMT Ports and the Management Engine Interface — none of which any earlier configuration would have found. One of the ten (`AlpsAlpine - System` on an Intel chipset device) looks like an OEM bundle indexed under a shared chip ID, the same shape as the Clevo-Realtek case; `inf_package_applies` plus the post-install bind check are what catch those, at the cost of a download. **`DEEP_CATALOG_BLOCKED_CLASSES` used to be deliberately narrower than the generic-replace blocklist** (HID/Display/Ports allowed, on the theory that updating an existing vendor driver to its own newer version is not the same risk as swapping Microsoft's driver for a vendor one) — **as of 2026-07-28 the two are identical** (`STORAGE_RISK_CLASSES | FIRMWARE_RISK_CLASSES`), because that distinction produced the indefensible result that a device got no better driver *because* it was on a worse one. **Storage must stay in it**: during development the deep set did pull in `Standard NVM Express Controller` and `Standard SATA AHCI Controller` before that list existed, which is exactly the `INACCESSIBLE_BOOT_DEVICE` scenario the whole project avoids.

**The list below is now mostly HISTORY — read it as the reasoning behind the two surviving exclusions, not as a live blocklist.** As of 2026-07-28 only storage and firmware are held back, both behind checkboxes, and both fully available once ticked. Every other entry that used to live here (Display, Monitor, Processor, Battery, Printer, CDROM, WPD, USB, HID/keyboard/mouse, PCI bridges) has been reversed, each after the same discovery: the exclusion was hiding a real driver. The reasons are kept because they explain *why* storage and firmware are different in kind — and because each reversal is a warning about how easy it is to write a plausible-sounding ban that costs the shop real drivers. **Do not add a new entry here**; see the governing rule above.

- **Storage controllers** (`SCSIAdapter`, `HDC`) — **from the Catalog, in AutoFix, always; from WU in AutoFix, unless the tech ticks the box**: a bad controller swap surfaces as `INACCESSIBLE_BOOT_DEVICE` at the *next* boot, where no rollback of ours can run — not even the restore point, only recovery media. **The rule used to be enforced on the Catalog side only** (2026-07-27 audit): `SCSIAdapter`/`HDC` are not in `WU_SCAN_IGNORED_CLASSES`, so they sailed through to `_match_wu_updates_to_devices` and AutoFix would have installed a WU-offered NVMe/AHCI driver unattended — the code and this document disagreed, and it stayed hidden only because WU happened to offer nothing for the field machine's controller. Resolved by **explicit user decision**: not a silent ban (WU packages are WHQL and the server itself vets applicability, which is a different risk class from a scraped Catalog row) but a second checkbox on the AutoFix confirm dialog — `mc-allow-storage`, **default off, and forced back off every time the dialog opens** because it is a per-machine, boot-critical judgement, not a remembered setting. `wu_core.filter_autofix_risky_devices` applies it (together with the firmware switch) to the WU device list and names every dropped device in the log. The choice rides the chain through `--allow-storage-drivers` exactly like the printer flag (both appended by `_schedule_autofix_resume`, never by call sites). **Firmware has its own, second checkbox** (`mc-allow-firmware`, also default off and reset on every open, explicit user decision 2026-07-27). It is deliberately *not* folded into the storage switch, because the failure mode is a category worse: a firmware update rewrites non-volatile memory (UEFI/BIOS, SSD controller, TPM, dock), no restore point or Windows reinstall can undo it, an interrupted flash kills the device in hardware, and a TPM flash can invalidate BitLocker keys. This one closed a real hole rather than a theoretical one: `Firmware` was never in `WU_SCAN_IGNORED_CLASSES`, so **AutoFix has always been able to flash firmware unattended** whenever WU offered it — the Catalog-side block was cosmetic at the time, because firmware devices failed the then-existing vendor-HWID test and `c_firmware.inf` was on the then-existing bus-INF list. **Both of those safety-by-accident mechanisms are gone since 2026-07-28**, so the `Firmware`-class gate in `filter_autofix_risky_devices` is now the *only* thing holding firmware devices back — do not weaken it on the assumption that something else catches them. The gate is enforced at **two levels**, and both are needed: `filter_autofix_risky_devices` drops `Firmware`-class devices, and `filter_firmware_updates` drops firmware *packages* (`is_firmware_update`: `DriverClass == Firmware`, or `\bfirmware\b` in the title/model) — because an SSD firmware package pairs with the *storage controller* and a dock firmware with a *USB* device, so the device-class filter alone would miss them. The title fallback is deliberately generous and every skipped package is logged by name, so over-filtering stays visible in the field log. **The checkbox governs BOTH AutoFix sources** — the WU device list (`filter_autofix_risky_devices`) *and* the Catalog deep scan (`deep_catalog_candidates(include_risky=…)`). It was WU-only for one iteration; that was rejected as confusing (explicit user decision): the tech makes one decision about storage drivers, not one per source. - **Two hidden filters in `_filter_wu_scan_devices` were also opened up, and all of them now log what they dropped.** They had excluded devices for four separate reasons while logging *none* of them, so "why did device X get nothing?" was unanswerable from a field log — a direct violation of the log-everything rule this file opens with, hiding in the one function every driver decision starts from. (a) The name test was a raw `"virtual" in name` substring match that threw out **real hardware** — `Intel(R) Virtual Buttons`, the volume/power buttons on most business laptops and 2-in-1s — and is now `_VIRTUAL_DEVICE_NAME_RE`, word-bounded hypervisor names only (`vmware|virtualbox|vbox|qemu|parallels|hyper-v|xen|virtio`). (b) The blanket `ROOT\` prefix skip is gone: most root-enumerated devices are Microsoft software objects that no source ships a package for, but application-installed drivers live there too (ViGEmBus, VPN TAP adapters), and skipping them also kept a broken one off the "Problémás eszközök" list entirely. The Catalog paths drop them anyway on the vendor-HWID test, so the cost is a few extra in-memory comparisons. **If you ever add an exclusion here, log it in the same `dropped` dict** — a silent filter in this function is how three separate exclusions stayed invisible through several rounds of "does it now cover everything?".
- What remains excluded is only what a driver cannot exist for: `Volume`/`VolumeSnapshot` (the volume object, not the disk or controller behind it — both of those are driverized), `Endpoint`/`AudioEndpoint` (`SWD\MMDEVAPI\…` audio *endpoints* — the speaker/mic entries, not the sound card, which is `MEDIA`), `PrintQueue` (`SWD\PRINTENUM\…`, the queue, not the printer), `LegacyDriver` (a non-PnP driver entry with no device behind it), and `Computer` (the HAL — replacing it means the machine does not boot, and nothing ships a package for it anyway).
- **Keyboard/mouse/HID**: vendors ship *software* (Synapse etc.), not drivers; where a real WHQL package exists the WU path already installs it (field-confirmed: Razer `rz00b9dev.inf`).
- ~~**USB controllers/hubs — for the *generic→vendor swap* only**~~ — **no longer excluded anywhere (2026-07-28)**, when the generic-replace class lists were removed. The old argument (Microsoft's driver is the correct one on modern chipsets, and a failed swap takes out the keyboard and mouse — the very input needed to recover) survives only as a caution, not a rule: the rollback net runs unattended in the same process, so it does not need the user's input to revert, and the measurement below applies here too — nearly every USB-class device is already dropped by the bus-INF rule (`usbxhci.inf`/`usbhub3.inf`/`usb.inf`) or the vendor-HWID rule, so the class entry was protecting almost nothing. **In the deep scan `USB` had already stopped being blocked** (2026-07-27): measured against the field device list, every USB-class device was *already* dropped by one of the other two filters — `usbxhci.inf`/`usbhub3.inf`/`usb.inf` by the bus-INF rule, `USB\ROOT_HUB30` by the vendor-HWID rule — so the class entry protected nothing. The single case it did catch was a controller running a genuine **vendor** USB driver (`oemNN.inf`), which is exactly the case that should be updated, and which the inbox-version guard in `_catalog_find_driver` still protects from a generic→vendor swap by the back door. Same finding applies to `FIRMWARE` (`UEFI\RES_{…}`), `PROCESSOR` (`ACPI\AUTHENTICAMD…`) and `COMPUTER` (`COMPUTER\{GUID}`): all three fail the vendor-HWID test on their own, so listing them was documentation of an intent the code never had to enforce. **`DEEP_CATALOG_BLOCKED_CLASSES` is now exactly `STORAGE_RISK_CLASSES | FIRMWARE_RISK_CLASSES`, and it is the *only* filter the deep scan has** — the bus-INF and vendor-HWID rules that this paragraph used to lean on no longer exist. **Do not add a class back here.** The product rule is that the blocklist has exactly two entries: what the user unticks, and what is not hardware (`WU_SCAN_IGNORED_CLASSES`). If a wrong-vendor package shows up, the cause is a type-code search key, not a missing class ban — check `is_specific_hwid` first.
- ~~**PCI bridges / root ports / ACPI nodes**~~ — **this entry was wrong and is gone (2026-07-28).** The claim ("no vendor driver exists at all") was never measured, only assumed, and it was the justification for `GENERIC_REPLACE_BLOCKED_INFS`. When the filter came off, a `machine.inf` "Motherboard resources" node returned `Intel - System 11.7.0.1019` and the HD Audio *controller* returned `Intel - System 9.21` — real chipset drivers that had been silently unreachable for as long as the list existed. Bus/enumerator devices are now queried like everything else; the ones that genuinely have nothing simply return zero rows, which costs a request and answers the question honestly.
- **Printer, PrintQueue, AudioEndpoint, Battery, Processor, Computer, Volume, CDROM, WPD**: excluded at the device-filter level (`WU_SCAN_IGNORED_CLASSES`).

**Boot-path protection is the one exception on the *delete* side (`wu_core._collect_boot_path_protection` / `_is_boot_path_protected`, 2026-07-26, used by BOTH AutoFix paths).** The blocklists above only ever governed *installing*; the delete phase had no class filter at all and `drivers_core.delete_driver_package` calls `pnputil /delete-driver … /uninstall /force` — i.e. it removes an in-use, boot-critical storage driver too (CLAUDE.md already documents the Intel RST case surviving only by *stalling*). On plain AHCI/NVMe that is harmless: Microsoft's inbox `storahci`/`stornvme` takes over. **Behind Intel VMD or an RST RAID volume it is not** — the inbox stack may not cover the controller, and the result is `INACCESSIBLE_BOOT_DEVICE` at the next boot, the one failure mode where none of our rollbacks (restore point included) can ever run, because the machine cannot start. So before deletion the code resolves the device chain carrying `%SystemDrive%` (WMI `Win32_LogicalDiskToPartition` → `…DiskDriveToDiskPartition` → `Win32_DiskDrive.PNPDeviceID`, falling back to `Get-Partition`/`Get-Disk`, then walking `DEVPKEY_Device_Parent` up to 12 levels) and protects every third-party package on it, exactly like the printer protection (published **and** original INF name, since a reinstall renumbers `oemNN.inf`). Two rules that must not be softened: (a) this is **targeted, not class-based** — a class blocklist here would gut the "strip everything" design, and measured live (2026-07-26, WD Blue SN580) the chain resolves to `disk.inf` → `stornvme.inf` → `pci.inf` → `acpi.inf` → `hal.inf`, i.e. all inbox, so **zero** packages get protected and the fix behaves exactly as before; (b) if the chain cannot be resolved at all, it **fails safe** to protecting all `BOOT_FALLBACK_PROTECT_CLASSES` (`SCSIAdapter`/`HDC`/`DiskDrive`) rather than falling back to the old unprotected behaviour — an unnecessarily retained storage driver is at worst stale, a wrongly deleted one is a machine that will not boot.

**Asymmetry worth remembering**: the AutoFix *delete* phase removes third-party packages regardless of class (bar the printer opt-out and the boot-path protection above), but the *reinstall* only reaches classes that survive `WU_SCAN_IGNORED_CLASSES`. A deleted **printer** driver therefore never comes back through us — which is exactly why the printer checkbox exists and why leaving it on is the shop-safe default.

### WU + Catalog engine (shared by AutoFix and the manual scan)

- **WU driver scan/install — shared core (`app/wu_core.py`)**: the PnP query+filter (`WU_PNP_QUERY_PS` + `_filter_wu_scan_devices`), WU↔device matching (`_match_wu_updates_to_devices` → `_hwid_matches`: **prefix match OR same-bus token-subset**, plus title↔name fallback, without which SoftwareComponent packages never match. The token rule is not a nicety: Windows composes hardware IDs as `VEN&DEV&SUBSYS&REV`, while WU frequently ships `VEN&DEV&REV` — SUBSYS sits *between* the tokens, so neither string is a prefix of the other. Field-proven (2026-07, Win10 + Radeon R9 200): `pci\ven_1002&dev_6811&rev_00` never matched `PCI\VEN_1002&DEV_6811&SUBSYS_30001682&REV_00`, so AutoFix **deleted the vendor GPU driver and silently never reinstalled it** — the machine finished the "successful" run on the Microsoft Basic Display Adapter, error-code-free, so even the summary looked clean. Class-scoped `&cc_` package IDs were unreachable for the same reason. IDs with no bus prefix — bare `usbmmidd` — stay exact/prefix-only, since anything looser false-positives on them), and the WUA installer PowerShell (`_build_wu_install_ps`) exist in exactly ONE copy, used by all three consumers: GUI manual install (`app/gui/hwscan.py`: `start_hw_scan` pool + `_install_wu_api`, filtering by exact `UpdateID`s with HWID-prefix fallback), GUI AutoFix (`_scan_and_install_wu_sync`), CLI AutoFix (FÁZIS 6, `match_system_devices=True`). **Never copy this logic back into a class** — the duplicated era produced the "AutoFix works, manual install silently broken for a whole release" bug (Build ~192). Baked-in rules: downloads are **synchronous `$DL.Download()`** — never `BeginDownload($null,...)` (null callbacks throw NullReferenceException instantly; that was the Build-192 regression; hang protection is the Python-side cancel `taskkill`); selection filters by exact `UpdateID` because distinct WU packages can share one HWID (field-seen: 3 selected → 4 installed with HWID-only filtering); with no filter args the script installs NOTHING (`EMPTY`). The script emits a line protocol (`INIT/SEARCH/FOUND/SKIP/TOTAL/DLONE/INSTONE/OK/OKRB/FAIL/EMPTY/DONE/ERROR`) parsed by all three callers — adding a marker means updating all three reader loops (`OKRB` = success but `$IR.RebootRequired`; counted as success everywhere, surfaced as a reboot warning in the manual GUI path via `self._wu_reboot_required`). **All three reader loops go through `wu_core._iter_process_lines`** (reader thread + queue): cancel is checked every 0.5s even when the script emits nothing, and a watchdog taskkills the process after 30 min of silence (`WuProcessAborted('cancel'|'hang')`) — the old direct `for line in process.stdout` blocked forever (dead Cancel button) when the in-script WUA search hung; don't revert to direct iteration. **The "poisoned session" rules (2026-07, field-diagnosed twice on a Dell OptiPlex 7060 — Builds 214 and 218) — all three live in `wu_core` and are used by both AutoFix paths:**
  - `is_reboot_pending(run)` (+`PENDING_REBOOT_PS`): once a *storage/chipset* driver installs (field case: Intel RST `iaAHCIC`), Windows goes pending-reboot and the WUA then returns `orcFailed(4)` for **every remaining package in that session — after a fixed ~143s wait each**. 8 leftovers = ~20 wasted minutes per round. `_install_abort_reason(consecutive_failures, reboot_pending)` is the shared decision: `'reboot'` if pending, else `'failstreak'` after `WU_MAX_CONSECUTIVE_FAILURES` (3) consecutive install failures (the net for a session that rots without setting the flags), else None. It is wired in through the new `abort_check=` parameter of `_iter_process_lines`, which kills the installer process and raises `WuProcessAborted(reason)` — callers never touch the PID.
  - **The pending-reboot query runs only after an install FAILURE, never after `OKRB`** — deliberate: in the field log the OKRB'd Display driver was followed by three more packages that installed fine, so bailing on mere reboot-*need* would sacrifice good installs. Failure is the evidence; reboot-need is not.
  - `verify_failed_installs(failed_titles, pkgs_before, pkgs_after)`: **a `[kód=4]` is not proof of failure.** All 8 "failed" packages in the field log were sitting in the DriverStore afterwards — the WUA verdict was a false negative. After every round the third-party package list is re-read and any failed title whose version shows up among the newly added packages is counted as a **success** (and never added to `install_failed_uids`). Never report a WUA install failure to the user without this check.
  - `pending_reboot_victim(round_failed_titles, aborted_reason)`: **the package that tripped the pending-reboot abort must NOT be blacklisted for the rest of the chain.** `install_failed_uids` (persisted as `wu_failed_uids`) exists so a genuine `[kód=4]` isn't retried at ~2.5 min per leg — but it used to swallow the one failure that is *not* genuine. The abort ordering proves which: `is_reboot_pending` is queried **only after an install failure**, and the first PENDING answer aborts immediately, so the **last** entry of `round_failed_titles` is exactly the package that got its `[kód=4]` from the already-poisoned session; everything before it failed while PENDING was still False and is real. `'failstreak'` gets no mercy (that *is* a real failure run). Field-proven (2026-08-05, Dell Latitude 7400): "Intel Corporation Bluetooth Driver Update (24.40.0.3)" was package 16/20, `[kód=4]` → PENDING → round aborted → permanently excluded, so the chain's remaining **two** legs never retried it and the machine shipped with the 3-months-older 24.20.0.3 — while the cure (a reboot) happened seconds later anyway. The contradiction was already written down one screen higher: the `attempt_counts` comment says *"Lábak közt viszont pont az újraindítás a gyógyír"*, and that reasoning was applied to the per-leg counter but not to the chain-wide blacklist. Cannot loop: on a fresh boot the same package no longer gets a `'reboot'` abort, so a real failure there blacklists normally, and `AUTOFIX_MAX_INSTALL_LEGS` is the backstop. Pure function, offline-tested over every abort reason.
  - `_filter_wu_older_duplicates(matches, wu_by_uid)`: WU offers a package's whole history (field: 10 `iigd_ext` Extension packages for one Intel UHD 630, from 2018), and AutoFix used to install every one of them. Keeps only the newest per `(HardwareID, DriverClass, DriverProvider, DriverModel)` family. That key is deliberately narrow: a wrong merge means a needed driver never installs, while a missed merge only restores the old behaviour.
- `_filter_wu_downgrades` (+`_iso_date_or_none`) is the AutoFix **downgrade guard**: WU can offer a package *older* than the installed driver (field-relevant right after a vendor NVIDIA install); matches whose `DriverVerDate` is strictly older than the installed driver's date are skipped — but NEVER for error-coded devices (any driver beats none), and **NEVER when the currently installed driver is an inbox (Windows built-in) one** (`_is_inbox_driver`: published INF is not `oemNN.inf`, or provider is Microsoft). That second exception is not optional: AutoFix deletes the vendor package, Windows immediately drops its own generic driver on the device, and an inbox driver's date is always newer (it ships with the OS) — so a pure date comparison locks the vendor driver out *forever*. Field-proven (2026-07, X670): `atihdwt6.inf` (AMD HDMI audio, 2021-07-13) was skipped in all three rounds because the inbox `hdaudio.inf` replacing it reports 2026-05-16, and the machine ended the run with one fewer driver than it started with. This is why `_get_installed_driver_info` also selects `DriverProviderName` + `InfName`. The manual scan doesn't filter, it only flags (`downgrade: true` pool items render an orange warning and are not pre-selected) — using the same inbox exception.
- **Printer protection 2.0 (`app/wu_core.py`: `_collect_printer_protection` + `_is_printer_protected`, used by BOTH AutoFix paths)**: class-based skipping (`AUTOFIX_PRINTER_SKIP_CLASSES`) alone was NOT bulletproof — multifunction printer packages spread across USB/Ports/SYSTEM classes (field-seen: `mvusbews.inf`, `hppscnd.inf`, `hpbuio70l.inf`), and deleting those broke customer printers/scanners. Before third-party deletion the code now also protects (a) every INF actually used by present printing components (`Get-PrinterDriver` InfPath + present Printer/PrintQueue/Image devices' `DEVPKEY_Device_DriverInfPath`) and (b) every package whose provider matches a printer vendor present on the machine (`PRINTER_VENDOR_KEYWORDS`; deliberately over-protective — WU restores e.g. HP laptop drivers anyway, a broken customer printer is unrecoverable). **INF matching must check both the published (`oemXX.inf`) and original (`hpc1320u.inf`) names** — `Get-PrinterDriver` reports original names, PnP `DriverInfPath` reports published ones (live-verified on the shop machine). **The same protection is available for MANUAL deletion since 2026-08-28** (explicit user decision: *"ha manualisan akarom csinalni az egeszet akkor nem tudom a nyomtatokat kiszurni egyetlen kapcsoloval"*): the Drivers view has a `hide-printer-drivers` toggle, **default on**, that filters printer packages out of the deletable table — `GuiDriversMixin.get_printer_driver_infs(known_drivers)` calls **the very same two functions**, so the manual list and the fix's protection cannot drift apart (a second, class-only implementation here would hide `mvusbews.inf`-class packages from the fix but not from the technician's Delete button). Three rules: it takes the **already-loaded** driver array from JS rather than re-running `dism /Get-Drivers` (15–50 s — same trick as the AutoFix delete preview); while the detection is in flight `printerInfs` is `null` and **nothing is hidden**, because an empty set would falsely imply the machine has no printer drivers (the toggle shows `⏳ felderítés...` meanwhile); and toggling it **drops the selection of any row it hides**, or a printer package ticked while the filter was off would still be deleted — the exact outcome the switch exists to prevent. Measured live on the dev box: 4 of 6 test packages classified as printer, including the Samsung `mvusbews.inf` in class `USB` that a class-only filter misses, and the vendor keyword set resolved to `canon/epson/hewlett/konica/minolta/samsung` — ~~no generic vendor, so the filter cannot swallow unrelated packages~~.

- **NIC safety net (`app/wu_core.py`: `_export_net_driver_backup`/`_restore_net_driver_backup`, both AutoFix paths)**: AutoFix deletes the LAN/Wi-Fi driver too, and if neither inbox nor WU covers the NIC (field-seen: fresh AM5 + Realtek 2.5GbE), the machine strands offline while the chain needs internet. Before deletion, Net-class packages are exported (`pnputil /export-driver`) to `<app_data>\netdrv_backup`; on the resume leg (GUI) / after install (CLI), if `_check_internet()` fails the backup is reinstalled + rescan.
- **Wi-Fi-s telepítés — the AutoFix's fourth checkbox (`--wifi-mode`, 2026-08-05, explicit user decision)**: until this, AutoFix was only reliable on a **wired** machine ("wifivel nem megy"), for three independent reasons, all of which had to be fixed together. (1) **`_check_internet` is a single 3 s TCP probe**, and the chain runs it right after logon — on Ethernet the link is up at boot, but a Wi-Fi association + auth + DHCP takes 15–45 s (more on 802.1X), so the chain read "no internet" when it would have had one half a minute later, and dropped into the rescue branch for nothing. The fix is `GuiBaseMixin._wait_for_internet(timeout, task_id, reason)`, which polls every ~2 s and reports progress; `AUTOFIX_NET_WAIT_WIFI` = 120 s, `AUTOFIX_NET_WAIT_WIRED` = 45 s (wired waits too — slow switch/DHCP could hit the same wall). It costs nothing in the normal case: the first probe returns immediately. (2) **The delete phase removed the Wi-Fi driver.** On Ethernet that is usually harmless (Windows' inbox LAN driver takes over); on Wi-Fi many Intel/Realtek/Qualcomm cards have no usable inbox driver, so the machine strands with no connectivity at all. (3) **Even if the driver returns, the saved network can be lost**: WLAN profiles hang off the interface GUID (`Wlansvc\Profiles\Interfaces\{GUID}`), and a driver remove+reinstall can regenerate it, orphaning the profiles. — The design (chosen over delete-and-restore): with the box ticked, the **connected** Wi-Fi adapter's driver is *protected from deletion*, exactly like the printer opt-out — `wu_core.collect_wifi_protection`/`is_wifi_protected`, matching **both** published and original INF name. This does not freeze the driver: the install phase can still put a newer version on top. **The Wi-Fi adapter is looked up whether or not it is CONNECTED** (2026-08-07): `_WIFI_DETECT_PS` used to enumerate only `Status -eq 'Up'` adapters, so on a laptop sitting on the cable — the exact machine where a tech ticks "I'll switch to Wi-Fi during the fix" — no adapter was found, nothing was protected, and **no package could land in the preview's `wifi` group**, i.e. the Wi-Fi checkbox visibly did nothing to the delete list. `detect_wifi_state` now reports `present` (a Wi-Fi card exists) separately from `wifi` (it is associated): `wifi` still decides whether the dialog pre-ticks itself, `present` decides whether there is anything to protect once the tech ticks it by hand. An `Up` adapter always wins the pick, so a disabled second card cannot displace the working one. Since `collect_wifi_protection` is only consulted by the delete phase **in Wi-Fi mode** (the preview always calls it and lets the UI decide), the widening cannot protect anything the user did not ask for. It also logs a WARNING when a Wi-Fi card exists but no third-party package matches it — otherwise the "the switch locks nothing" report is unanswerable.

The adapter is identified with `Get-NetAdapter`/`Get-NetConnectionProfile` (structured objects), **never `netsh wlan show interfaces` text** — that output is localized, and this project already has a scar from parsing localized console text (see the Hungarian pnputil stems in `delete_succeeded`). **Remembering the Wi-Fi password and auto-reconnecting** is part of the deal, and it has three moving parts, all of which were needed: (a) `export_wlan_profiles` saves every WLAN profile *with its key* before deletion; (b) the **active SSID is persisted to `autofix_stats.json` (`wifi_ssid`), not just to the instance** — the legs are separate processes, so the original `self._autofix_wifi_ssid` was always empty by the time `_autofix_recover_wifi` ran on the install leg, and the rescue could not tell which of the saved networks to return to (found 2026-08-05 while wiring this up); (c) the remembered network is forced to `connectionmode=auto` (`wlan_set_autoconnect`) — the chain does 3–4 **unattended** reboots, and a customer profile set to manual connect would bring the machine up with no network every single time, no matter how well we remembered the password. The reconnect itself is two-stage: first a plain `wlan_connect` with the remembered SSID (the common case — profile and key are intact, Windows just did not re-associate), and only if that fails the full profile re-import, which is what covers the orphaned-profile case (new interface GUID after a driver reinstall). Both the post-reboot path and the closing driver-swap path go through the same `_autofix_recover_wifi`. **`key=clear` is deliberately NOT passed** — that would write the customer's Wi-Fi password to disk in plaintext; without it the keyMaterial stays DPAPI-encrypted, which re-imports fine on the same machine+user (the resume legs run as `-UserId $env:USERNAME`, so that holds), hence `netsh wlan add profile … user=current`, not `user=all`. `clear_wlan_backup()` deletes the folder at the end of the chain — no network profile files are left on a customer machine. The checkbox is **auto-detected**: `get_autofix_net_state()` pre-ticks it when the machine is on Wi-Fi *and* has no active wired link (the dialog opens instantly and the tick arrives asynchronously, since the detection is a PowerShell call). Like every other dialog choice it rides the chain as a flag appended by **`_schedule_autofix_resume` itself, never by the call sites** — offline-tested over all 16 checkbox combinations. UI: deliberately a **bigger, highlighted block** above the three small toggles (`mc-wifi-mode`), because it is not fine-tuning — it states what network the machine is on, and the whole chain's survival depends on it. GUI-only (the CLI AutoFix is one-shot with no reboot chain, so it has no legs to survive). **The protected package is still exported to `netdrv_backup`** even though it is never deleted — it is the rollback copy, it costs seconds, and its absence would be an offline customer machine.
- **Wi-Fi mode does NOT freeze the driver, and the old one is swept at the very end (`_replace_old_wifi_driver`, 2026-08-05, user's own design and it is the better one)**: the Wi-Fi opt-out skips **deletion only** — `filter_autofix_risky_devices` gates storage/firmware and nothing else, so the adapter stays in the WU matching *and* the catalog closing round and gets the newest driver like every other device. What the protection costs is therefore not "an up-to-date driver", only the strip-and-reinstall — which matters solely for a *corrupt* driver. The remaining gap is the leftover: after an in-place update the **old** package sits in the DriverStore. `auto_cleanup_duplicates` already removes it when the vendor kept the original INF name (`netwtw10.inf` v22 → v23, same group); it does **not** when the vendor *renamed* (`netwtw08.inf` → `netwtw10.inf`), because those are different groups. So at the very end of the chain — after the duplicate cleanup, before the summary — this step checks whether the adapter now runs on a **different** INF than the protected old one, and if so retires the old package. **The order is the whole point and must not be inverted into "download → delete → install"**: here the new driver is already installed and *proven working*, so the machine is never left without a network driver, whereas pre-staging leaves a window where it runs on neither. Five guards, any one of which keeps the old package (keeping it is never an error): the device must be on a different INF; the internet must work; the old published name must still map to the same original INF (renumbering guard); it must not appear in `get_active_published_infs` (`None` ⇒ do nothing); and the delete is a plain `pnputil /delete-driver` — no `/uninstall`, no `/force`, so anything still using it simply refuses. Connectivity is re-checked **after** the delete, and a loss is reported loudly with the USB→RJ45 remedy — the tech must see it, not the next customer. The closing summary states which of the two outcomes happened. Offline-tested over all ten branches.
- **Wi-Fi driver FULL REBUILD — the fifth checkbox (`--rebuild-wifi-driver`, `mc-rebuild-wifi`, 2026-08-06, explicit user decision)**: the rule above closes the "up-to-date driver" gap but not the *corrupt* one, and the difference is narrower than it sounds — it is exactly **the adapter's driver key** (Device Manager → Advanced: power saving, 802.11 mode, roaming aggressiveness). An in-place upgrade merges the new INF's values into the existing key and leaves everything it does not mention; only `/uninstall` detaches the driver from the *device*, which is what makes Windows rebuild that key from scratch. That matters because a classic field symptom — "the network printer keeps dropping" — is usually the adapter's power-saving setting, not the driver files. So with the box ticked the delete phase, **as its last action before the reboot**, runs `wu_core.rebuild_wifi_driver`: `pnputil /delete-driver <wifi.inf> /uninstall /force` → re-add from a **dedicated** backup folder (`netdrv_backup\wifi`, exported by `export_wifi_driver_backup`) → `/scan-devices` → `restore_wlan_profiles` → `_wait_for_internet(AUTOFIX_NET_WAIT_WIFI)`. Load-bearing details: (a) **the placement is the safety net** — the leg reboots right afterwards, so the existing post-reboot rescue (`_wait_for_internet` → `_autofix_recover_wifi` → `_restore_net_driver_backup`) heals any failure by itself; putting this at the *end* of the chain would leave a reboot-requiring driver (3010) offline with nothing left to run; (b) **the backup folder is separate from `netdrv_backup`'s root** — that root also holds the *wired* NIC's old package, which the chain deleted on purpose so WU can reinstall it fresh, and a `*.inf /subdirs` restore from the root would put it straight back; (c) **nothing is deleted unless there is something to restore** (`wifi_backup_has_inf`) and a failed removal never proceeds to the install, so the machine keeps a working driver in both cases; (d) the step is **skipped entirely when Wi-Fi mode is off** — the adapter's driver is then deleted with all the others in the normal phase, so the rebuild already happens; the UI shows the checkbox greyed-out-but-ticked on a wired machine because that is the truth, not a setting. Default **on** in both cases (explicit user decision: "ha nincs wifin akkor egész nyugodtan cserélheti"), unticking it in Wi-Fi mode falls back to the update-only behaviour with no connection loss at all. The passwords survive because `export_wlan_profiles` already saves **every** profile with its (DPAPI-encrypted, never plaintext) key and `wlan_set_autoconnect` forces `connectionmode=auto`. Offline-tested over all outcomes (success, no backup, failed removal, 3010, empty list) plus all 32 flag combinations of the propagation.

### Manual scan pipeline

- **Manual scan — hybrid pipeline (`app/gui/hwscan.py`)**: the scan now (1) surveys installed driver versions+dates once (`_get_installed_driver_info`, returns `{PNP: {'version','date'}}`) and shows "telepítve: X · date" next to every offer (offer side also shows `wu_date` from `DriverVerDate`/catalog row); (2) after a successful WU search runs a **catalog top-up** for error-coded devices WU returned nothing for — the pool is therefore MIXED (WU items carry `update_id`, catalog items carry `url`), so `install_selected_wu` is a **per-item dispatcher**: one `_safe_thread` worker creates a restore point, then calls `_install_wu_api_sync` then `_install_catalog_sync` (both return `(success, fail, cancelled)` and must NOT emit `task_start`/`task_complete` — the dispatcher owns the lifecycle), and on success emits `offer_rescan` (UI banner offering a new scan — chipset/USB drivers surface new devices); (3) emits a `problems` list (devices with `ConfigManagerErrorCode` ≠ 0, code descriptions in `PNP_ERROR_CODE_DESCRIPTIONS`, `has_fix` flag, `pnp_id`) rendered as a red section in the UI so unresolved devices are never silent — rows with quick-fixable codes get a button calling `fix_problem_device(pnp_id, code)` (22 → `Enable-PnpDevice`, others → disable+enable cycle; synchronous, deliberately bypasses `_task_busy`). The old catalog install path downloaded every cab TWICE (a vestigial sequential loop + the threaded worker) — the sequential loop was removed; don't reintroduce it.
- **Manual scan — WU-API timeout policy & Catalog fallback (`app/gui/hwscan.py`)**: `_search_wu_api` runs the WUA search with a 300s timeout; on timeout it restarts the WU services (that heals the *next* search) but deliberately does **NOT** retry the search itself — field-proven (cloned Windows on brand-new AM5 hardware, 2026-07, twice in a row) that the post-restart retry times out identically, doubling the wait to ~10.5 min for zero benefit. Callers handle the `None` return on their own: manual scan falls back to the Catalog, AutoFix breaks out of the WU rounds (and still runs its catalog closing round). The **Catalog engine** (`_catalog_fetch_rows`/`_catalog_find_driver`/`_catalog_search_collect`; `_catalog_search` is the pool-appending wrapper) scrapes `catalog.update.microsoft.com` on 10 threads, and per device queries **all of its *specific* HWIDs** (max 4; `wu_core.is_specific_hwid`, 2026-07-28 — **type-code IDs are never used as a search key**, and a device with no specific ID at all is skipped with a DEBUG line naming the IDs). That rule exists because the Catalog answers a type code with *any vendor's* package for that type, and once round 3 lost its device-level filters the damage was immediate and measured on an Intel Q170 box: `ACPI\PNP0501` (serial port) returned an **LG** package, `ACPI\PNP0A08` and `USB\ROOT_HUB30` each returned an **AMD** package — on an Intel machine. The USB hub is the instructive one: it *has* an Intel-specific ID (`USB\ROOT_HUB30&VID8086&PIDA12F`), but the AMD row pulled in via the generic key had a newer date and won the row selection. Filtering the *query key* rather than the *device* removed all four bogus hits, kept every legitimate one, and halved the round (13.9s → 6.9s). Do not "fix" a wrong-vendor catalog match by excluding the device — check whether a type code got used as a key. The synthesized base ID goes through the same test) plus the synthesized **base vendor HWID** (`wu_core.base_vendor_hwid` — strips `&SUBSYS_`/`&REV_`/`&CC_`), then **unions every returned row into one candidate set** before choosing. Both halves of that are load-bearing and were measured (2026-07-24, Realtek ALC892): (a) the old code stopped at the *first* HWID that returned rows and its comment claimed a more generic HWID "would return the same" — false, the SUBSYS-scoped key returns a 2021 package (6.0.9136.1) while the base key returns the 2026 one (6.0.9992.1); (b) the device's own `HardwareID` list contained **only** SUBSYS-scoped IDs, so without synthesizing the base key that newer package is unreachable entirely. Rows are **scored for the host OS/arch** (`_catalog_row_score` on the tag-stripped `<tr>` text: arm64 rows excluded on x64, Win11-only rows excluded on Win10, Server rows deprioritized; if every row is excluded it falls back to all rows) **[2026-09-28: the catalog's OS label is NOT reliable in either direction - measured on AMD GPIO 3.0.5.0 (labelled "Windows - Client, version 21H2", scored 1, INF Win11-only) and 3.0.3.0 (labelled Win11, INF `NTamd64` = Win10-OK). The row score stays a cheap pre-filter; the verdict is the INF `[Manufacturer]` decoration checked after download (`wu_core.inf_os_applicable`), and a fallback-only winner carries `os_label_ok=False` so it can never displace a WU offer. See the Build 344 section.]**, and among the best-scoring rows the **newest `Last Updated` date wins, with version only as the tiebreak** — *not* highest version: one vendor ships mutually incomparable version schemes for the same device (measured on the Realtek NIC: `Realtek - Net - 1168.19.704.2024` from 2024-07-03 vs `Realtek Net Driver Update (10.79.50.1003)` from 2025-10-02 — by version the 2024 package "wins" by three orders of magnitude). `wu_core._parse_driver_version` (tiebreak only) counts only ≥3-component number sequences as versions, so "2.5GbE" doesn't parse as 2.5; row order on the catalog page is NOT newest-first; it lives in `wu_core` because the AutoFix duplicate/verification filters use it too. Results **that are not a newer *release* than the device's currently installed driver are skipped** (`_get_installed_driver_info`) — without this the fallback re-offered a driver installed 3 minutes earlier, and this same filter is what makes the AutoFix catalog closing round terminate (the WU API path doesn't need it: the server applies `IsInstalled=0`). **"Newer" means newer by DATE, with the version only as a same-date tiebreak** — one shared definition for the whole project, `wu_core.is_newer_release` / `release_rank` (**explicit user decision, 2026-07-27**: "kit érdekel milyen verziót adnak neki, ha dátum szerint van újabb, az mehet fel"). This gate was the last purely version-based decision on the install path (the WU side's `_filter_wu_downgrades` and the catalog's own row selection were already date-first), and the mismatch cost real drivers: measured on the field machine, AMD SMBus sat on **5.12.0.38 from 2017-08-30** while the catalog offered `System Driver Update (2.0.0.26)` from **2025-12-03** — by version the 2017 package "wins" and the box kept a driver eight years old. Do not revert this to a version comparison. Two properties make it safe, both verified against that log: (a) it does not loop, because the catalog's *Last Updated* runs a day **behind** the installed INF's DriverVer date for the same package (AMD PCI `2025-09-08` vs `2025-09-09`, AMD PSP `2026-03-15` vs `2026-03-16`, Realtek NIC `2025-10-02` vs `2025-10-03`), so every already-current package still evaluates to "not newer"; (b) **when the installed driver is an inbox one and the device is not a `generic_ok` candidate, the date rule is skipped and the old version comparison stands** — an inbox driver carries a Windows date (`input.inf` says 2006-06-21), so date-first would silently turn the deep scan into a generic→vendor swapper on exactly the classes (HID, keyboard, mouse) that `mark_generic_replace_candidates` deliberately excludes, and without its rollback verification. That decision stays where it belongs. When date and version disagree the choice is logged at INFO (`[CATALOG] Dátum szerint ÚJABB, verzió szerint nem`), because "why did it install a lower version number?" is otherwise unanswerable from a paste. Install (`_install_catalog_sync(pool, task_id=...)` — task_id lets AutoFix reuse it on the 'autofix' channel) goes cab-download → `expand` → INF-presence check → `pnputil /add-driver /install` (or `dism /Add-Driver` for offline target). **A pnputil "success" is only a real install when something *new* actually landed**: `Added driver packages: 0` (nothing applied) AND the "already exists in the system" case (every `added successfully` line is a re-add of a package already staged in a previous leg — `Added driver packages: N` with N>0 but all marked `(Already exists in the system)`) are both treated as **no-ops** (counted as skipped, never success). The second check is not optional — a generic-replace candidate that stages fine but never *binds* (field: Realtek UAD audio stays on `hdaudio.inf`) would otherwise report "1 installed" every leg forever, an infinite reboot loop (field-seen, Build 228, capped only by `AUTOFIX_MAX_INSTALL_LEGS`). With the no-op detection the candidate installs once, and on the next leg its package is already in the store → 0 installs → the chain terminates on its own. **A pnputil "added successfully" is not proof the device took the driver, either** (2026-07-25, two cases in one run): the Catalog answers a *base* vendor HWID (`HDAUDIO\FUNC_01&VEN_10EC&DEV_0892`) with every OEM-specific variant of that chip, and newest-date wins — which handed an ASRock board a **Clevo-laptop** Realtek package. It staged fine (`Added driver packages: 4`) and never bound; the device stayed on `hdaudio.inf`. Same run, an NVIDIA catalog package (32.0.15.9595) lost to the incumbent 32.0.15.9186 because that one matches a **more specific** HWID (Windows ranks specificity above version/date). Both reported `✅ telepítve`, and the chain re-downloaded them every leg. Two guards now: (a) **before** install, `wu_core.inf_package_applies(ext_dir, dev_hwids)` scans the extracted INFs for a HWID matching the device's *real* `all_hwids` (returns `None` = undecidable → never blocks); (b) **after** install, the device's INF is re-read and compared against `installed_inf` captured at search time — unchanged means it didn't bind, so it counts as **skipped, not success** (crucial: a false success chains another AutoFix leg). Installs that returned `3010`/"reboot is needed" are exempt from (b) — they legitimately bind at next boot (field: AMD PSP). Non-binding items land on `self._catalog_no_bind`, which the AutoFix round persists to `catalog_no_bind` in `autofix_stats.json` so later legs don't re-download them, **and which the closing summary now names to the user** (`_emit_catalog_no_bind`): these are packages the chain proved to exist and be newer, so silently discarding them with the stats file left the shop with no idea a newer driver was available — the remedy (vendor card for a GPU, board vendor's page for onboard devices) is actionable, so it must be printed. **Guard (a) may only veto when we actually parsed the right INF** (2026-07-27, RTX 3060): a driver cab holds several INFs, and `_read_text_best_effort` returned *nothing usable* for the NVIDIA display INF while the ANSI `nvhda.inf` parsed fine — so `inf_ids` was non-empty (158 HDAUDIO ids) and the "no match" branch vetoed a **legitimately newer** package (catalog 32.0.15.9595 > installed 32.0.15.9186), after downloading 1.1 GB for it, on two separate legs. Two rules came out of it: `_read_text_best_effort` now detects **BOM-less UTF-16** (the `latin-1` fallback never raises, so such a file decodes "successfully" into `P\x00C\x00I\x00…` and silently yields zero ids), and `inf_package_applies` returns `None` instead of `False` when **not one** extracted id sits on the device's own bus (device is `PCI\…`, ids are all `HDAUDIO\…` ⇒ we did not read the INF that matters). That bus test is what keeps the Clevo-Realtek case working — there the device *and* the INFs are both `HDAUDIO\`, so the veto still fires. Both functions log per-INF id counts, because "which INF did we actually read?" is the only question that could have settled this from the field log.

  **THE CATALOG PAGINATES AT 25 ROWS, AND THE UNSORTED FIRST PAGE IS NOT A STABLE SAMPLE — always request `&scol=DateComputed&sdir=desc`** (2026-08-06, field log + live measurement). `_catalog_fetch_rows` used to issue one unsorted `Search.aspx?q=<hwid>` and decide from whatever 25 rows came back.   **A CATALOG TIE IS DECIDED FROM THE DETAIL PAGE'S `Driver Model` FIELD, BEFORE DOWNLOADING** (2026-08-06). `ScopedViewInline.aspx?updateid=<guid>` is a few KB and carries `Driver Model: NVIDIA GeForce RTX 3090,…,NVIDIA GeForce RTX 3060,…` — the only pre-download signal of which tied row is meant for this machine. `wu_core.driver_model_rank` scores it 2 (an entry equals the device name) / 1 (containment, or ≥3 shared tokens) / 0, and is used **only to reorder, never to veto** (the field's fuzzy naming — catalog `Realtek High Definition Audio` vs Windows `High Definition Audio Device` — would make a veto lose real drivers). Two guards the offline test forced: the probe **stops at the first exact match** (a tie can be 45 rows — measured on the Realtek NIC — and a fixed probe window could exclude the right row; the test caught exactly that with the correct row at index 7), and the token rule requires a **digit-bearing token in common** when either name has one, otherwise `RTX 4070` "matches" a list of RTX 30-series cards on the shared words `nvidia geforce rtx`. Probing runs *after* the release gate, so it only costs requests on devices we were going to download for anyway.

  **A ROW FOUND VIA THE DEVICE'S OWN SUBSYS KEY BEATS A NEWER ROW FROM THE GENERIC KEY — and on an inbox-driver device an OLDER release is a legitimate fallback** (`spec_by_guid`, `CATALOG_INBOX_FALLBACK_CANDIDATES`, 2026-08-26, field-proven + measured live). `_catalog_find_driver` queries up to 4 HWIDs and **unions every row into one pool**, after which date alone picks the winner. Measured on an ASRock B450M with a Realtek ALC897 (`HDAUDIO\FUNC_01&VEN_10EC&DEV_0897&SUBSYS_18494897`, sitting on inbox `hdaudio.inf`):
  - the device's **own SUBSYS key** returns `Realtek - MEDIA - 6.0.9360.1`, and that package's INF lists **`…DEV_0897&SUBSYS_18494897` verbatim** (145 ASRock ids in it) — it is exactly the right driver;
  - the **generic key** (`…DEV_0897`) returns a *newer* `Realtek … (6.0.10007.1)`, whose INFs are `HDXACERAIO.inf`, `HDXACPAcer.inf`, … — an **Acer** build whose 332 `DEV_0897` entries are all `SUBSYS_1025xxxx` (1025 = Acer) with **zero** generic and **zero** ASRock ids.
  Date-first therefore crowned the Acer package, `inf_package_applies` correctly vetoed it, and the tie-only fallback rule ("a fallback can never be an older release") meant the correct package **was never reachable** — the machine kept Microsoft's generic audio driver while the right driver sat at position 1 of its own search key. Two changes, and note what each is *not*: the winner is still chosen date-first (that stays an explicit user decision), and a device already on a **vendor** driver keeps the old same-date-only behaviour so it can never be downgraded. What changed is only the **fallback list on an inbox-driver device**: it now also admits older releases, ordered **most-specific HWID first, then newest date** (`spec_by_guid` records which of the 4 keys produced each row). Explicit user decision: *"a semminél, az inbox drivernél jobb a régi driver milliószor… ha semmit se tud feltelepíteni, akkor azt ami jó hozzá, de verzióban régebbi, azt rakja fel — és ez ne csak a hangra legyen igaz, MINDENBŐL mindennél legyen ez a szabály"*. Cost in practice is nil: offline-tested against the real rows, the correct package becomes the **first** fallback, and the installer already dedupes by resolved URL and skips packages the persistent no-bind store proved wrong. The measurement that settles the "should we just page deeper?" question: 12 pages / 300 rows of the generic key are **all** published by "Realtek Semiconductor Corp." yet OEM-specific inside (**PONTOSÍTVA 2026-09-02, újramérve — a korábbi "az ASRock egyáltalán nem publikál a Windows Update-re" megfogalmazás FÉLREVEZETŐ VOLT**: a katalógus az ASRock-specifikus `…&SUBSYS_18496893` kulcsra **41 csomagot ad**, 2017-05-26 és 2021-03-22 között [évenként 2017:7, 2018:4, 2019:12, 2020:16, 2021:2], a legfrissebb a `Realtek - MEDIA - 6.0.9136.1`, amit a lánc meg is talál és fel is rak. Ami igaz: a **kiadó** mindegyiknél a Realtek, nem az ASRock — ASRock nevű publisher tényleg nincs, de ASRock-ra indexelt csomag bőven van. Aki ezt "nincs hozzá driver"-ként olvassa, téved.) — so depth was never the problem, ranking was. **A mélyítés haszontalansága 2026-09-02-én újra lemérve, és megerősítve:** a SUBSYS-kulcs 3 lapon (deep) **41 sort** ad, 12 lapon szintén **41-et** — vagyis ott nincs "hátul maradt" csomag, a program mindet látja. Az ÁLTALÁNOS kulcson a mélyítés valóban hoz többet (3 lap = 75 sor [2025-12-01..2026-07-13] → 12 lap = 300 sor [2024-12-26..2026-07-13], 20,6 vs 10,8 mp), de azok a sorok más gyártók OEM-változatai, tehát a nyereség ott nulla. Ezért marad a `CATALOG_MAX_PAGES` = 3 az általános kulcson, és a mélyítés kizárólag az inbox-driveres eszköz SAJÁT SUBSYS-kulcsán.

  **AN INF VETO NOW FALLS BACK TO THE NEXT TIED CANDIDATE — but candidates are deduped by DOWNLOAD URL, which is what makes it safe** (2026-08-06). `_catalog_find_driver` returns `alt_candidates` (same score, **same date**, so a fallback can never be an older release than the winner), and `_install_catalog_sync` walks them when `inf_package_applies` returns False, up to `CATALOG_MAX_CANDIDATES` = 3. The dedupe is not an optimization, it is the thing that stops this fix from being worse than the bug: measured live, **the top five tied rows for `PCI\VEN_10DE&DEV_2504` all resolve to the identical cab** (same filename, same 1165.1 MB, same 4-INF list) — the catalog publishes one package as several per-OS-branch entries, so a naive fallback would have downloaded the same 1.2 GB three times. The URL is known only after the (few-KB) `DownloadDialog` call, so the skip is free. A **download** failure never advances the candidate (the network is at fault, not the package). Every vetoed candidate is recorded with its GUID, so a later run skips it without downloading at all.

  **How the 2026-08-05 NVIDIA case actually resolves** — worth knowing before someone "fixes" the veto again. The chain downloaded 1.2 GB, `inf_package_applies` rejected the package, and it was reported as no-bind. Verified afterwards with a 2 MB HTTP range read of the cab header (the CFFILE table sits at the start of a cab, so the file list is readable without the payload): the package contains exactly **`nvhda.inf`, `nvle.inf` (346 KB — the display INF), `nvpcf.inf`, `nvppc.inf`** — so the extraction was complete and the veto was not the truncated-download case. Our parser was independently cleared: run against the installed `nv_dispig.inf` it reads **208 ids, 207 of them PCI, and it does match `PCI\VEN_10DE&DEV_2504`** (the desktop INF lists the bare id), and it reproduces the field log's counts exactly for the companion INFs (`nvhda`=104, `nvpcf`=0, `nvppc`=4). `_INF_HWID_RE` is `re.IGNORECASE`, so casing is not a factor either. What is *not* settled: the catalog's own metadata claims RTX 3060 support for that package while `nvle.inf` yields 50 ids that do not match this card — reading `nvle.inf` itself would need the full 1.2 GB (it sits at uncompressed offset ~1.34 GB in a single-folder cab). Practical impact is nil either way: the vendor card offers 610.88 against the catalog's 595.95. **Do not "solve" this by weakening `inf_package_applies`** — the Clevo-Realtek case is what it exists for.

**Catalog cab downloads get 3 attempts, not one** (2026-07-27): these payloads are hundreds of MB (a GPU package is 1.1 GB), so a mid-transfer `[WinError 10054]` ("connection forcibly closed by the remote host") is ordinary, not exceptional — in the field one killed the NVIDIA download after 18s and it was booked as a permanent failure, while the identical URL came down fine on the next leg. Retries pause 3s and **delete the partial file first** (same reasoning as the stresstools.zip rule: the leftover eats exactly the disk the retry needs), and each attempt logs its number and the final byte count. **The attempt loop covers download + size check + expand + INF-presence, not just the download** (2026-07-28, field log from the dev box): a server can close the connection early *without* an exception — `http.client` returns a short read silently on chunked reads — so the NVIDIA cab arrived as 139 MB of 1,221,644,925 bytes and was logged as `Letöltve … 1. próbálkozásra`; `expand` then failed with rc=1, **which nothing checked**, and the failure surfaced as the misleading permanent error "nincs .inf a csomagban" while the retry designed for exactly this never fired. Hence: (a) the received size is compared to `Content-Length` and a short file is a failed attempt; (b) an `expand` rc≠0 or an INF-less tree is also a failed attempt (corrupt cab → delete cab + ext dir, re-download), not a terminal error. The catalog `pnputil /add-driver` call passes `ok_codes=(0, 259, 3010)` — 259 (no-op/up-to-date) and 3010 (reboot required) are expected outcomes the code already branches on, and they produced 4 false WARNINGs in an otherwise clean field run. `.msu` links go through `wusa /quiet /norestart` (offline: `dism /Add-Package`), `.exe` links are skipped with a clear message (never silently run an unknown installer). **Multi-INF packages: the unused INFs are unstaged right after install** (`_cleanup_unused_staged_infs`, 2026-07-28, field-seen on the dev box): `pnputil /add-driver <dir>\*.inf /subdirs /install` stages EVERY INF in the package whether or not any present device matches it, and one Razer catalog cab carries the whole Razer product line as separate INFs — a single AutoFix run inflated the machine from 19 third-party packages to **219** (measured: 201 staged `rz*` INFs, none bound to any device). The pnputil output tells each INF's fate per block: an INF with an `installed on device` / `up-to-date on device` line is in use by a present device and **stays**; the rest are deleted with a plain `pnputil /delete-driver` (no `/uninstall`, no `/force` — if anything does use one, pnputil refuses and it stays, which the logic tolerates). Runs only for multi-INF packages (a single-INF no-bind is the bind-check's job). **On a reboot-required install (3010) the verdict is DEFERRED, not skipped** (2026-08-05 — the original code just did nothing there, and that hole cost a machine 120 packages): the binding really does settle at next boot, so judging now would be wrong — but *dropping* the package meant its unused INFs stayed in the DriverStore **forever**, since nothing ever came back to them. Field-proven (Dell Latitude 7400): the `Intel(R) PCI Express Root Port #13 - 9DB4` catalog cab carries Intel's **entire** chipset INF collection (ApolloLake, Avoton, Baytrail, Braswell, Broadwell, ColetoCreek, CougarPoint, Crystalwell, Denverton, FPGA, Haswell, IceLake, IvyBridge, IvyTown, JakeTown, KabyLake…), returned 3010, and the machine went from **23 third-party packages to 163** — 143 even after the closing duplicate cleanup, which cannot touch them (they are not duplicates: every one has its own original INF name). Side effect worth remembering: `dism /Get-Drivers` went from 0.6 s to **77 s**. So `defer=True` now records every published INF of that package into **`pending_inf_cleanup.json`** (`_app_data_dir()`, deliberately *not* `autofix_stats.json` — that dies with the chain), and `_finish_deferred_inf_cleanup()` settles it **after a real reboot**: at the start of the next install leg, and — for a deferral in the *last* leg — from a background thread at the next app start (guarded by a file-existence check, so a normal start costs nothing; skipped on resume legs so two pnputil delete runs can't collide). It re-decides from **live system state**, never from the stale pnputil output: the active published-INF set is the judge, and the same-`original`-INF-name check from `_finish_pending_deletes` prevents a renumbered `oemNN.inf` from taking out a fresh package. **The deferral is not paranoia — it is load-bearing**: in that same field log `oem106.inf` (`iaLPSS2_GPIO2_CNL`) showed no `installed on device` line at install time and *did* bind after the reboot, so an immediate cleanup would have deleted a driver the machine uses. All eight branches offline-tested against the log's verbatim pnputil output. pnputil still enforces signature + INF applicability, but catalog matching is inherently less precise than WUA's server-side evaluation: it's the B-plan for machines where the WU Agent is broken, not full parity.
- **Persistent no-bind memory (`catalog_no_bind.json` in `_app_data_dir()`, 2026-07-28)**: the chain-scoped `catalog_no_bind` list in `autofix_stats.json` dies with the chain, so the manual scan run right after a finished AutoFix re-offered — **pre-selected** — the very packages the chain had just proven don't bind (field log, 2026-07-28: 4 of the 5 manual-scan catalog hits were exactly the chain's no-bind list: Clevo-Realtek audio, Razer USB composite, AMD ISA bridge, NVIDIA 32.0.15.9595 — and the user reasonably read that as "AutoFix left drivers uninstalled"). `_install_catalog_sync` now records every no-bind/veto item (key: `(pnp_id, wu_title)`, with reason + date) into the persistent file via `_no_bind_record`, and `_catalog_search_collect` marks matching hits `prev_no_bind` — the UI shows them **unticked** with a `↷ korábban nem vette át az eszköz` badge. Three deliberate limits: it only *marks* (the user can still tick and retry — a wrongly recorded package must stay reachable); the AutoFix rounds do **not** consult it (a fresh chain deletes+reinstalls drivers, so re-trying there is correct, and its own stats list already prevents within-chain repeats); and a later install that the bind-check **verifies** as taken removes the entry (`bound_ok` → `_no_bind_record` removal), so the file can't go stale-forever. A *newer* catalog release has a different title, so it is never masked by an old entry. **Since 2026-08-06 the record also carries the catalog `guid` and the release `date`, and matching is release-aware**: an entry masks (a) the same GUID, (b) the same title, or (c) **an older-or-equal release of the same package family** (`wu_core.catalog_title_family` strips the trailing `(version)`), compared with `release_rank`. Case (c) is the 2026-08-05 field case: the closing round offered the Realtek audio as `6.0.9992.1` [2026-05-18] while the recorded failure was `6.0.10007.1` [2026-06-22] — a different title, so the old key missed it and the chain re-downloaded the same Clevo package. A genuinely **newer** release is still never masked (the vendor may have fixed it). The GUID is also what lets `_catalog_find_driver` drop a known-bad candidate *before* resolving its URL. **The strongest key, however, is the download URL, and it is the one that actually stops the repeat**: measured 2026-08-06, the catalog lists one NVIDIA cab under **25 separate entries** (25 GUIDs, 25 titles), so a GUID/title ban only pushes the next run onto a different entry pointing at the same 1.2 GB file. The record therefore stores `url` too, and `_install_catalog_sync` seeds its per-device `tried_urls` from the store — so a package already proven inapplicable for that device costs **zero** bytes on every later run (the few-KB `DownloadDialog` resolve is all that happens). URLs carry a content hash, so a genuinely newer release gets a different URL and is still tried. **The skip must live in `_install_catalog_sync`, NOT in `_catalog_find_driver`** (Build 264 field run, 2026-08-06): the same chain downloaded the Clevo Realtek package twice — `6.0.10007.1` [2026-06-22] in the catalog round and `6.0.9992.1` [2026-05-18] in the closing round — because they are different titles *and* different URLs, so neither key matched. The family rule (`catalog_title_family` + `release_rank`) closes that, but only at install time: putting it in the search would make the hit **vanish from the manual scan list**, and the standing rule is that we only ever *mark* a known-bad package (unticked + badge), never hide it. One more restriction: the family skip applies **only when the recorded reason was the INF veto** (`nem alkalmazható`) — that is a fact about the INF that a fresh chain cannot change; a recorded *bind* failure can change, so those are always retried. The search side keeps only the exact-GUID filter, and even that never empties the candidate list.

  **A log line on a hot path is measured, not estimated** (same run): the new `[CATALOG] Lekérdezés:` line produced **448 lines, of which 412 were `-> 0 sor`** — 92% noise in a 5 MB rotating file, which is exactly what the Rule-0 counter-rule forbids. It now logs only when the query returned rows (DEBUG) or when something unusual happened — paging or a lost sort (INFO). A zero-row query is not lost information: `install_call_logging` already records every call with its HWID, and the per-device `Döntés` line summarizes the outcome.

Ha bármelyik szűrő változik, mindhárom helyet nézd meg. ~~**A KÉZI SZKEN IS KIÍRJA, MI MARADT A WINDOWS BEÉPÍTETT DRIVERÉN**~~ (`inbox` a `hw_scan_result`-ban, `renderHwInbox`, 2026-08-31, explicit user decision: *„írja már ki a program hogy hány driver fut a windows beépített generikus driverén… hogy tudjam mik nem kapnak drivereket"*). Ez a szken **legcsendesebb kimenetele**: az eszköz hibakód nélkül működik, csak épp a Microsoft általános driverén — tehát a találati listán SEHOL nem jelenik meg, mert nincs rá találat. Eddig ezt csak az AutoFix záró jelentése mondta ki, a kézi szken után a technikusnak nem volt honnan tudnia. **UGYANAZT a szűrőt hívja, amit a záró jelentés** (`_health_report_worth_listing`) — két külön lista előbb-utóbb ellentmondana egymásnak ugyanarról a gépről. A szűrő szándékosan szűkebb, mint a keresésé (a katalógust mindenre megkérdezzük, de csak azt írjuk ki, amivel a szerelőnek TEENDŐJE lehet); a többit egyetlen szám összegzi, a *„ehhez gyári driver nem is létezik"* magyarázattal. Amire van találat a listán, az zöld jelet kap: ott nincs teendő, elég feltelepíteni a szken eredményét.
- **"Vendor driver instead of the Windows generic one" (`wu_core.mark_generic_replace_candidates` + the `generic_replace` flag; used by BOTH the manual scan and AutoFix)**: the WU Agent never offers a replacement for a device Windows considers fine, so a machine can finish a flawless AutoFix chain with its onboard audio on Microsoft's generic `hdaudio.inf` and its NIC on the inbox driver — while the chip vendor's own package sits in the Microsoft Update Catalog (measured 2026-07-24, ASRock B450M Pro4: Realtek MEDIA 6.0.9992.1 and Realtek Net 10.79.50.1003 both present in the Catalog, zero offers from the WU Agent). Devices whose current driver is inbox (`_is_inbox_driver`) are therefore marked `generic_ok` and fed to the Catalog engine alongside the error-coded ones — the manual scan lists them with a `🏭 most Windows alapdriver → gyári elérhető` badge (pre-selected, the tech can uncheck), the AutoFix closing round installs them automatically. Rules that must not be softened:
  - **For a marked device the version comparison is SKIPPED entirely.** An inbox driver's version is the Windows build (`10.0.26100.8457`) and the vendor's is its own scheme (`6.0.9992.1`), so the generic always looks "newer" and the better driver would always lose. Same trap the WU path already handles in `_filter_wu_downgrades`. This cannot loop: after a successful install the device runs on `oemNN.inf` with a vendor provider, so `is_generic_replace_candidate` no longer marks it (and `added_zero` already guards the AutoFix reboot loop).
  - **Candidate selection has NO class filter** (2026-07-28, explicit user decision — "ITT IS MINDENT KERESSEN, kivéve amit checkboxszal nem engedek"). It used to carry both a 16-entry class whitelist (`GENERIC_REPLACE_CLASSES`) and a class blocklist (`GENERIC_REPLACE_BLOCKED_CLASSES`); **both constants are gone**. What killed them was an asymmetry nobody could defend: a printer / keyboard / USB controller sitting on a Windows inbox driver was never asked about here, while the *same* device on a vendor driver was picked up fine by the deep scan — i.e. a device got no better driver *because* it was on a worse one. What remains is **only** the two checkbox-gated risk classes, exactly as in the WU path and the deep scan (`is_generic_replace_candidate(dev, inst, allow_storage=, allow_firmware=)`; manual scan passes True/True with the red badge, AutoFix passes the dialog's values). **The bus-enumerator INF blocklist and the vendor-coded-HWID requirement were removed from this round too** (same day, same decision: "menjen ki minden driver, mindenre keressen, maximum nem talál"). Measured live on an Intel Q170 box: candidates went 6 → 66, the round took **6.9s on 10 threads**, and it found **two genuinely new packages the old filters had been hiding** — `Intel - System 11.7.0.1019` on a `machine.inf` "Motherboard resources" node and `Intel - System 9.21` on the HD Audio *controller*. So the old belief that these devices "have no vendor driver at all" was simply wrong for chipset nodes. If this round ever gets slow, the fix is more threads or a result cache — **not** a new device filter. **Consequence to keep in mind: with the storage checkbox ON, this branch can swap the inbox NVMe/AHCI driver for a vendor one, and `_verify_generic_replacements` cannot catch that failure** — it surfaces at the next boot. That is the informed trade the checkbox exists to offer (its warning text names recovery media); it is not a reason to reintroduce a class ban. **Processor is a measured non-candidate, not a banned one** (2026-07-28, live query): a CPU enumerates as `ACPI\GenuineIntel_-_Intel64_Family_6_Model_94` and the Catalog returns **0 rows** for it (and for `ACPI\ACPI000C`), while the PCI chipset device on the same machine returned 25 — so the AMD/Intel "chipset driver" reaches the box through its PCI devices (rounds 1 and 4), never through the processor node. Relaxing `_VENDOR_HWID_RE` to admit `ACPI\` would buy network round-trips and nothing else. **Display is NOT excluded** (and the code comment claiming it was is gone as of 2026-07-28): there is no class list left to exclude it from — this branch only ever runs on a device *currently on an inbox driver*, i.e. a machine stuck on the Microsoft Basic Display Adapter, where the "the vendor card is a better source" argument has nothing to work with (AMD/Intel are link-out only and the NVIDIA check runs in the manual scan alone). On a machine already on a vendor GPU driver the device is not a candidate at all, so the vendor cards keep their monopoly exactly where it matters.
  - **Every replacement is verified and rolled back if it fails** (`_verify_generic_replacements`, runs after the batch): the published `oemNN.inf` names are captured from the pnputil output, the devices' `ConfigManagerErrorCode` is re-read once the PnP stack settles, and any device that went error-coded gets its freshly installed package deleted + a rescan, at which point Windows re-binds the inbox driver automatically. **Error code 0 alone is not success** — it also re-reads the device's INF, because a package can install cleanly while the device stays on the Microsoft driver (field 2026-07-25: the run printed `✅ gyári driver működik` for the Realtek audio and, minutes later in the same summary, correctly listed that device as still on `hdaudio.inf`). Still-inbox after install is reported as a warning, not a success, and nothing is rolled back (the generic driver never left). A device that vanished from the present-device list is reported but **not** rolled back (typically an unplugged USB device — don't discard a good driver over a query miss). This "try it, verify, revert" net is only sound because the inbox driver never leaves the machine, which is exactly why the storage exclusion above is not negotiable.
  - **A COMPOSITE USB PARENT IS NOT A GENERIC-DRIVER DEVICE, and a package that binds to its CHILD interface is a success** (2026-08-06, field log + screenshot). `usb.inf`/usbccgp is the *correct* driver for a multi-function USB parent — its job is to split the device into `&MI_00`, `&MI_01`… children, and the vendor driver goes on those children, which Windows enumerates (and this program searches) separately. Treating the parent as "stuck on a Windows generic driver" produced two field symptoms in one run: the Razer parent (`USB\VID_1532&PID_00B9`) got a catalog package that staged **200 unused INFs** (all of which then had to be unstaged) and was reported as *"az eszköz a Windows driverén maradt (usb.inf) - nem valódi csere"* — a verdict the parent can never pass; and the Creative parent (`USB\VID_041E&PID_3274`) was re-offered **pre-ticked** on every scan even though its package was already installed on the child (`pnputil` said so in as many words: `up-to-date on device: USB\VID_041E&PID_3274&MI_00\…`). Two changes, and note what they are *not*: `wu_core.is_composite_parent` makes such a parent **not a generic-replace candidate** (the device stays in every search — the deep scan still queries the catalog for it — we simply stop claiming its driver needs replacing, and the ordinary version gate then declines the no-op offer), and the post-install bind check accepts a bind **anywhere in the device's own family** (`wu_core.pnputil_bound_devices` + `package_bound_to_device_family`, matching the `USB\VID_xxxx&PID_yyyy` / `PCI\VEN_xxxx&DEV_xxxx` stem against the instances pnputil names). This is not a device filter and must not become one — see the governing rule.
  - **Ugyanez a Creative eszköz, harmadik tünet (2026-10-11, Build 368, élő napló a fejlesztőgépen): téves „a KÖTÉS hiányzik” + fölösleges újrakötés-ajánlat.** 20:51:57–20:52:03 a WU-ág az „USB Composite Device” soron felrakta a `ksusbaud.inf`-et (→ `oem3.inf`). 20:52:05-kor a katalógus-ág ugyanezt a csomagot próbálta a „Sound Blaster Play! 4” (`…&MI_00`) sorra. A pnputil: `Already exists`, `Driver package is up-to-date on device: USB\VID_041E&PID_3274&MI_00\7&887c350&4&0000`, `Added: 0`. A program ennek ellenére ezt írta: *„a gyári csomag MÁR FENT VAN a gépen, de az eszköz még a Windows alapdriverén fut … a KÖTÉS hiányzik”*, és a végén újrakötést ajánlott. 21:00-kor a használat-felmérés: `oem3.inf` HASZNÁLATBAN, és a 21:01-es kézi újrakötés helyesen nem talált semmit. **Ok:** a no-op ág (`all_already and (generic_replace or err_code)`) a keresés-kori `generic_replace` jelzőből döntött, és nem nézte meg, mit mondott a pnputil a kötésről. A sikeres ág ugyanezt a `package_bound_to_device_family`-vel ellenőrzi. **Javítva:** a `generic_replace` eset csak akkor `staged_nobind`, ha a pnputil nem nevezi meg az eszközt (családját); különben „↷ már naprakész”. A hibakódos (`err_code`) eset változatlan. Teszt: `tests/test_field_regressions.py`, `StagedAlreadyBound`, a terepi kimenettel szó szerint, és mindkét iránnyal.
